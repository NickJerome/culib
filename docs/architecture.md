# 系统架构

culib 是一个 C++11 静态库，由三部分组成：

- 一套照 Go 设计的协程运行时：`go()`、`wait_group`、能跨线程用的同步原语，以及写成阻塞形状的网络 I/O。
- 写命令行工具和服务器要用的基础设施：文件、进程与系统、时间、日志、命令行参数、配置、终端、字节缓冲、字符串和数值转换。
- 一个能替换 `malloc` / `new` 的分配器，和一个测试框架。

它只依赖 C++ 标准库和操作系统 API，支持 64 位的 Windows 10 及以上、Linux、macOS，三个平台行为一致。

这份文档讲整体：各层怎么分，每个模块的机制，做过的优化，接口的形状，取舍和不做的事。接口用法见 [API 参考](../api.md)，模块的细节、测量和历史见文中链接的文档和 git 记录。

文中的测量都是同一台机器上同场对比的结果：WSL2，i7-12700，绑在 0–7 号核上，GCC 11.4 `-O2 -DNDEBUG`，另有说明的除外。第 13 节的记分板是提交 `1316887` 的完整运行。

## 1. 取舍的原则

- 基本操作先独立写清楚，功能和优化在上面组合。每个模块拥有自己的状态，只通过几个函数把能力交给上一层。没有虚基类、可插拔后端、策略参数或模板框架。
- 一件事只有一种做法，默认值固定，不给调参项。比如栈 1008 KiB，每调度 61 次看一眼全局，停住 10 毫秒算卡住。
- 可恢复的失败返回 `result<T>`，错误类型只有一种。误用打印一行诊断后终止，release 构建同样检查。全库可以关掉异常和 RTTI。
- 性能主张要有同场对比，量不出收益的改动不留。
- 涉及文件系统的接口按 HDD 和网络盘的代价设计：一次 stat 在本地是 0.5 µs，在网络盘上是一次 0.2–1 ms 的往返，所以库不悄悄多做 I/O。
- 「不做」比「做」更要写下来：试过什么，结果如何，什么条件下重开。第 15 节是这份清单。

## 2. 分层

| 层 | 模块 | 只依赖 |
| --- | --- | --- |
| 基础 | `result`、`optional`、`string_view`、`strings`、`lexical_cast`、`bytes`、`defer`、`time` / `stopwatch`、`os` | C++ 标准库、操作系统 API |
| 内存页 | `mem/pages`：保留、提交、归还、保护地址空间 | 系统的虚拟内存 API |
| 内存 | 通用分配器 `mem`；协程栈池 `mem/stack` | `pages`，两者互不依赖 |
| 协程 | 换栈汇编、控制块 | 分配器（控制块）、栈池（栈） |
| 运行时 | 调度器、定时器、监控线程、事件引擎 | 协程、`os` |
| 同步原语 | `mutex`、`condition_variable`、`channel`、`wait_group` | 运行时的挂起接口（`park.h`） |
| 网络 | `net::socket`、`endpoint`、`resolve` | 运行时的 I/O 接口（`scheduler_io.h`） |
| 文件 | `fs::path`、`file`、`ofstream`、`directory_iterator`、复制、删除 | 基础层 |
| 命令行 | `flag`、`config`、`log`、`term` | 基础层、文件 |
| 测试 | `TEST` / `EXPECT` | 基础层、`term` |

边界的规则：

- 下层不读上层的缓存、配置或调度状态，上层不改下层的内部字段。只搬文件、不减少模块间依赖的，不算简化。
- 平台差异放在文件名带 `_posix`、`_win`、`_linux`、`_macos` 后缀的文件里，由 `xmake.lua` 按平台选择。平台文件和平台无关的部分之间只有一个私有头文件里的几个函数，例如 `fs/directory.h`、`net/net_socket_detail.h`、`platform/os_detail.h`、`mem/stack_detail.h`。编译器之间的差异只在 `include/culib/detail/macros.h` 里判断一次。
- 同步原语只认识挂起接口：记下等待者、挂起、叫醒。网络只认识两件事：把套接字登记到引擎，做一次 I/O。它们都不知道工作线程、就绪队列和监控线程。事件引擎拿着的挂起凭据是一个不透明指针。
- `layers_test` 不链接 culib，直接编译几个底层文件：配置与命令行解析、路径运算、定时堆、页分配。底层要是重新依赖了上层，它在链接时就失败。

## 3. 基础层

### result 与 error

`result<T>` 是值和 `error` 的 union，只构造活着的那个成员，所以成功时不构造 `std::string`，零分配。`error` 是一个 `error_kind` 加一句消息，不带消息的错误也零分配。

错误类型只有这一种。和 `result<int, 枚举>` 比（GCC 14，跨编译单元调用）：

- 成功 11.4 对 8.5 ns。
- 补完上下文的失败 120 ns，两次分配。要每秒 8 万次失败才吃掉一个核的 1%。

所以没有第二种错误类型。省掉的是每个层边界上的一次转换，和每个调用点的一次选择。跨层传播时，在同时知道「哪个文件的哪个字段」的那一层把上下文拼进消息。

不提供 `TRY` 之类的宏：它会把一个 `return` 藏在像变量声明的一行里。取错分支打印诊断后终止。

### optional 与 string_view

两者都自己定义，不在 C++17 下别名到 `std::` 的对应物：使用方可以用更高的标准编译，公共函数的签名和类的布局不能跟着变，否则违反 ODR。跨标准的转换用两边定义相同的受约束构造模板。

`optional<int>` 8 字节、平凡可复制，按 ABI 走寄存器返回。`bytes` 的逐字段读取就是它的调用方。

### strings 与 lexical_cast

`strings` 是一组自由函数：split / join / trim / replace、ASCII 大小写，以及给 Windows W 系列 API 用的 UTF-8 和 UTF-16 互转。全库只用 `std::string`，不另造字符串类。

`lexical_cast<T>` 严格解析：整段输入都要被消费，不接受首尾空白，不猜八进制、十六进制。

- 整数：解析和格式化都是手写的十进制循环。
- 小数解析：一遍扫完语法、尾数和指数。尾数不超过 2^53、10 的幂在 10^22 以内时，一次乘或除就是正确舍入的结果（Clinger 快路径），其余交给 `strtod`。`lexical_cast.parses_exact_decimals_like_strtod` 用 2 万个随机输入和 `strtod` 逐位比对。这一改让记分板上的解析从 90 ns 降到 30 ns。
- 小数格式化：依次试 15、16、17 位有效数字，取第一个能原样读回的。时间几乎都在 `snprintf` 上，比 Go 慢 4 倍多，见第 15 节。

### bytes

`buffer` 是一段内存加读、写两个游标：

- 字节序写在函数名里（`write_u32_be`），没有「主机字节序」的函数。
- `prepare` / `commit` / `consume` 让 I/O 直接读进、写出这段内存，省一次拷贝。
- 读不够时返回空的 `optional`，游标不动。
- 定长整数的写入只在容量不够时才调库里的慢路径，`write_u32_be` 每次 0.8–0.9 ns。

### defer 与 time

`defer { ... };` 在作用域结束时执行。全库只有三个不带前缀的短名字宏，另外两个是 `TEST` 和 `EXPECT`，都可以在包含头文件之前关掉。

`timestamp` 把单位写在类型里。ISO 8601 的格式化、解析和 UTC 的日历换算都是自己算的，只有本地时区问系统。不提供 `strftime` 格式串，也不带时区数据库。

## 4. 内存

### pages

分配器和栈池共用的一层：保留地址、提交、归还、改保护、关掉透明大页。三种平台的做法：

- 默认允许 overcommit 的 Linux：保留下来的地址直接可读写，提交是空操作，归还用 `MADV_DONTNEED`，全程不改映射。
- 严格 overcommit 的 Linux 和 macOS：保留成不可访问，提交时才改成可读写。
- Windows：用 `VirtualAlloc` / `VirtualFree`。

分配器要能替换 `malloc`，所以这一层直接调系统 API，不能经过 `malloc`。

### 通用分配器

结构照 mimalloc，见[分配器实现](mem-internals.md)：

- 地址按 64 MiB 的 chunk 保留、按 64 MiB 对齐，任何地址掩掉低位就是它所在的 chunk。每个 chunk 分成 1024 个 64 KiB 的 slice，开头 3 个是头部（位图和页描述符表）。
- 尺寸档有 49 个。8 KiB 以内的块放在 64 KiB 的页里，8–64 KiB 的放在 512 KiB 的页里。更大的块直接占连续的 slice；一个 chunk 装不下的单独保留，释放时立刻还。
- 每个线程一个堆，每个尺寸档一个可用页队列。快路径只看队首页的空闲链，有就取走。
- 每页三条空闲链：拥有者分配用一条，拥有者释放用一条，别的线程释放用一条。别的线程用 CAS 往上压，拥有者一次摘走整串，所以跨线程释放不拿锁。
- 线程退出时，还有活块的页进共享池，别的线程按尺寸接手。
- 全局只有一把锁，只在慢路径上拿：chunk 列表、slice 位图、共享池。
- 空出来的 slice 至少过 1 秒，才在之后的分配或释放里还给系统；`collect()` 马上还。每档最多留一个空页，免得分配、释放交替时反复换页。
- 释放时查误用，release 同样查：不是本分配器给出的指针（每 64 MiB 地址一位的位图）、块中间的地址、页还掉以后再释放、重复释放（块里写一个随机值）。每对分配和释放因此多执行约 24 条指令。

接入方式有三种：

- 普通依赖只提供显式接口（`mem::alloc` 一族）。
- 依赖 `culib_new_override`，全局 `new` / `delete` 和标准容器就改用它。
- Linux 上还能用 `LD_PRELOAD` 换掉 `malloc`。

mimalloc-bench 的 21 项，几何平均下用时是 glibc 的 91%、mimalloc 的 109%，峰值内存是 glibc 的 113%、mimalloc 的 97%。记分板上，一根线程分配释放小块比 Go 快 3.8 倍；8 根协程同时做，在 8 / 4 根工作线程上快 21 / 13 倍。

### 协程栈池

栈不向分配器要，有自己的池（`mem/stack`）：

- 地址按 64 格一次保留。一格 1 MiB：上面 1008 KiB 可用，最底下 16 KiB 是保护区。一格只在第一次用时准备一次，之后反复复用，不碰系统。
- 协程第一次运行时才取栈，结束时还回去。排着队的协程不占栈。
- 每根工作线程手边留最多 32 格，取、还都不拿锁；不够或者满了，一次和池换 16 格。
- 准备好的空闲格常留 1024 个，多出来的由监控线程每 2 毫秒还 64 根的内存给系统，地址留着。10 万根协程的高峰过后，4 秒内常驻内存回到高峰之前。
- 整个区域标成不用透明大页：栈只碰顶上几页，开了 THP 的系统上一碰就是 2 MiB。
- Linux 和 macOS 的 release 构建不设保护页：每格要多占两个映射，默认的 `vm.max_map_count` 会把并发协程卡在约 3 万根，而容器里改不了这个上限。debug 构建设保护页。代价是 release 里的栈溢出不会被拦住，见第 15 节。
- Windows 上和线程栈一样只提交用到的部分：提交栈顶两页，下面一页放 `PAGE_GUARD`，系统沿保护页往下按需提交，起步只占 12 KiB。换栈时，线程块里的栈底、栈顶和已提交的下界一起切换。协程结束前记下栈长到了哪里，下一根协程接着用。

为什么不向分配器要：

- Windows 上分配器交出去的内存必须已经提交，按需提交只有栈有。
- 保护区要跟着一格走，不能每次设、每次撤。
- 同时活着几十万个大块时，分配器找空位会变慢；栈池取一格是常数时间。

## 5. 运行时

公共行为见[协程运行时](runtime.md)，实现细节见[实现说明](implementation-notes.md#schedulercpp)。

### 协程

`go(f, args...)` 只分配一块，里面是控制块、可调用对象和参数，向 culib 的分配器要。协程常在一根线程上起、在另一根上结束：这个分配器释放别的线程的块是一次 CAS，libc 的 `malloc` 却要抢锁，8 根工作线程起协程会慢一倍。

栈在第一次运行时从栈池取。换栈是汇编，照 Boost.Context 写，覆盖 x86_64 的 SysV 和 Windows ABI，以及 arm64，只存被调用者保存的寄存器。Windows 上另外切换线程块里的栈范围和 fiber 本地存储。

开着 ASan 或 TSan 时，换栈按它们的 fiber 接口标注。进程开着 CET 影子栈时，打印诊断后终止：换栈不切影子栈，系统会直接杀掉进程。

### 调度器

调度器是 Go 的 G-M-P 的简化版。

就绪队列和找活：

- 每根工作线程（`vcpu`）一条就绪队列，由一把自旋锁护着。协程里起的、被工作线程叫醒的排进本线程的队列；普通线程里起的、普通线程叫醒的排进全局队列，全局队列另有一把自旋锁。
- 找活的顺序：本地队列，全局队列，再从别的线程的队首拿一半。每调度 61 次还要看一眼全局队列、事件引擎和所有线程的定时器，免得一直有活的线程把它们饿着。Go 也用 61。
- 每根线程的调度计数只有它自己写、监控线程读，所以用一次读加一次写，不用带锁的加法。`yield` 因此快了 6–9%。

闲着的线程与叫醒：

- 闲着的线程里只有一根等在事件引擎里，同时等 I/O、最早的时限和别的线程的通知。其余的睡在各自的条件变量上。
- 放进活的一方叫醒一根，被叫醒的记成「找活的」。它找到活、又是最后一根找活的，才再叫下一根，这是 Go 的 `wakep` 的简化。一次放进来很多时，线程一根接一根醒；放进一根时，不会把所有闲着的都叫起来。
- 叫醒的协程排进叫醒它的那根工作线程。队里只有它一根时，不叫闲着的线程：叫醒它的协程多半马上挂起或结束，本线程接着跑它，数据还在这个核的缓存里。两根协程来回交替，从 1013 ns 降到 340 ns（8 根工作线程）。叫醒它的协程一直不让出时，由监控线程叫人来偷，最多多等 4 毫秒。
- 叫醒是系统调用，所以放在锁外：锁里只定下叫谁，放了锁再叫。普通线程里起 10 万根协程，从 91–114 ms 降到 51–55 ms（8 根）。
- 一次叫醒一串时（`notify_all`、`wait_group` 等到最后一根、channel 关闭），攒成一批：排进队列只拿一次锁，只叫一根线程。

挂起、定时器和普通线程上的等待：

- 挂起只有一种（`park`）：等定时器、等 I/O、等锁，都是「挂起，直到有人叫醒或者到点」。挂起凭据在等待者自己的栈上，一次挂起零分配。叫醒的一方和到点的一方用一次比较交换定输赢，两者同时发生时只有一方生效。
- 定时器每根工作线程一组：一个最小堆、一把锁，和一个记着最早时限的原子量。到点的协程不管登记在哪根线程上，都按时限的先后排回队列。原来整个进程只有一个堆，1 万个连接带超时回显时，服务端每次往返花 24 µs CPU，拆开以后是 15 µs。Go 从 1.14 起也是每个 P 一个堆。
- 普通线程（`main` 和使用方自己的线程）上的等待者，睡在按凭据地址散列到的 64 个等待格上，等待格从不释放。等待器不放在 `thread_local` 里：MinGW 的 `thread_local` 析构跑在存储释放之后（GCC bug 80816）。

### 监控线程

监控线程每 2 毫秒醒一次。Windows 上它用高精度的可等待定时器睡，不改系统的时钟精度。每次醒来做四件事：

- 交接名额。一根工作线程停在同一根协程里超过 10 毫秒，没有闲着的线程，又有活可做，就把它跑协程的名额，连同它队里的协程，交给备用线程；没有备用的就新起一根，总数不超过 256。C++ 里分不出阻塞的系统调用和长计算，两者一样处理。所以文件读写、DNS 解析和第三方库的阻塞调用可以直接在协程里调。
- 叫人来偷。有闲着的线程，某根线程停住了一个间隔以上，队里还排着协程，就叫一根闲着的来偷。
- 看着事件引擎。没人等在引擎里，却有 I/O 在等或者有定时器，就叫醒一根去等。工作线程都在忙、又有 10 毫秒没人收过完成时，替它们收一次。
- 还多出来的空闲栈。

线程数默认取 `os::cpu_count()`，Linux 上看 CPU 亲和性和 cgroup 的配额（向上取整，和 Go 1.25 一样）。环境变量 `WAVVIX_MAXPROCS` 可以改，代码里不能改。运行时在第一次 `go()` 时起来，之后不析构；`main` 返回时进程直接退出，和 Go 一样。

### 事件引擎

事件引擎整个进程一个。接口是「完成」的形状（「帮我读，读完叫我」），三个后端对等。

Linux epoll 和 macOS kqueue：

- 套接字一建出来，就用边沿触发登记读写两个方向，之后不再改兴趣集。
- I/O 先直接试一次，做不了才排队。就绪时，把这个方向排着的等待者全部叫醒，各自回去重做系统调用，还做不了的重新排队。读写因此分散在各自的工作线程上，不挤在等引擎的那一根上：64 个连接同时来回时，每个来回从 4.7 µs 降到 4.1 µs（8 根工作线程）。
- 登记时先记下这个方向来过几次事件，在锁外试一次系统调用，次数变了就再试一次。系统调用不在锁里，唤醒也不会丢。

Windows IOCP：

- 用 `AcceptEx`、`ConnectEx`、`WSASendTo`、`WSARecvFrom` 等 overlapped 操作。
- 协程的定时器另用高精度定时器加等待完成包按时叫醒，不然要按 15.6 毫秒的节拍。
- 同步完成的操作照样等完成包，不开 `FILE_SKIP_COMPLETION_PORT_ON_SUCCESS`，见第 15 节。

三个后端共有的：

- 等在引擎里的那根线程收到完成以后，自己去跑叫醒的协程，不叫别的线程来接着等。UDP 一来一回在 8 根工作线程上从 25–29 µs 降到 5.6–5.9 µs。
- 以前有过 io_uring 后端，没有可证明的收益，已经移除；`io_request` 因此从 160 字节降到 88 字节。

### 同步原语

`mutex`、`condition_variable`、`channel`、`wait_group` 在协程里只挂起协程，在普通线程里阻塞线程，协程和普通线程之间也能用。

每个对象一把自旋锁，护着等待队列和对象自己的状态。等待队列是照 Linux `list_head` 写的侵入式双向链表，一次等待零分配。锁里只摘下等待者，放了锁再叫醒。

`mutex` 照 Go 的 `sync.Mutex`，有两种模式：

- 平时，醒来的等待者和刚来的一起抢。有等待者等了 1 毫秒以上，就进饥饿模式，直接把锁交给队首。
- 叫醒的那根还没回来抢之前，不再叫第二根，这是 Go 的 `mutexWoken`。锁在这期间又放开了一次，说明放锁的协程不会很快挂起，就叫一根闲着的线程来把醒着的那根偷走。
- 拿得到的 `lock()` 和没人排队的 `unlock()` 内联在头文件里。

8 根协程抢一把锁，每次 13.5 ns，Go 是 31.5 ns。

其余几个：

- `channel` 有界、先进先出，`close()` 不挂起。值的次序由缓冲区保证，不靠等待者的次序。
- 自旋锁拿不到时指数退避，每轮 1 到 64 次 `pause`，16 轮以后让出线程。

### Windows 上的协程栈

- 溢出时，系统在剩下的栈上分发异常，要把 `CONTEXT` 连同扩展状态压上去。带 AMX 的机器上 `CONTEXT` 有 11.3 KiB，而系统默认只留约 11.4 KiB，加上分发的几层调用放不下：分发本身又溢出，进程以访问违例结束，什么都看不到。
- 所以工作线程起来时调一次 `SetThreadStackGuarantee`，要系统溢出时多留 32 KiB，代价是溢出前能用的深度少 24 KiB。CI 上带 AMX 的 runner 在修复前失败过 5 次，修复后通过了。
- MSVC 的 `__chkstk` 按线程块里的已提交下界逐页探，C++ 异常按线程块里的栈范围找帧。所以换栈时这三个值都要和实际一致（见第 4 节）。

## 6. 网络

一个 `net::socket` 承担监听、连接和收发。协议在构造时定，原生套接字到 `bind` / `connect` 时才建。用法写成同步阻塞的样子，多路复用藏在运行时里：在协程里调只挂起协程，在普通线程里调就阻塞线程。见[网络](net.md)。

- 套接字不属于哪根线程：一根协程读、另一根写，读写之间换了线程，或者按值移给别的协程，都行。
- 每个 I/O 调用都带超时。正数是整个操作的预算：`read_exactly` 和 `write` 里的多次读写合用一份，不每轮重新计时。
- 地址只接受数字形式，IPv4 必须是四段十进制，`127.1` 和八进制都不收。`resolve` 直接调系统解析器，会阻塞，卡住了由监控线程交接名额。主机名连接按系统给的顺序逐个试候选地址，DNS 不计入连接超时。
- IPv6 套接字只收 IPv6。
- 建立好的 TCP 连接关掉 Nagle。Linux 回环上先写头、再写体的 20 个来回，从 1.63 秒降到 2.4 毫秒。
- POSIX 上只在显式绑定 TCP 套接字时设 `SO_REUSEADDR`。
- Windows 上关掉「ICMP 端口不可达让下一次接收报错」这一行为。
- 不做：TLS、HTTP、连接式 UDP、用户态缓冲、自动重连。

## 7. 文件

`fs::path` 是 UTF-8 的路径值类型，名字对齐 `std::filesystem`，路径运算只碰字符串。查询是三态：「不存在」是 `false`，「问不成」才是错误。`fs::file` 是只能移动的句柄，`fs::ofstream` 是带缓冲的写，`directory_iterator` 走 range-for，错误放在元素里。

各项操作都按 HDD 和网络盘的代价来做：

- 遍历：每一项带着枚举时顺带给出的类型（POSIX 的 `d_type`、Windows 的查找数据），问「是不是目录」不再 stat。记分板上遍历比 Go 快 2.2 倍。
- 删除：先删，失败了再看是什么，所以删文件和链接是一次系统调用。
- `create_directories`：照 Go 的 `MkdirAll`，先查目标本身。路径已经存在时只发 1 次 stat，原来是每一级一次。
- `copy_file`：Linux 上先让内核拷（`copy_file_range`，只在 5.3 起的内核上用），NFS 4.2 和 SMB 上是服务器端复制；拷不了的情况退回读写。Windows 用 `CopyFileW`。覆盖之前先确认源和目标不是同一个文件：Windows 上认卷号加 FileIndex，认不出就拒绝。
- Windows 上路径转成 UTF-16 调 W 系列 API。长路径、共享模式、reparse point 都在 `fs_win.cpp` 里处理。
- `remove_all` 按路径递归，不防别的进程中途把目录换成链接，见第 15 节。

## 8. 进程与系统

`os` 提供环境变量、程序路径、主机名、进程号、CPU 数和停止信号。

- 环境变量：名字和值的检查在平台无关的一侧。Windows 上读写的是 `GetEnvironmentVariableW` 那份环境；CRT 的 `getenv` 读的是启动时拷下的那份，看不到后来的修改。
- 停止信号：`install_stop_handler()` 要显式调用。POSIX 上处理 SIGINT 和 SIGTERM，处理函数只置一个无锁的标志，不带 `SA_RESTART`，卡在阻塞调用上的线程以 EINTR 返回，好回头查 `stop_requested()`；库自己的系统调用遇到 EINTR 都会重做。Windows 上处理控制台的 Ctrl-C、关窗口、注销和关机，后三种在处理函数里置位以后一直等，让程序自己收尾退出。
- 不做动态库加载和崩溃调用栈。

## 9. 命令行：flag、config、log、term

- `flag`：Go 风格。全局选项对象在 `main` 之前登记，这是全库仅有的两处启动开销之一，另一处是 `TEST`。支持类型化的选项、必填项、位置参数、GNU 风格的重排，自带 `--help` 和 `--version`；`set()` 和 `was_given()` 留给配置文件用。
- `config`：ini 子集，段里的键变成 `section.key`。「键不存在」用默认值，「值写错了」报错，所以 `port = 80 80` 不会悄悄变成默认值。`apply_to_flags()` 让配置文件和命令行共用一套定义，命令行优先。
- `log`：一个默认 logger 加任意个具名 logger，每个 logger 一组 sink，一个 sink 可以挂在几个 logger 上。有两道级别门槛，logger 的级别不够时，`<<` 右边的表达式不求值。一行在调用方的栈上拼好，最多 1024 字节，所有 sink 写同一行。文件一行一次 `write`、不缓冲，所以没有 flush，进程崩了也不丢已经写过的行。支持轮转；写失败时每秒最多报一次。写日志从不挂起协程。见[日志](log.md)。
- `term`：样式是值，写成 `fg::red("x")`，漏掉括号就编译不过，所以不会出现设了颜色忘了恢复。按是不是终端、`NO_COLOR` 和 `TERM` 决定上不上色。Windows 上开 VT 模式，开不起来就输出纯文字。

## 10. 测试框架

`TEST(组, 名)` 登记用例，`EXPECT(a, op, b)` 断言：

- 有符号和无符号整数按数学值比较，两边都是 C 字符串时比较内容。
- 失败时印出两边的值，接着执行。
- 支持 `--filter` 和 `--list`。

会终止进程的用例（误用诊断、崩溃）在子进程里跑，例如 `runtime_faults` 和 `mem_test_security`。断言执行次序的用例放在只有一个名额的 `runtime_order_test` 里，那里同一时刻只有一根线程跑协程，次序是确定的。

## 11. 跨平台的做法

- Windows 源文件一律经 `src/platform/win32.h` 包含 `<windows.h>`。公共头文件不包含平台头文件，也不包含 `<iostream>`。
- 公共头文件存成带 BOM 的 UTF-8，字符串字面量只用 ASCII：使用方在中文代码页下不加 `/utf-8`，开着 `/WX` 也能编过。
- 零警告：GCC / Clang 开全警告加 pedantic，MSVC 开 `/W4`，都当错误。被别的工程当源码依赖引入时，不强加 `-Werror`。
- C++11 以 GCC / Clang 在 `-std=c++11` 下的结果为准，CI 里另有 GCC 4.8。只支持 64 位，Windows 最低是 10。
- 不用 MSVC 弃用的和平台专有的 libc 函数，比如 `getenv`、`gmtime_r`、`fopen` 一族。库自己的接口能做的，就用自己的。
- `thread_local` 只放平凡析构的类型，原因是第 5 节说的 MinGW emutls 问题。

## 12. 接口的形状

- 资源一律是值类型加 RAII：`socket`、`file`、`path`、`buffer`，句柄只能移动。接口里没有要手动释放的指针，`mem` 的 C 语义接口是唯一的例外。
- 协程没有句柄：`go()` 起了就不管，要等它用 `wait_group`，要它的结果用 `channel`。
- 会等的调用只有一个版本：在协程里挂起协程，在普通线程里阻塞线程。
- 错误只有 `result` 加 `error` 一种，误用一律打印诊断后终止。
- 热路径上不用 `std::function` 和虚函数：`go()` 把可调用对象直接放进控制块。等待者是挂在侵入式链表上的栈对象，事件引擎是自由函数加不透明指针。
- 同一件事只有一个函数；行为不同才换名字，名字说明做了什么。

culib 快的有这几类：

- 调度：让出、来回交替、依次建连接。
- 同步：抢锁、channel。
- 定时器：多核时 1 万根同时睡。
- 分配。
- 遍历目录。
- 文本转换和日志。

慢的几处和原因：

- release：醒来的 1 万根都要拿回同一把锁。8 根工作线程时这把锁很快进了饥饿模式，2 万次拿锁里 8 千多次是直接交接，排队挂起近 2 万次，采样六成落在锁内部的自旋锁上。Go 在直接交接时由 `Unlock` 把 P 让给接手的 goroutine。试过把接手的协程排到本线程队列的最前面，没有变快；栈格子缩小能快 0–24%，见第 15 节。
- parked_memory：每根协程的栈占一个 1 MiB 的格子，常驻 4.2 KiB，页表另占约 2 KiB。Go 的栈从 2 KiB 起，不够时整段搬到更大的地方。
- tcp_echo 在多核时：Go 找不到活的线程先自旋一阵，完成常在这几微秒里就到，不用睡下再被叫醒。culib 闲着的线程直接睡。照 Go 做的原型见第 15 节。只有一根工作线程时，culib 快 1.17 倍。
- format_double：时间在 `snprintf` 上，见第 15 节。
- mutex_uncontended：一次自旋锁进出加改标志，11.4 对 10.8 ns。用一个原子字的版本见第 15 节。
- 4 根工作线程时起协程，1 根时依次交接和 1 万根同时睡：Go 快 13–17%，原因没有再查。

## 15. 取舍与不做的事

| 不做的事 | 为什么 | 什么条件下重开 |
| --- | --- | --- |
| 把协程栈缩小到 256 / 128 KiB 一格 | 放行快 0.99–1.24 倍，依次交接快 1.01–1.19 倍，其余不动，每根常驻内存仍是 4.2 KiB；而 Linux / macOS 的 release 没有保护页，栈越小越容易悄悄写坏相邻的那一格 | release 也能设保护页而不多占映射（Linux 6.13 的 `MADV_GUARD_INSTALL`），或者出现同时挂着十万根以上协程、页表内存成了问题的消费者 |
| Linux / macOS release 的保护页 | 每格多两个映射，默认的 `vm.max_map_count` 把并发协程卡在约 3 万根，容器里改不了 | 同上 |
| 找不到活时先自旋（Go 的 spinning M），加上 `runnext` 那样的格子 | 64 个连接同时回显快 1.1–1.4 倍，但依次建连接、UDP 一来一回、两方来回、起协程变慢；这台机器的 0–7 号是 4 个 P 核的超线程，自旋的线程还和同一个核上跑着的那根抢执行单元 | 在没有超线程的机器上重新量，或者出现以多连接回显为主的消费者 |
| `mutex` 用一个原子字（Go 的做法） | 没人抢时 10.9 ns，比现在的 11.4 ns 快一点；但有人排队时，拿着锁的一方每拿放一次多做两次读改写，`mutex_contended` 从 13.5 ns 变成 33 ns | — |
| 拿不到锁先自旋几轮再挂起 | 吞吐高一些，但单次拿锁最长到 8 毫秒，空转期间占着工作线程 | — |
| 全局队列换成无锁环（Photon 的做法） | 只在起得密、每根活不到 1 µs 时快，还要处理环满；实现 171 行，现在的 38 行 | 实际负载里大量起不到 1 µs 的协程，而且全局队列的锁出现在剖析结果里 |
| 从全局队列一次取一批（Go 的 `globrunqget`） | 叫醒挪到锁外以后再比，一处快一处慢；锁更容易进饥饿模式 | 实际负载卡在取的一方抢全局队列的锁上 |
| 小数格式化用 Ryu / Schubfach / Dragonbox | 每种都要一张几百项的 128 位表加两三百行；Grisu2 的表小，但不保证最短。现在的消费者是命令行参数和配置文件 | 出现在热路径上大量格式化浮点的消费者（JSON、指标输出） |
| io_uring 后端 | 曾经实现过；网络调用点上没有证实比 epoll 好，多一套环管理和运行期探测 | 有明确的性能需求和对照测量 |
