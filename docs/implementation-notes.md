# 实现说明

这里记录实现文件原先写在文件头的结构、设计理由与平台取舍。数据结构旁边仍保留维护局部不变量所需的注释；完整历史与验证记录见各节的设计文档。

## 构建依赖

系统链接依赖统一由 `culib` 目标公开传递，测试和使用方通过 `add_deps("culib")` 继承。
Windows 的网络实现需要 `ws2_32`；当前 macOS 实现使用 POSIX 与 kqueue，已移除文件监听器
留下的 `CoreServices` / `CoreFoundation` 链接项。CI 在 macOS 源码依赖示例运行后输出
`otool -L`，便于核对使用方实际加载的动态库。

## [`defer.h`](../include/culib/defer.h)

守卫宏优先用 `__COUNTER__` 生成变量名，支持同一行展开多个 `defer`，也避免 MSVC
开启 `/ZI` 时 `__LINE__` 无法直接拼接的问题。缺少计数器的编译器退回行号，此时同一
作用域的一行只能展开一次。C++11 不保证复制消除，移动时转移 `active_`，保证只有
接收者析构时执行回调；正确性不依赖编译器是否省略移动。

clang 22 起，`-Wpedantic` 把 `__COUNTER__` 报成扩展（`-Wc2y-extensions`：WG14 的 N3457 在 C2y
里把它标准化，clang 把 C++ 里的使用也算作扩展），使用方开着 `-Werror` 写一句 `defer` 或 `TEST`
就编不过；Google Benchmark、Boost.Test、doctest 都撞上过。所以这两个宏的展开用
`WAVVIX_DETAIL_ALLOW_COUNTER_BEGIN` / `END` 包住：在认识这条警告的 clang 上 push、忽略、pop，
屏蔽只覆盖宏自己的展开，使用方自己写的 `__COUNTER__` 照样会报。不退回 `__LINE__`：同一行两个
`defer` 会重名，MSVC 的 `/ZI` 也拼不了。本机 clang 22.1.3 验证过；CI 上的 clang 还没有这条警告，
覆盖不到。

## [`spin_lock.h`](../include/culib/detail/spin_lock.h)

就绪队列、定时器组、协程栈池，以及 `wavvix::mutex`、`condition_variable`、`wait_group` 里护着状态的那把锁，临界区都只有几次指针操作。原来用 `std::mutex`：拿、放各是一次不能内联的库函数调用（glibc 的 `pthread_mutex_lock` / `unlock`），抢不到就睡在 futex 上，放锁的一方还要一次系统调用叫醒它。两根协程来回交替一次，要进出这些锁十几次。

`spin_lock` 拿锁是一次 `exchange`，放锁是一次带 release 的写，都内联。抢不到先执行 64 次 `pause`（arm64 上是 `yield`），在这台 i7-12700 上约 2.3 微秒（一次约 36 纳秒，CPU 之间差得很多），比这些临界区长得多；还拿不到，多半是拿着锁的线程被系统换了下去，就改成 `std::this_thread::yield()`，让它早点回来。不睡：拿着这些锁的地方都不阻塞，睡下要一次系统调用，叫醒又要一次。Go 运行时的锁先转 4 轮、每轮 30 次 `PAUSE`，再让一次线程，最后才睡在 futex 上。`pause` 的指令在 [`spin_lock.cpp`](../src/base/spin_lock.cpp) 里：MSVC 要 `<intrin.h>`，不能放进公共头文件，抢不到时才走到那里，多一次函数调用无所谓。

拿着自旋锁的地方不拿别的锁、不做系统调用，有两处例外：定时器到点时要在那一组的锁里撤销等着的 I/O（凭据在等待者的栈上，等待者要先拿这把锁撤掉自己的定时器才能返回），定时器堆扩容时要分配。同步原语的唤醒分两步，锁里只摘下等待者，见[闲着的工作线程](#闲着的工作线程)；栈池建新区域（`mmap`、`madvise`、分配格子的记录）在锁外做，两根线程同时建的话多出来的格子也挂上去。

调度器的 `state.mutex` 和普通线程等待用的锁要配条件变量用，不换；`poll_mutex` 由等在引擎里的那根一直拿着，也不换。channel 也不换：它在锁里移动使用方的 `T`，可能分配内存，拿锁的时长不由库定。

同场轮流跑五轮，取中位数（WSL2，i7-12700，绑在 8 个核上，GCC 11 `-O2 -DNDEBUG`）：

| | `std::mutex` | `spin_lock` |
| --- | --- | --- |
| 两根协程用锁和条件变量来回交替，1 / 4 / 8 根工作线程 | 312 / 340 / 331 ns | 209 / 228 / 223 ns |
| 1 万根协程排在一把锁上依次交接，1 / 4 / 8 根 | 3.4 / 3.0 / 3.1 ms | 3.0 / 2.1 / 2.7 ms |
| 协程里起 10 万根、等它们跑完，1 / 4 / 8 根 | 0.22 / 0.47 / 0.54 µs / 根 | 0.18 / 0.39 / 0.47 µs / 根 |
| 回显 1 万个连接、读写带超时，服务端每次往返的 CPU | 14.3–16.0 µs | 11.7–13.2 µs |

普通线程 `notify_all` 放行 1 万根在噪声以内；1000 个连接的回显每次往返 9.3–11.6 → 8.3–10.1 µs。

## [`io_engine.h`](../src/runtime/io_engine.h)

相关设计见 [设计文档](superpowers/specs/2026-10-05-event-engine-design.md)。

事件引擎的内部接口。不是公共头文件，使用方不该包含。

抽象取**完成**形状：「帮我读，读完叫我」，不是「等到可读，你自己去读」。那个决定
和它的理由见 superpowers/specs/2026-10-04-scheduler-design.md 第 2 节，账单
（就绪形状在 Windows 上要付什么）见 2026-10-05-event-engine-design.md 第 2 节。

### 分工

**引擎不碰调度，调度器不认识后端。** 接触面只有 io_request 和它里面那个挂起凭据：

  - 引擎负责「这次操作完成了，结果是这些」，把请求追加到完成批次；
  - 调度器从请求取出凭据，把对应的协程排回运行队列。

凭据（park_token）对引擎是**不透明的**：它存着、交回来，一个字段都不读。
请求离开等待链后，完成批次复用它的 `next` 指针组成 FIFO，不分配堆内存。
`io_engine_wait()` 因此不会因同时完成的请求过多而在 `noexcept` 中触发容器扩容。

所以引擎里**一行都不能碰 wavvix::sleep_for**——协程版的 sleep 自己就是靠引擎的
wait() 实现的，在 wait() 里调它就是自己等自己。（这个坑是 Photon 的 master engine
头文件注释里明写着的，照抄过来。）

### 为什么是自由函数加不透明指针

三个后端的状态没有三方共有的部分（epoll 和 kqueue 共用 fd 下标表，IOCP 要句柄关联），
所以 io_engine 只在这里前置声明；调度器只拿指针。

### 跨线程通知

引擎整个进程一个，运行时建它的时候打开内部的 `io_engine_enable_notify()`。别的线程用 `io_engine_notify()` 打断等在引擎里的那根工作线程：队列里来了活而它是唯一闲着的、新的定时器比它要睡到的时刻还早，都走这一条。通知是粘的：发出时没人在等，下一次 `io_engine_wait()` 立刻返回。通知只打断等待，不增加 I/O 完成数，也不进入协程的 `park_token` 队列。

Linux 的 epoll 用非阻塞 `eventfd`；macOS 用 `EVFILT_USER` 和 `NOTE_TRIGGER`；Windows 直接向 IOCP 投递空完成项。通知失败时运行时打印诊断后终止：活已经排进队列，叫不醒等在引擎里的那根就没有别的恢复办法。三个后端的通知由 [`60417e4` 的三平台 CI](https://github.com/NickJerome/culib/actions/runs/38411545278) 验证过（那时每根工作线程一个引擎，通知的代码没有变）。

## [`io_engine_posix.h`](../src/runtime/io_engine_posix.h)

相关设计见 [设计文档](superpowers/specs/2026-10-05-event-engine-design.md)。

两个 POSIX 后端（epoll 和 kqueue）真正共享的那部分。不是公共头文件。

**抽出来的理由是开发机没有 macOS。** 当时连 `<sys/event.h>` 都不可用，
所以让 kqueue 尽可能复用已在 Linux 上测试的完成逻辑，独有部分只负责登记兴趣。
随后 kqueue 在 macOS CI 上编译并通过测试；见[事件引擎的实现验证](superpowers/specs/2026-10-05-event-engine-design.md)。

两个后端在接管 fd 时用边沿触发登记读写两个方向，之后不再改兴趣集，所以除了建引擎、
接管和等待这三处系统调用，其余都在这里共用：`io_enqueue()` 先试一次、做不了就排队，
`io_dequeue()` 撤掉超时的请求，`io_dispatch()` 处理一个 fd 上的读写事件。

引擎整个进程一个，这三件事可能同时发生在几根线程上：协程在一根线程上登记，等在引擎里的那根
在分发，定时器在第三根线程上撤销。同一个 fd 的等待链由同一把锁护着（按 fd 取模分成 64 把）。
登记时「试一次、做不了就排队」整段在锁里：试完放了锁再排队的话，边沿事件落在中间那一刻会被分发
扔掉（那时链上还没有人），排上去的请求再也等不到事件。

等待表按 fd 下标存，按块分配（每块 1024 格，最多 4096 块），块建好以后不移动也不释放，
别的线程拿着格子的地址不会失效；两根线程同时建同一块时，比较交换输了的那根丢掉自己建的。
分配用不抛异常的版本；分配失败时 `io_engine_arm()` 在请求入队前返回 `ENOMEM`，原有等待项保持有效。
完成批次复用请求节点的链指针，不需要扩容容器。

套接字也由引擎建：`io_open_socket()` 和 `io_accept_socket()` 在两个后端里各实现一份，网络层只管调用。Linux 用 `SOCK_NONBLOCK | SOCK_CLOEXEC` 和 `accept4`，一次系统调用就建好，也没有「建好了、还没设 CLOEXEC」的窗口让另一根线程的 fork + exec 把 fd 带进子进程。macOS 没有这两个标志和 `accept4`，建好以后补 4 次 `fcntl`，再设 `SO_NOSIGPIPE`。以前为了 GCC 4.8 那个 CI 用的 CentOS 5（glibc 2.5），Linux 上也是补 `fcntl`：一根协程连、一根协程接各 1000 次，`strace -c` 数到的系统调用从 16625 次降到 8622 次，其中 `fcntl` 从 8004 次降到 0（2026-10-13，WSL2，GCC 11.4 release）。

`epoll_wait()` 与 `kevent()` 被信号打断后，会按单调时钟扣除已经等待的时间，再传入剩余超时；否则连续信号会反复重启完整时限，使一次限时 I/O 或睡眠远超调用方指定的时长。无限等待仍直接重试。

## [`io_engine_linux.cpp`](../src/runtime/io_engine_linux.cpp)

相关设计见 [设计文档](superpowers/specs/2026-10-05-event-engine-design.md)。

Linux 的 epoll 后端。此前曾实现 io_uring；它只服务于套接字公共接口，普通文件 I/O 没有接入公共 API，额外的环管理、运行期探测和每请求字段没有实际调用方，因此移除。x86_64 / GCC 11.4 下 `sizeof(io_request)` 从 160 字节降到 88 字节。历史设计仍在 [io_uring 设计](superpowers/specs/2026-10-08-io-uring-design.md)；有明确的性能需求与对照测量后再考虑恢复。

「完成」形状在一个「就绪」后端上要多做的事，就是**醒来之后当场做一次系统调用**——
那段在 io_engine_posix.h 的 io_complete() 里，和 kqueue 后端共用同一份。本文件只管
epoll 独有的那件事：怎么登记。

**接管时用 `EPOLLIN | EPOLLOUT | EPOLLET` 登记一次，之后不再改。** 早先取水平触发、
每次等待前 `epoll_ctl` 登记、完成后撤销，理由是边沿触发要求「一直读到 EAGAIN」，
像是「一个 fd 一个常驻读循环」的用法（设计文档 6.1）。但两条已有的规则正好补上了这个要求：

- **每次读写先直接试一次。** 已经就绪的数据不靠通知也拿得到，所以某次事件来时没人在等、
  事件被丢掉，也不会让后来的请求漏掉数据。
- **事件来了把这个方向排着的请求一直做到 EAGAIN 或者队列空。** 同方向有人排队时新请求不试、
  直接排到后面，所以排着的请求一定在等一次还没来的事件。

`connect` 之前就登记，新建套接字在登记那一刻是可写的；但 `epoll_wait` 取事件时会重新检查
当前状态，连接还在进行中，这个过期的可写不会被报出来，不会把没连上的 `connect` 当成成功。

同一根工作线程上两根协程经 TCP 回环来回传 1 字节（WSL2，GCC 11.4 `-O2`，绑在同一个 CPU 上，
新旧交替各跑 3 遍）：每个来回从 5.87–5.95 µs 降到 4.71–4.80 µs；系统调用从 12 次降到 8 次，
少掉的正是每次等待时登记、撤销兴趣的 4 次 `epoll_ctl`。代码也少了一套「已登记掩码」的状态。

fd 关闭时内核自动把它从 epoll 里摘掉；号码被复用后，新句柄建出来时会再接管一次。

## [`io_engine_macos.cpp`](../src/runtime/io_engine_macos.cpp)

相关设计见 [设计文档](superpowers/specs/2026-10-05-event-engine-design.md)。

事件引擎的 kqueue 后端。

「完成」形状多付的那次系统调用在 io_engine_posix.h 的 io_complete() 里，和 epoll
后端共用同一份——**这是为了缩小 kqueue 独有的实现面**。开发机没有 macOS，
但后续已由 macOS CI 验证编译和行为；见本页前面的 `io_engine_posix.h` 说明。

和 epoll 一样在接管时登记一次：一次 `kevent()` 提交 EVFILT_READ 和 EVFILT_WRITE 两条
过滤器，都带 `EV_CLEAR`。`EV_CLEAR` 让过滤器在事件取走后清掉状态，再有新数据或新空间
才再报，效果相当于 epoll 的边沿触发，上面 epoll 那节的两条规则在这里同样成立。
`nevents` 传 0 时只提交不收事件，登记失败通过返回值和 `errno` 报告。

等待时不提交任何变更，所以返回的事件里不会出现 `EV_ERROR`，原来那条「整个方向报废、
把排着的请求全部收掉」的分支随之删掉。未连接的套接字不报可写，`connect` 不会被提前当成完成。

早先每次等待前登记、完成后撤销，还讨论过把变更攒到下一次 `kevent()` 一起提交；
接管时登记一次之后，等待路径上已经没有变更要提交，这个问题不再存在。

## [`io_engine_win.cpp`](../src/runtime/io_engine_win.cpp)

相关设计见 [设计文档](superpowers/specs/2026-10-05-event-engine-design.md)。

事件引擎的 IOCP 后端。

**这一边不用模拟任何东西。** IOCP 原生就是「完成」形状：发出一个 overlapped 操作，
完成包回来时结果已经在里面——epoll / kqueue 那边要在醒来之后补一次 read / write，
这里一次都不用。参照实现为了把 IOCP 塞进「就绪」形状付了什么（`\Device\Afd`、
硬编码的 IOCTL_AFD_POLL、一个自管道、一套重提交状态机，外加一整套平行的完成式
API），见 superpowers/specs/2026-10-05-event-engine-design.md 第 2 节。
那张账单是选定这个形状的全部理由。

写的时候本机只有 MinGW 交叉编译 + wine，真 MSVC 是推上 CI 才第一次编到、跑到的
（`3a766aa` 那次全绿，`3e8ed8d` 记录）。

取消操作后始终等对应完成包。`CancelIoEx` 报 `ERROR_NOT_FOUND` 时，操作可能已完成，
但完成包仍在 IOCP 队列；此时释放请求栈帧会让包里的 `OVERLAPPED` 地址悬空。
Windows 测试先确认读操作完成，再取消并取包，覆盖这个时序。

「确认读操作完成」只能对当场完成的读做。句柄关联了完成端口时，挂起以后才完成的操作，`OVERLAPPED` 里的状态要等完成包被取走才写回：先发起读、再从对端写一个字节，`WSAGetOverlappedResult(FALSE)` 轮询 50 毫秒一直报没完成，`GetQueuedCompletionStatus` 取到包以后才报完成；不关联完成端口的对照组轮询就看得到。这条测试原来先 `send` 再发起读，平时字节已经到了、读当场完成，偶尔晚到一点读就挂起，测试单独连跑 600 遍失败 1 次；现在先用 `FIONREAD` 等字节到了再发起读。引擎自己只在取到完成包以后读结果，不受影响。

完成端口不设并发上限（`MAXDWORD`，Go 的 netpoll 也这样）。这个参数限制的是「在端口上取过完成项、
还没阻塞的线程」最多几根：每根工作线程都可能等过引擎，之后去跑协程，上限取 1 的话，只要有一根
这样的线程还在跑，等在端口里的那根就被扣着放不出来，完成项和唤醒都堆在端口里。改成整个进程一个端口时
踩到过：一根协程占着它的工作线程，另一根等在端口里的线程拿不到唤醒，测试挂死。每根工作线程一个端口时
只有它自己等，这个参数无所谓。

句柄关联由创建句柄的调用方完成，引擎不缓存“已关联的句柄值”，因为系统会复用这个数值。完成项通过 OVERLAPPED 地址找到请求，完成键无需另存索引。后端未启用 FILE_SKIP_COMPLETION_PORT_ON_SUCCESS：同步成功同样等待完成包，保证内核持有 OVERLAPPED 期间请求一直存活；不为省去一次让出再增加一套同步完成分支。读方向的 ERROR_HANDLE_EOF / ERROR_BROKEN_PIPE 统一返回 0 字节，写方向保留错误，与 POSIX 语义一致。

### 按时醒

`GetQueuedCompletionStatusEx` 的超时按系统定时器的节拍到期，默认约 15.6 毫秒。协程的定时器靠等在引擎里的那根线程按最早的时限醒，所以协程里 `sleep_for(1ms)` 原来要睡 15 毫秒上下。CI 上也看得到（[`134e177` 那次](https://github.com/NickJerome/culib/actions/runs/39215374595)）：等 20 毫秒的测试在 Windows 上用 31 毫秒左右，在 Linux 上是 20 毫秒出头。

现在带超时的等待另设一个高精度定时器（`CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`，Windows 10 1803 起），用等待完成包把它接到完成端口上：`NtAssociateWaitCompletionPacket` 让定时器到点时往端口里投一个包，等待就醒了。这个包不带 `OVERLAPPED`，和 `io_engine_notify()` 的唤醒包一样被跳过。毫秒超时照旧传给 `GetQueuedCompletionStatusEx`，只是兜底。Go 的 netpoll 也这么做（`netpoll_windows.go` 的 `netpollQueueTimer`）；它每根 M 一套定时器和包，这里同一时刻只有一根线程在 `io_engine_wait()` 里（`poll_mutex`），整个引擎一套就够。等待完成包的三个函数在 ntdll 里，learn.microsoft.com 从 2023 年起有文档，但没有头文件和导入库，只能 `GetProcAddress`。

一个包同一时刻只能关联一次。等待常被 I/O 或唤醒提前叫醒，那时定时器还没到点，所以每次设之前先 `NtCancelWaitCompletionPacket(packet, TRUE)` 撤掉上一次的；已经到点、包还在端口里没取走的，也一并撤掉。撤不下来（上一次的包正在投）时，后面的关联会失败，这一次只按毫秒超时醒。用一个独立程序在本机（Windows 10 22H2）核对过这几种情况：从没关联过时撤销返回 `STATUS_CANCELLED`；已经关联时再关联返回 `STATUS_INVALID_PARAMETER_1`；到点前撤销、到点后包还在端口里时撤销都返回成功，端口里不留包；包取走以后撤销返回 `STATUS_CANCELLED`；关联时定时器已经到点，包当场投进端口。

同一个程序量的精度（各 100 次，跑两遍）：

| 等多久 | 只用超时：中位数 | 定时器 + 等待完成包：中位数 / 最大 |
| --- | ---: | ---: |
| 1 毫秒 | 14.1、14.1 毫秒 | 1.40、1.38 / 2.24 毫秒 |
| 2 毫秒 | 13.1、13.1 毫秒 | 2.43、2.41 / 3.14 毫秒 |
| 5 毫秒 | 10.1、10.1 毫秒 | 5.37、5.36 / 9.84 毫秒 |

每次带超时的等待多三个系统调用，一共约 0.6 微秒。协程里 `sleep_for(1ms)` 的中位数从 15.46、15.49 毫秒变成 1.39、1.37 毫秒（同一个程序，改动前后各跑两遍）。

建不起来时（Windows 10 1803 以前没有高精度定时器，较老的 Wine 没有等待完成包）退回原来的做法，只按毫秒超时醒。`runtime_order.a_short_sleep_lasts_about_as_long_as_asked` 查睡 1 毫秒的中位数在 5 毫秒以内：把函数名改错、强制走这条退路时它失败（中位数 15.5 毫秒），其余测试照常通过。

只管协程。协程外的 `sleep_for` 就是 `std::this_thread::sleep_for`，普通线程上的限时等待用条件变量，它们在 Windows 上仍按节拍醒。

没用 `timeBeginPeriod(1)`：它让进程里所有的等待都按 1 毫秒醒，系统定时器中断跟着变密、更耗电，还要链接 winmm。Go 也只在建不起高精度定时器时才调它（`os_windows.go` 的 `osRelax`）。也没用 APC（定时器到点时往线程里排一个 APC，在可警告状态下等端口）：APC 只排给设定时器的那根线程，而等在端口里的线程每次可能不同；可警告的等待还会顺带执行别人排给这根线程的 APC。

## [`park.h`](../src/runtime/park.h)

相关设计见 [设计文档](superpowers/specs/2026-10-05-sync-and-timeout-design.md)。

一次挂起的凭据。不是公共头文件。

调度器、事件引擎、同步原语三方共用它，所以它放在比三者都低的一层。

### 为什么要有这个东西

第三期之前，调度器有两条互不相干的挂起路径：等定时器（`sleeping` 容器）和等 I/O
（引擎拿着）。第五期要的是「等 X，但最多等这么久」——**超时和同步原语需要的是同一
件事**，而那件事两条路径都给不了：定时器那条没法被提前叫醒，I/O 那条没有时限。

所以两条并成一条：**挂起，直到有人叫醒我或者到点**。

  - `sleep_for` 是「没人会叫我的 park」，所以它必然超时返回；
  - 等 I/O 是「引擎会叫我的 park」，加上时限就是带超时的读写；
  - `mutex::lock` 是「持有者会叫我的 park」，加上时限就是 `try_lock_for`。

一个机制，三种用法，而调度器里只剩一个挂起容器。

### 它活在哪

**等待者自己的栈上**，和 io_request 一样，所以不需要任何分配。挂起期间栈不会动，协程换了线程继续也不动，所以把它的地址交给别人是安全的——这正是 `mutex` 的等待队列里能串它的原因。登记的一方（同步原语的 `enqueue()`、`scheduler_io()`）先调 `park_prepare()` 记下等待者是谁（协程的控制块，或者普通线程的等待器），再让凭据对别的线程可见。

带时限的协程等待把凭据放进它所在那根工作线程的定时器堆（`timer_heap`，每根一组、各一把锁），凭据记着自己在哪一组（`timers`），`timed` 标着它还在不在堆里；堆和这个标记都在那一组的锁里读写。

### 唤醒和到点

凭据的 `state` 从 `waiting` 出发，唤醒者比较交换成 `woken`，到点的一方比较交换成 `timed_out`，先换成的一方说了算：唤醒者输了就换下一个等待者（见本页 `sync.cpp` 一节的交棒），到点的一方输了什么也不做，等待者照被唤醒返回。

协程等待者的「到点」由定时器那边做：叫醒到点定时器的那根工作线程在那一组的锁里把凭据移出堆、做那次比较交换（`fire_timers()`）。等待者被唤醒者叫醒时，返回之前也要拿这把锁把自己的定时器撤掉（`remove_timer()`），所以定时器那边拿着凭据的整段时间里，凭据一定还在；锁外它只碰协程的控制块。

等 I/O 的协程到点时不和完成的一路比较交换，而是请引擎撤掉那次操作（`give_up()`）：POSIX 上在 fd 的锁里同步摘下，摘得下就按超时结束、由定时器叫醒；摘不下（分发已经把它做完了），或者在 Windows 上（`CancelIoEx` 之后完成包照样会来），都由完成的那一路叫醒，结果看请求本身——撤销之前已经做成的照常返回，读到的字节不丢。所以一次 I/O 等待只被叫醒一次，凭据只会在完成包取回之后才离开栈帧。

唤醒者赢了比较交换以后把协程放回就绪队列（`make_runnable()`）。协程可能还在挂起的路上：排进了等待队列、放了锁，还没切出去。所以协程控制块上另有一个 `park_state`：协程切出去以后，它所在的工作线程把 `running` 换成 `parked`（`run()`）；唤醒者把它换成 `woken`，换之前是 `parked` 才由唤醒者放回队列，否则由那根工作线程切出来以后放回。一根协程因此不会同时在两根线程上跑。原来按线程投递的收件口随之删掉：唤醒者不用知道等待者在哪根线程上，也不用等送达。

### 普通线程上的等待

不在工作线程上的协程里（`main`、普通线程）挂起时，`park_prepare()` 不填 `home`，而是填本线程的等待器 `parker`：每根线程一个，一把 `std::mutex` 加一个条件变量，跟着线程走（`thread_local`）。`scheduler_park()` 在等待器的锁里等 `delivered` 置位；`scheduler_wake()` 赢了比较交换以后在同一把锁里置 `delivered` 并通知。等待者看到 `delivered` 才返回，所以唤醒者放锁之前凭据一直在；放锁以后唤醒者只碰等待器，而等待器比这一次等待活得久。超时和唤醒同时发生时仍是那次比较交换定输赢，等待者输了就在等待器上等 `delivered`。同一套原语于是在协程和普通线程之间都能用：一方在协程里、一方在 `main` 里也行。

`mutex_order.does_not_lose_the_lock_when_a_waiter_times_out` 在一根线程上把超时和放锁排在同一时刻；`mutex.timed_waiters_on_several_workers_never_lose_the_lock` 让 8 根协程在 4 根线程上以 20 µs 的时限抢一把持有时会让出的锁。

## 协程栈

[`stack.cpp`](../src/mem/stack.cpp) 是协程栈的池，和分配器并列，都只建在 `mem/pages` 上。地址按 64 格一次保留，一格 1 MiB：上面 1008 KiB 可用（`default_stack_size`），最底下 16 KiB 是保护区。协程第一次运行时取一格，结束时还回来，下一根协程接着用；工作线程手边先留几格，取还不拿锁（见下）。一格只在第一次用时准备一次（Windows 上提交栈顶、放保护页；Linux / macOS 的 debug 构建设保护页），之后反复复用不碰系统。准备好的空闲格常留 1024 个；再多的还回来时挂到另一串上，下一根协程照样直接用，内存由监控线程每 2 毫秒还 64 根给系统（`trim_stacks()`），地址留着，下次重新准备。区域整段标成不用透明大页：栈只碰顶上几页，开了 THP 的系统上一碰就是 2 MiB。比一格大的栈（只有自己指定了栈大小的 `fiber`）单独保留，用完直接还。和操作系统打交道的三步在 [`stack_posix.cpp`](../src/mem/stack_posix.cpp) / [`stack_win.cpp`](../src/mem/stack_win.cpp)。控制块和可调用对象另在一块堆内存里，不在栈顶。

### 工作线程手边的栈

8 根工作线程一起起协程时，栈池的锁成了瓶颈：协程里起 30 万根空协程，perf 的采样有一半多落在 `allocate_stack` / `release_stack` 抢这把锁上。现在每根工作线程手边留最多 32 格准备好的空闲栈（`cache_stacks_on_this_thread()`）：还回来的先放这里，取的时候先用这里的，都不拿锁；手边空了从栈池一次拿 16 格，满了一次还 16 格。普通线程不留，它们会退出，手边的格子就还不回去了；工作线程从不退出。手边的格子不算进常留的 1024 格，监控线程也不还它们的内存：每根工作线程最多多留 32 格，一格只碰过栈顶几页。

协程里起 10 万根空协程、等它们跑完，同场轮流七轮的中位数（WSL2，i7-12700，绑在 8 个核上，GCC 11 `-O2 -DNDEBUG`），每根：

| 1 / 4 / 8 根工作线程 | 原来 | 手边留栈 |
| --- | --- | --- |
| 控制块走 glibc 的 `malloc` | 0.17 / 0.36 / 0.45 µs | 0.16 / 0.34 / 0.40 µs |
| 控制块走 culib 的分配器（链上 `culib_new_override`） | 0.13 / 0.26 / 0.44 µs | 0.12 / 0.22 / 0.19 µs |
| Go 1.24.5 | 0.76 / 0.17 / 0.16 µs | |

控制块走 glibc 的 `malloc` 时，剩下的时间多半在 `malloc` 的 arena 锁上（采样一半落在 libc 里，`__lll_lock_wait_private` 和 `free`）：控制块在起协程的那根线程上分配，在跑完它的那根线程上释放。culib 的分配器释放别的线程的块是一次 CAS，不拿锁（见[分配器实现](mem-internals.md#分配和释放)）。来回交替、依次交接、放行和回显在噪声以内。

### 高峰过后还内存

原来常留的 1024 个满了以后，再还回来的每一根当场把内存还给系统：Linux 上一次 `madvise(MADV_DONTNEED)`，进程里还有别的线程在跑时还要跨核刷 TLB。这一步就做在协程结束的路上。1 万根协程同时活着、再一根接一根结束（排在一把锁上依次交接，或者条件变量一次放行）时，九千多根各做一次：一根工作线程时每根约 2.5 微秒，4 到 8 根工作线程时约 6.5 微秒，占了整段时间的八成以上。是和 Go 对照时发现的：同样 1 万根 goroutine 依次交接，Go 只要 3 到 4 毫秒。

现在多出来的先挂着，监控线程每 2 毫秒还 64 根，还完了才睡；协程结束时不做系统调用。同场轮流跑四轮（WSL2，i7-12700，绑在 8 个核上，GCC 11 `-O2 -DNDEBUG`）：

| | 改之前 | 改之后 |
| --- | --- | --- |
| 1 万根排在一把锁上依次交接，1 / 4 / 8 根工作线程 | 26–29 / 67–69 / 67–75 ms | 3.3–3.8 / 9.1–10.2 / 9.8–11.3 ms |
| 普通线程 `notify_all` 放行 1 万根，1 / 4 / 8 根 | 30–34 / 74–83 / 77–90 ms | 6.5–7.2 / 17–23 / 18–24 ms |

起协程、来回交替和回显不变。代价是内存还得晚：10 万根协程同时睡 50 毫秒，全部结束时进程 RSS 原来是 9–23 MiB、1 秒后 9 MiB，现在是 196–231 MiB、1 秒后 87–118 MiB、4 秒后 9 MiB。`runtime.gives_surplus_stacks_back_to_the_system_after_a_peak` 查高峰过后多出来的栈最后都还掉了、一共还的根数涨了：去掉监控线程里还栈的那一行，它等满 5 秒后失败。原来看的是高峰刚过那一刻还剩几根，ASan 下协程结束得慢，监控线程边产生边还，那一刻已经还完了。

### 为什么不向分配器要

栈以前向分配器要（`mem::aligned_alloc`）。三件事让它不合适：

- Windows 上分配器交出去的内存必须已经提交：它可能被当成 `ReadFile` 的缓冲区，而内核往没提交的页里写时不会走到用户态的异常处理，调用直接失败（实测错误 998）。1 MiB 的栈整块提交，每根协程就占 1 MiB 提交额度。按需提交是操作系统只给栈的机制，见下一节。
- 保护区要跟着这一格走：同一格反复复用时保护页只设一次。分配器回收的地址会切给任意大小的分配，保护页得每次设、每次撤，debug 构建每根协程多两次系统调用。
- 分配器给大块时从第一个 chunk 往后找空位，同时活着的块越多越慢：同时活着 5 万 / 30 万个 240 KiB 的块，每次分配 3.4 / 34 µs（2026-10-19，WSL2，GCC 11.4 `-O2`）。量到的这个情况正是协程栈；栈池取一格是常数时间。

### Windows：只提交用到的部分

和线程栈一样：保留整格，提交栈顶两页，下面一页设成 `PAGE_GUARD`。碰到保护页时系统再提交一页、把保护页往下挪；长到保护区（最底下 16 KiB，从不提交）就报 `STATUS_STACK_OVERFLOW`。起步只占 12 KiB 提交额度。

系统怎么判断该不该扩栈，微软没写成文档。本机（Windows 10 19045 x64）实测和反汇编的结论：

- 出错的地址落在线程块的 `DeallocationStack` 和 `StackBase` 之间，系统才扩栈，并更新线程块的 `StackLimit`；否则当成普通的保护页违例报出去。
- MSVC 的 `__chkstk`（栈帧超过一页时调用）只逐页探 `StackLimit` 以下的部分。`StackLimit` 比真实的已提交下界低，就会跳过没提交的页，直接访问违例。
- 抛 C++ 异常时，系统按线程块的范围找各帧。`StackLimit` 比真实的已提交下界高、帧又在它下面时，异常找不到 `catch`，进程以 `0xE06D7363` 终止。

所以换栈时线程块里的栈底、栈顶和已提交下界都要跟着切（换栈汇编照 Boost.Context 本来就在切），而且已提交下界要说实话：

- `make_context` 多接一个参数，新协程的已提交下界是栈顶两页的下沿。Boost.Context 写的是整根栈的下沿：它的栈本来就整块提交。
- 协程结束前、还在这根栈上时读线程块的 `StackLimit`，记在这一格上（`note_stack_growth`），下一根协程从这里接着用。没跑完就销毁的协程不知道长到了哪里，那一格先整块撤销提交，下次重新准备。

实测：起步 12 KiB，递归 500 层（每层 1 KiB）后 540 KiB，超出保留范围时以 `0xC00000FD` 终止。两个反向验证：不记已提交下界时，复用深栈的协程在深处抛异常，进程以 `0xE06D7363` 终止（`fiber.throws_from_deep_in_a_reused_stack`）；不放保护页、整格提交时，溢出变成访问违例 `0xC0000005`（`runtime_faults.stack_overflow` 失败）。单独保留、提交、放保护页、释放一根栈约 5 µs，所以这几步只在一格第一次用时做。

溢出时系统先报 `STATUS_STACK_OVERFLOW`，异常就在剩下的栈上分发。本机量过还剩多少：出错时 rsp 离 `DeallocationStack` 约 15.8 KiB，系统把已提交的下界放到 `DeallocationStack` 往上一页，所以还有约 11.7 KiB，分发到向量化异常处理时用掉 2.5 KiB（其中 `CONTEXT` 连扩展状态 1663 字节）。同一段递归放在线程栈上，出错时 rsp 离 `DeallocationStack` 16.1 KiB，和协程栈一样。

[`9cad3fd` 的 CI](https://github.com/NickJerome/culib/actions/runs/39220220574) 里，MSVC release 那一格的 `runtime_faults.stack_overflow` 以 `0xC0000005` 结束；前两次运行用的是同一个镜像、同一版 MSVC，都是 `0xC00000FD`。原因没有确定，本机复现不出来。这条用例原来只看退出码，把「系统报了栈溢出」和「之后的默认处理」混在一起。现在子进程里装一个向量化异常处理，第一时间看到 `STATUS_STACK_OVERFLOW` 就往 stderr 写一行，父进程看这一行，退出码只报出来，印在用例的 OK 行里。不放保护页、整格提交时它仍然失败：`0xC0000005`，没有那一行。

[`9bf6b0b` 的 CI](https://github.com/NickJerome/culib/actions/runs/39375520160) 里又出现一次，这次用例印出了分发异常用的 `CONTEXT` 大小：11567 字节，扩展状态 0x608E7，比本机多了 AVX-512 和 AMX（第 17、18 位）。存下来的 CI 日志里，通过的 31 个 Windows 作业的 `CONTEXT` 是 1663、3247 或 3263 字节，扩展状态里都没有 AMX。溢出以后留给异常分发的栈约 11.7 KiB，装不下 11.5 KiB 的 `CONTEXT`，所以很可能是 runner 分到带 AMX 的机器时，分发本身又溢出了一次，变成访问违例。[`ce52538` 的 CI](https://github.com/NickJerome/culib/actions/runs/39397847169) 里又是一样的 11567 字节、0x608E7。还没有修：要修得在栈底按 `CONTEXT` 的实际大小多留出空间，本机没有 AMX，验证不了。

没覆盖的：线程块里的 `GuaranteedStackBytes` 没有跟着切（Boost.Context 也没切，只有调过 `SetThreadStackGuarantee` 的线程才受影响）；arm64 Windows 没有换栈汇编。CET 影子栈见[下面](#cet-影子栈)。

### CET 影子栈

CPU 支持 CET（Intel 11 代、AMD Zen 3 起）时，系统可以给进程开用户态影子栈：`call` 把返回地址同时压进一个只有硬件能写的影子栈，`ret` 时两边对不上就终止进程。Windows 10 2004 起，系统给用 `/CETCOMPAT` 链接的 exe 开。换栈只切栈指针，不切影子栈：`wavvix_jump_context` 和 Boost.Context 一样用 `pop` 加 `jmp` 跳到对面，切换本身没有 `ret`，但切回调度器以后，`coroutine_resume` 的第一个 `ret` 就和影子栈对不上。本机（i7-12700，Windows 10 22H2）实测：同一个起几根协程的程序，不加 `/CETCOMPAT` 正常结束，加了以后以 `0xC0000409` 终止，没有任何输出。

要真支持，每根协程得有自己的影子栈。Windows 没有给用户代码建影子栈的公开接口，只有系统的 fiber（`CreateFiber` / `SwitchToFiber`）会替它建。所以运行时在协程第一次跑起来之前查一次进程的缓解策略（`GetProcessMitigationPolicy` 的 `ProcessUserShadowStackPolicy`，见 [`shadow_stack_win.cpp`](../src/runtime/shadow_stack_win.cpp)），开着就打印诊断后终止，告诉使用方去掉 `/CETCOMPAT`。[`tests/process/cet.cpp`](../tests/process/cet.cpp) 用 `/CETCOMPAT` 链接，在子进程里起一根让出一次的协程，查它以这句诊断终止；去掉这个检查时子进程以 `0xC0000409` 终止，测试失败。协程不让出、一下子跑完的话，进程可能在那个 `ret` 之前就退出了，查不出来，所以要让出一次。机器不支持 CET 时，测试打印 SKIP。CI 的 Windows runner 支持 CET：[`5b82477` 的 CI](https://github.com/NickJerome/culib/actions/runs/39226069857) 里这条测试在 MSVC 的 release、debug 两格都真跑了，而别的测试程序照常运行，说明 xmake 用 MSVC 14.51 链接时默认不加 `/CETCOMPAT`。runner 不全是同一种机器：[`a0466ec` 的 CI](https://github.com/NickJerome/culib/actions/runs/39379236801) 里 release 那一格分到的机器不给影子栈（扩展状态 0xE7，没有 CET 那一位），这条打印 SKIP；debug 那一格照常跑了。

Linux 上可执行文件和它加载的库都标了 SHSTK，才可能开影子栈；链接器只在每个输入的目标文件都带这个标记时才给可执行文件标上。Ubuntu 的 GCC 默认 `-fcf-protection=full`，C++ 的目标文件都带标记，换栈汇编的目标文件没有，链接出来的程序就没有（`readelf -n` 看过）。macOS 没有 CET。所以只查 Windows。

### 为什么 Linux / macOS 的 release 不设保护页

在 Linux 上，保护页每根栈要多占映射：改了保护的那一页把一段映射拆成两段。默认的 `vm.max_map_count` 是 65530，每根带保护页的栈占 2 个映射，并发协程数卡在约 3.2 万根，再多就分配不到栈，打印诊断后终止。ws / API 服务器常要数十万根。这个上限只能在宿主机上改：容器里 `/proc/sys` 是只读的，`docker run --sysctl vm.max_map_count=...` 直接被拒绝（`not allowed`）。在 6.13 以下的内核上，任何形式的保护页都要占映射。Windows 没有这个上限，保护页也是按需提交本来就有的。

撞到上限时坏掉的不只是协程：映射数用完后，进程里任何需要新映射的分配都会失败。旧实现（每根栈各自 `mmap`）同时挂起 30 万根协程的实测里，第 32746 根 `spawn` 返回 `resource_exhausted`，接着调度器自己的定时堆扩容失败，整个进程以 `std::bad_alloc` 退出。

栈池的实测（2026-10-19，WSL2，GCC 11.4 `-O2`，THP 为 `madvise`；每根协程碰 1 KiB 栈后挂起；和改之前的 240 KiB、向分配器要的栈同场对比）：

| | 改之前 | 栈池，1008 KiB |
| --- | ---: | ---: |
| 每根常驻 | 4.7 KiB | 4.2 KiB |
| 每根页表 | 0.5 KiB | 2.0 KiB |
| 映射数，1 万 / 10 万 / 30 万根 | 82 / 436 / 1220 | 198 / 1605 / 4730 |
| 每根创建耗时，1 万 / 10 万 / 30 万根 | 2.1 / 8.1 / 23.7 µs | 2.6 / 2.1 / 2.0 µs |

映射只随区域增长，64 格一个区域，30 万根约 4700 个。页表多 1.5 KiB：一张页表管 2 MiB 地址，以前 8 根栈共用一张，现在 2 根。常驻少 0.5 KiB：分配器要给每个 64 KiB 的片记一条描述符，栈池不用。

Boost.Context 默认也不设保护页：`default_stack` 是用 `std::malloc` 分配的 `fixedsize_stack`，带保护页的 `protected_fixedsize_stack` 要显式选。

### debug 构建保留保护页

不设保护页时，溢出的症状出现在别的协程上，开发者看不出原因。旧实现里实测协程 A 递归 300 层、每层写满 1 KiB，越界写进紧挨在下面的协程 B：不设保护页时 A 正常结束，B 的挂起凭据被写坏，再也醒不过来，程序卡住，没有任何输出；有保护页时 A 在越界的那一刻 SIGSEGV，gdb 的调用栈直接指向第 254 层递归。所以 Linux / macOS 的 debug 构建保留保护页：开发和测试时溢出当场崩溃，CI 的 debug 与 sanitizer 任务也一直带着它，`runtime_faults.stack_overflow` 在 debug 构建里查这一点。代价是 debug 构建在 Linux 默认设置下最多约 3.2 万根并发协程。

### 代价有多大

把栈填满固定字节、协程结束时从栈底往上扫，量每根协程最深用到多少栈（WSL2，GCC 11.4，`-O2`）：

| 代码 | 最深用栈 |
| --- | ---: |
| culib 全部测试里的协程（1294 根） | 4.1 KiB |
| `snprintf` 格式化浮点数 / `ostringstream` | 3.4 / 3.9 KiB |
| 抛出并捕获异常 | 3.4 KiB |
| `std::sort` 100 万个 `int` | 1.0 KiB |
| `net::resolve("github.com")`，走 DNS | 11.5 KiB |

普通代码在 1008 KiB 的默认栈上有 80 多倍余量。会用超的只有递归深度随输入增长的代码，栈开多大只是把门槛往后挪。下表的最后一列按每单位的用量从 240 KiB 时的实测折算，没有逐个重量：

| 代码 | 每单位输入用的栈 | 240 KiB 时实测 | 1008 KiB 折算 |
| --- | ---: | ---: | ---: |
| `std::regex_match`，GCC 11.4 的 libstdc++ | 约 0.7 KiB / 字符 | 第 347 个字符时用完（gdb 看到 3835 层调用） | 约 1450 个字符 |
| 递归下降解析，每层一个 `std::string` | 约 80 B / 层，`-O0` 约 110 B | 约 3000 层 | 约 1.26 万层 |
| `unique_ptr` 串成的链表析构 | 约 12 B / 节点，`-O0` 约 144 B | 约 2 万个节点，`-O0` 约 1700 个 | 约 8.4 万个，`-O0` 约 7100 个 |

`std::regex` 的栈用量取决于标准库：libstdc++ 在 GCC 15 及以前每个字符递归一圈 `_M_dfs`，GCC 16 起改成压进堆上的 `_M_frames`；MSVC（14.44）的 `_Match_pat` 也递归，x64 上 600 层后抛 `regex_error(error_stack)`，这 600 层在默认栈上够不够没量过；libc++ 用堆上的 `vector<__state>`。这些规则写进了[协程运行时](runtime.md#栈溢出)。

### 不做的

| 试过什么 | 结果 | 什么条件下重开 |
| --- | --- | --- |
| Linux / macOS 的 release 构建也给每根栈设保护页（原来的做法） | Linux 默认设置下并发协程卡在约 3.2 万根，容器里改不了上限 | 不重开 |
| 用环境变量在任何构建里打开保护页 | 能在 release 程序里排查，但 Windows 要单独写读环境变量的代码，CI 也要专门打开；debug 构建自动带上已经覆盖开发和测试 | 出现只能在 release 程序里复现的栈溢出时 |
| 只给一部分栈设保护页（folly fibers 的做法） | 溢出时是崩溃还是写坏内存，取决于这是第几根栈 | 不重开 |
| 保护页能设上就设，失败不报错（Photon 的做法） | 照抄 Photon 两种分配器的系统调用实测：每根栈占 3 个映射，从第 21836 根起悄悄没有保护页 | 不重开 |
| `MADV_GUARD_INSTALL`，Linux 6.13 起保护页不占映射 | 实测 10 万根保护页不增加映射；但更老的内核要退回 `mprotect`，行为随内核版本变化。glibc 2.42 的线程栈已经这么做 | 最低支持的 Linux 内核到 6.13 时 |
| 栈底放 canary，切换时检查 | 检查到时相邻的栈已经被写坏，溢出的写入还可以直接越过 canary | 不重开 |
| 共享栈（coost、libaco） | 挂起时栈被拷走，指向栈的指针失效。culib 的 park 凭据、`io_request`（Windows 上含 `OVERLAPPED`）都在栈上；libaco 的实测程序里子协程的写入悄悄丢了 | 不重开 |
| 像 Go 那样按需增长 | 要编译器在每个函数开头插检查，还要找到并改写所有指向栈的指针，C++ 都做不到。GCC 的 `-fsplit-stack` 只有 Linux 有，而且要求所有库都这样编译 | 不重开 |
| 默认栈开到 8 MiB（Photon 的默认值） | 向分配器要时撞上它 1 TiB 的地址上限，实测同时 10 万根还行、30 万根直接失败；栈池没有这个上限，但一根栈独占一张页表，实测每根的页表从 2 KiB 涨到 4.6 KiB | 出现普遍需要更深栈的调用方时 |
| 分配器给普通内存也按需提交（只保留，碰到再在异常处理里提交） | 用户态的读写可以，但 `ReadFile` 往没提交的页里写时直接失败（错误 998），异常处理根本没被调用 | 不重开 |
| Windows 上改用系统 fiber（`CreateFiber` / `SwitchToFiber`），影子栈由系统建 | 换栈、栈池和保护页要整套换成 fiber 的；fiber 的切换和内存代价没量过；现在没有使用方需要 `/CETCOMPAT` | 出现必须用 `/CETCOMPAT` 链接的使用方时 |

## [`scheduler.cpp`](../src/runtime/scheduler.cpp)

协程运行时：工作线程和它们的就绪队列、闲着的工作线程、监控线程、定时器、事件引擎和普通线程上的等待。公共行为见[协程运行时](runtime.md)。

### 结构

`runtime_state` 一个进程只有一个，第一次 `go()` 时由函数内静态变量建出来，之后不析构：持有工作线程、全局队列、闲着的工作线程名单和事件引擎。每根工作线程一个 `vcpu`：一条就绪队列，由一把锁护着（这根线程自己和来拿协程的线程都要拿它），一组定时器（见下），以及只有它自己读写的当前协程。协程里 `go()` 起的、被工作线程叫醒的协程排进那根线程的队列；协程外起的、被普通线程叫醒的排进全局队列。

就绪队列、睡着的和备用的工作线程名单，都是 `detail::list_node` 串起来的侵入式链表（见本页 `sync.cpp` 一节）：协程控制块和 `vcpu` 从 `list_node` 派生，入队不分配；睡着的线程撤销登记时直接把自己摘下来，不用在名单里找。弹出发生在恢复之前，所以协程结束后可以立即释放自己的栈。

### 挂起只有一种

第三期时这里有两条互不相干的挂起路径（等定时器一个容器、等 I/O 由引擎拿着），第五期并成一条 **park**：挂起，直到有人叫醒我或者到点。于是

  - `sleep_for` 是「没人会叫我的 park」；
  - 等 I/O 是「引擎会叫我的 park」，带上时限就是带超时的读写；
  - `mutex::lock` 是「持有者会叫我的 park」，带上时限就是 `try_lock_for`。

凭据（park_token）活在**等待者自己的栈上**，所以调度器这边只存指针，一次挂起零分配。详见本页 `park.h` 一节。

### 工作线程找活

每调度一次协程之前：

1. 本线程这一组有到点的定时器，就叫醒所有线程上到点的（`fire_timers()`，见下）。没有定时器时只读一个原子量。
2. 每 61 次不等待地收一次 I/O 完成、叫醒所有线程上到点的定时器、从全局队列取一根：本地队列一直不空时，引擎没人收，登记在卡住的线程上的定时器没人叫，全局队列没人取（Go 也用 61）。全局队列一次只取一根。2026-10-20 照 Go 的 `globrunqget` 试过一次取一批（按名额均分、至少一根、最多 128 根，第一根马上跑，其余排进本线程的队列给别的线程偷），没有留下。那时叫醒还在锁里做，它反而更慢：普通线程里起 10 万根协程，中位数 4 根工作线程 92 → 112 ms、8 根 97 → 119 ms。原因是一批被一根线程拿走以后，别的线程更常闲下来、再被叫醒，每次叫醒都是锁里的一次系统调用（见下面的「叫醒放在锁外」）。叫醒挪到锁外以后再比，同场轮流八轮，一处快一处慢：8 根工作线程起 10 万根，中位数 51 → 49 ms；1 根工作线程放行 1 万根等在一扇门上的协程，28 → 30 ms；其余持平。全局队列换成自旋锁、放进来的一次排一批以后又比了两次，普通线程放行 1 万根，1 / 4 / 8 根工作线程：同场五轮 4.9 → 5.6、4.9 → 6.6、7.6 → 8.0 ms，同场十一轮 5.9 → 5.9、6.0 → 5.8、8.9 → 8.5 ms，在噪声以内。一批拿到本线程以后，放锁时叫醒的协程排在这一批后面，等锁的协程更容易等过 1 毫秒：4 根工作线程时锁改成直接交接的次数从 0 涨到 1.2 万到 1.5 万（共 1 万根协程、2 万次拿锁）。没有留下。有实际负载卡在取的一方抢全局锁上时再试。
3. 依次看本地队列、全局队列，都没有就从别的工作线程的队首拿一半（至少一根）。从哪根开始看随调度次数轮转，免得都去抢同一根。
4. 还没有就闲下来（`idle()`），闲下来之前先叫醒所有线程上到点的定时器。

### 定时器

每根工作线程一组定时器（`worker_timers`：一把锁、一个按时限排的堆、最早的时限），协程挂起时登记在它所在的那根上。原来整个进程一个堆、一把锁：服务端的读写都带超时时，每次挂起都要进出这把锁两次，撤销时堆往下调整，每一层都去读别的协程栈上的凭据，锁拿得久。1 万个连接、8 根工作线程时 84% 的锁争用在这把锁上，抢不到就进 futex 睡，服务端每次往返花的 CPU 是每个连接一根线程的 1.8 倍。Go 从 1.14 起也是每个 P 一个定时器堆。

每组的堆是一个按需加倍的数组，扩容失败时打印诊断后终止：调用方这时已经把凭据排进了等待队列或者交给了事件引擎，没法退回。

叫醒一律走 `fire_timers()`：每次从时限最早、已经到点的那一组里取一个，所以几个时限一起到期时，不管登记在哪根线程上，都按时限的先后排回就绪队列。上面三处会调它，所以登记它的那根线程卡住时，有线程闲着就马上叫，都在忙的话最迟等别的线程调度 61 次。等在引擎里的那根按所有组里最早的时限醒，监控线程看「有没有到点的定时器」时也看所有组。交接名额时定时器不搬。

同一个回显程序同场轮流跑三轮（WSL2，i7-12700；服务端绑在 8 个核上、`WAVVIX_MAXPROCS=8`，客户端用改过的库、另占 8 个核；GCC 11 `-O2 -DNDEBUG`；每个连接一根协程或一根线程，客户端每次写 64 字节、读回 64 字节，读写都带 30 秒超时）：

| 1 万个连接 | 吞吐 | p99 | 服务端每次往返的 CPU |
| --- | --- | --- | --- |
| 整个进程一个堆 | 17.2–17.3 万次/s | 66–70 ms | 24.0–24.1 µs |
| 每根工作线程一组 | 23.3–23.9 万次/s | 48–59 ms | 14.6–15.0 µs |
| 每个连接一根线程 | 16.8–17.0 万次/s | 75–76 ms | 13.0–13.3 µs |

1000 个连接时依次是 27.4–32.7、32.9–40.2、17.0–21.8 万次/s，每次往返 13.3–16.2、9.5–11.7、10.5–13.1 µs。去掉读写超时，协程版每次往返约 11 µs，所以剩下的差距还在定时器上：等待者醒来后多半在另一根线程上撤销自己的定时器，要和登记它的那根抢同一组的锁，锁争用从每次往返 0.72 次降到约 0.3 次，其中一半还是定时器的。测量程序 `vs_threads.cpp` 不在仓库里。

协程切出来以后：结束的销毁；让出的、在挂起的路上就被叫醒的排回本线程的队列；其余记成 `parked`，由唤醒者放回。

### 闲着的工作线程

闲着的工作线程里只有一根等在事件引擎里，同时等 I/O、最早的时限和别的线程的通知；其余睡在各自的条件变量上。同一时刻只有一根线程在 `io_engine_wait()` 里（`poll_mutex`），所以唤醒不会被别的线程收走，epoll 的边沿事件也不会被几根线程分着拿。一直有活的工作线程隔 61 次不等待地收一次，等在引擎里的那根拿着 `poll_mutex` 时就跳过。

往队列里放了协程的一方放完看一眼（叫醒的协程排进本线程时有例外，见下）：有闲着的、又没有正在找活的，就叫醒一根（先叫睡在条件变量上的，都没有再通知等在引擎里的那根），被叫醒的记成「找活的」（`searching`）。找活的那根找到了活，要是它是最后一根找活的，就再叫醒一根，于是一次放进来很多时，闲着的线程一根接一根醒；找不到就重新闲下来。这是 Go 的 `wakep` 和 spinning M 的简化：同一时刻最多一根「被叫醒、还没找到活」的线程，免得放进来一根协程就把所有闲着的线程都叫起来。

**全局队列有自己的一把自旋锁**（`global_lock`），不和闲着的线程名单共用 `state.mutex`：放协程、取协程都只拿这把锁，`queued` 只在锁里改，取的一方和闲下来的一方不加锁先看它。原来放一根进全局队列要进出一次 `state.mutex`，和闲下来、被叫醒的线程抢同一把锁。

**唤醒不会丢**，靠两边都先写后看。闲下来的一方先在 `state.mutex` 里登记（闲着的数加一、找活的数减一），再看一遍全局队列的 `queued`、把每根线程的队列各拿一次锁看一遍，有活就撤销登记；放协程的一方放完、放了队列的锁，才看闲着的和找活的两个数。要是闲下来的一方看某条队列时协程还没放进去，那次看就排在放之前，它的登记又排在那次看之前，放的一方之后看那两个数时一定看得见登记。

**叫醒的协程排进本线程、队里只有它一根时不叫人。** 叫醒它的协程多半马上挂起或者跑完：放了锁接着去等，发完消息去等回信。本线程接着就跑它，数据还在这个核的缓存里。原来每次都叫，被叫醒的线程要么把它偷走，数据跨核搬一趟，两根线程轮流睡下、互相叫醒；要么扑空再睡下。每次都是一次几微秒的系统调用。这样不会把协程丢下：本线程正在跑协程，跑完手上这根就轮到它；名额交走时队列跟着名额走。手上这根一直不让出时由监控线程兜底：有闲着的线程、某根线程停在同一根协程里一个间隔以上、队里还排着协程，就叫醒一根闲着的来偷，排着的协程最多多等两个间隔（4 毫秒）。新起的协程照旧马上叫人，起协程就是要并行。Go 是照样叫（`ready()` 里的 `wakep()`），被叫醒的 M 偷 `runnext` 之前先等 3 微秒，给原来那根先跑它的机会；这里不叫，省掉那次叫醒。

同场轮流跑五轮，取中位数（WSL2，i7-12700，绑在 8 个核上，GCC 11 `-O2 -DNDEBUG`）：

| | 原来 | 只有一根时不叫 |
| --- | --- | --- |
| 两根协程用锁和条件变量来回交替，4 / 8 根工作线程 | 928 / 1013 ns | 316 / 340 ns |
| 1 万根协程排在一把锁上依次交接，4 / 8 根 | 9.6 / 10.2 ms | 3.5 / 3.4 ms |
| 普通线程 `notify_all` 放行等在一扇门上的 1 万根，4 / 8 根 | 21.0 / 17.9 ms | 11.4 / 10.3 ms |

放行那一项也快了，是因为放行的协程醒来以后要依次拿回那把锁，放锁时叫醒下一根，那一步不再叫人。一根工作线程时这三项都在噪声以内，协程里起协程不变，1000 和 1 万个连接的回显也在噪声以内。

**叫醒放在锁外。** 叫醒是系统调用：睡在条件变量上的要 futex，等在引擎里的要写 eventfd 或投一个完成包，在 WSL2 里一次几微秒。原来在 `state.mutex` 里叫，放协程的、找活的、闲下来的都得等它做完。现在锁里只定下叫谁（`wakeup`），放了锁再叫（`wake_up()`）。被挑中的线程在锁里已经摘下名单、记成找活的、`notified` 也置上了，所以晚一点叫不会叫重：它睡前在锁里看 `notified`，早一步醒来的话看见已经置上就不睡，那一下多出来的叫醒只让它白醒一次。Go 的 `startm` 也是先放 `sched.lock` 再 `notewakeup`。

这一处是查「从全局队列一次取一批为什么反而更慢」时找到的。普通线程里起 10 万根协程，几乎全部时间都花在主线程放协程上：4 根工作线程时主线程在 `push_global` 里一共 139 毫秒，其中大半是等这把锁和自己在锁里叫醒。一次取一批让工作线程闲下来、被叫醒的次数多了两成到七成（三次带计数器的运行），每一次都在锁里做系统调用，所以更慢。叫醒挪到锁外以后，同一个带计数器的构建里，主线程在 `push_global` 里的时间降到 20 毫秒，工作线程闲下来的次数从 8327 降到 1779，自愿切换从 2.35 万降到 0.9 万。

同场轮流跑四轮（WSL2，i7-12700，绑在 8 个核上，GCC 11 `-O2 -DNDEBUG`）：

| | 原来 | 放了锁再叫 |
| --- | --- | --- |
| 普通线程里起 10 万根协程，4 / 8 根工作线程 | 92–108 / 91–114 ms | 41–43 / 51–55 ms |
| 普通线程 `notify_all` 放行等在一扇门上的 1 万根，4 / 8 根 | 120–127 / 100–107 ms | 73–76 / 76–79 ms |
| 两根协程用锁和条件变量来回交替，4 / 8 根 | 2.6–4.0 / 1.65–1.81 µs | 0.91–0.95 / 0.95–1.02 µs |

一根工作线程时这三项都不变；1000 和 1 万个连接的回显在噪声以内。

**唤醒分两步，一次叫醒一串时攒成一批。** 同步原语在自己的锁里只摘下等待者、和到点的一方做那次比较交换（`scheduler_claim()`），抢到的协程串进一批（`wake_batch`）；放了锁再一次送到（`scheduler_deliver()`）：排进就绪队列只拿一次锁，只叫一根闲着的线程，它找到活以后再叫下一根；普通线程等待者逐个叫醒，已经到点放弃的跳过。收到的 I/O 完成也这样送。所以同步原语的自旋锁里只有内存操作，不会在里面拿调度器的锁、做叫醒的系统调用。抢到以后、送到之前，记进批里的等待者不会返回，凭据一直在；还在挂起路上的协程不进批，抢到的那一刻它就可能接着跑，所以抢之后不再碰它的凭据（`hand_over_locked` 先读出 `since`、先写好 `handed`）。`notify_all`、`wait_group` 等到最后一根结束、channel 关闭时，原来每叫醒一根都要拿一次锁、看一次要不要叫人。普通线程 `notify_all` 放行等在一扇门上的 1 万根协程，同场轮流五轮的中位数（WSL2，i7-12700，绑在 8 个核上，GCC 11 `-O2 -DNDEBUG`）：

| | 原来 | 攒成一批 | Go 1.24.5，main goroutine 里 `Broadcast` |
| --- | --- | --- | --- |
| `notify_all` 本身，1 / 4 / 8 根工作线程 | 2.6 / 5.3 / 5.5 ms | 2.1 / 1.2 / 1.0 ms | 0.6 / 1.1–1.4 / 1.0–1.1 ms |
| 放行到全部结束，1 / 4 / 8 根 | 5.8 / 8.0 / 10.9 ms | 4.5 / 4.8 / 8.8 ms | 2.3 / 3.2 / 4.0 ms |

`notify_all` 本身那一行是另外几次单独量的。一根工作线程时它比 Go 慢三倍多，可能是因为 main 在另一个核上，1 万根协程的凭据和控制块都在那根工作线程的缓存里，而 Go 的 main 是 goroutine，和它们在同一个 P 上；没有单独验证。其余各项持平。

等在引擎里的那根离开时（有活了，或者被叫醒），还有睡着的就叫醒一根：它找不到活就会来接着等在引擎里，不然 I/O 和定时器要等到有谁再闲下来才有人管。

### 监控线程

同一时刻能跑协程的线程数由「名额」管着：`slots` 根工作线程的 `has_slot` 为真，其余是备用线程。闲着、找活的都只在有名额的线程之间发生，备用线程睡在 `spares` 名单上，`wake_one_locked()` 不碰它们。

监控线程在有名额的线程不全闲着时，每 2 毫秒（`monitor_interval`）醒一次，读每根有名额的线程的 `ticks`（每调度一次加一）和 `current`，记下第一次看到这个 `ticks` 的时刻（`since`）。`ticks` 一直没变、手上又有协程，过了一个间隔、队里还排着协程、又有闲着的线程，就叫醒一根闲着的来偷（见上面「闲着的工作线程」）。过了 10 毫秒（`stall_limit`）就算卡住；卡住、没有闲着的有名额线程、而队列里还有协程或者有到点的定时器，就把名额交出去（`hand_off_locked()`）：取一根备用线程，没有就新建一根 vcpu 和线程，到 `worker_limit` 为止。交接在 `state.mutex` 里完成，有名额的始终是 `slots` 根。停住的那根不知道自己丢了名额，跑完手上那根协程、回到 `worker_loop()` 才看见，排进备用名单睡下，等下一次交接。`idle()` 进门时也看一眼：名额刚被交走，就不去登记闲着。

不区分阻塞的系统调用和长计算。Go 靠 `entersyscall` 知道一根线程进了系统调用，C++ 里没有这样的钩子；代价是从不让出的长计算也会被当成卡住，线程数可能涨上去（到 256 为止）。跑协程的线程被系统挂起 10 毫秒以上也一样会被交接：机器忙的时候会看到短时间里多一根线程在跑协程。

阈值原来是连着两个 1 毫秒的周期，也就是停住 2 到 3 毫秒就交接。机器忙的时候线程被系统挂起几毫秒很常见，CI 上为此误交接过好几次，测试只能一轮轮重试。Go 给一根 goroutine 的时间片是 10 毫秒（`forcePreemptNS`），sysmon 闲下来以后也是隔 10 毫秒看一次，所以改成 10 毫秒：误交接少得多，代价是真卡住的时候，排着的协程多等约 10 毫秒。按时间算而不是按次数数，醒得晚了或者被提前叫醒都不会算错。

Windows 上 `std::this_thread::sleep_for` 和条件变量的限时等待按系统定时器的节拍醒，默认约 15.6 毫秒：原来的「每 1 毫秒」实际是 15.6 毫秒，交接要 46 毫秒左右。[`sleep_precisely()`](../src/runtime/precise_sleep_win.cpp) 在 Windows 上用高精度的可等待定时器（`CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`，Windows 10 1803 起），不改系统的定时器精度；建不起来就退回 `sleep_for`。监控线程睡的时候不需要被叫醒，所以不用条件变量的限时等待。

没有闲着的有名额线程时，完成的 I/O 也没人收，监控线程每次替它们收一次（`poll_now()`），叫醒的协程排进全局队列。定时器它不替人叫：叫醒的协程会进全局队列，持名额的线程自己叫醒的进本地队列，本地队列先跑，同一批到点的协程就不按时限的先后了（MinGW 上真遇到过：三根睡 10、20、30 毫秒的协程醒来的次序是 BCA）。所以有到点的定时器只算「有活」，交接以后由拿到名额的线程叫。全都闲着、多出来的空闲栈也还完了（见协程栈一节）时，它睡在条件变量上，第一根忙起来的线程在 `leave_idle_locked()` 里叫醒它，所以空闲的进程不会每 2 毫秒被叫醒一次。

### 不叫停

运行时没有停的那一步：工作线程和监控线程都 `detach`，`runtime_state`、每根线程的 `vcpu` 和事件引擎都不析构。`main` 返回时进程直接退出，还挂着的协程不再运行，它们的栈和 IOCP 里的 OVERLAPPED 随进程一起消失，内核在关句柄时撤掉未完成的操作。运行中这条不变量照旧成立：挂起协程的栈在完成包取回来之前不会被释放，因为协程要醒来以后才能结束。

协程可能在静态析构期间还在跑，所以它们碰得到的库内状态也不析构：默认 logger、日志的登记表和 flag 的登记表都是函数内静态的指针，指向永不释放的对象。

库不检测死锁：唤醒可以来自别的工作线程、`main` 和使用方自己的线程，「再没有协程能被唤醒」在这里判断不出来。原来单线程的 `run()` 能报死锁，是因为它知道没有别的线程。

### 协程的生命周期

`go()` 分配一块：控制块和可调用对象在一起，经全局的 `operator new`（覆盖了 `new` 的程序里也归同一个分配器）。没有任务状态：协程结束时工作线程销毁控制块，栈还给分配器，就这些。

`wait_group` 自己数组里还有几根协程，再带一条等待者队列。`wait_group::go()` 把函数包一层：函数返回后，先把函数连同它保存的参数析构掉，再给组减一；减到零就把等待者整条摘下、放锁、逐个叫醒——放锁以后才叫醒，因为被叫醒的一方可能马上返回并析构这个组。所以 `wait()` 返回时，组里协程捕获的对象都已经析构。

### 试过的全局队列和栈

2026-10-13 在原型上量（WSL2，20 核里绑 5 核，GCC 11.4 `-O2`，release 库）。每种做法按轮换的顺序各跑 3 遍，表里取中位数。场景：

- spawn_*：4 根工作线程上各一根协程不停地起子协程，每批 64 根，等完再起，共 80 万根；子协程什么都不做、算 1 µs 或算 10 µs。
- fanout_io / fanout_main：4 根工作线程；一根协程（或 `main`）起 10 万根，每根 `sleep_for(1ms)` 模拟一次 I/O，再全部 join。fanout_cpu 同上，但每根算 50 µs。
- single_io：1 根工作线程，同 fanout_io。
- sporadic：4 根工作线程大多闲着，`main` 每隔 200 µs 起一根，量从起到开始跑隔了多久。
- channel_pool：8 根协程从 channel 里取 10 万个活，每个算 10 µs。
- TCP 回显：服务器和压测客户端各 4 根工作线程，各绑 5 个核；长连接 1000 条，短连接 64 路并发，每次来回 64 字节。

**全局等待队列**：互斥锁加侵入式链表，对照 Photon 的 `LockfreeMPMCRingQueue`（65536 格，满了让起协程的一方等空位）。两边的栈都在第一次运行时才分配。

| 场景 | 互斥锁 + 链表 | 无锁环 |
| --- | --- | --- |
| spawn_empty | 399 ns / 根 | 241 ns / 根 |
| spawn_1us | 615 ns / 根 | 489 ns / 根 |
| spawn_10us | 2738 ns / 根 | 2727 ns / 根 |
| fanout_io / fanout_main | 293 / 264 ms | 293 / 250 ms |
| fanout_cpu | 1341 ms | 1468 ms |
| single_io | 396 ms | 311 ms |
| sporadic，中位 / 99% | 12.7 / 76.1 µs | 13.1 / 78.5 µs |
| channel_pool | 286 ms | 285 ms |
| TCP 长连接 | 72.8–78.2 万次/秒 | 57.5–78.1 万次/秒 |
| TCP 短连接 | 14.3–16.5 万次/秒 | 13.7–16.8 万次/秒 |

TCP 两行是另一组运行的范围。短连接的头几遍两边都只有约 1.5 万次/秒，内核的 TIME_WAIT 攒满 65536 个之后才跳到十几万：瓶颈在内核找本地端口，和队列无关，表里只算攒满以后的几遍。

环只在「起得密、每根活很短」时快，10 µs 以上的活和两种 TCP 负载持平；fanout_cpu 反而慢，因为 10 万根超过了环的容量，`main` 要等空位。环还得处理满：Photon 的 WorkPool 在 mode -1 下，任务往已满的池里提交会死锁。实现 171 行，互斥锁版 38 行。

**栈**：全局队列都是互斥锁加链表。

| --- | --- | --- | --- | --- | --- |
| A 创建时取栈，每根线程一份栈缓存（原来的做法） | 866 ns | 643 ns | 1793 ms | 1860 ms | 519 ms |
| B 第一次运行时取栈，每根线程一份栈缓存 | 440 ns | 559 ns | 294 ms | 255 ms | 355 ms |

创建时取栈的做法（A、C、D）让排着队的协程每根先占一根栈、碰脏一页，起一大批时内存按数量涨：single_io 里一根线程要先把 10 万根全部建好才开始跑，峰值 400 MiB 以上。每根线程一份栈缓存（A、B）有上限，同时活着的协程一多就反复 `mmap` / `munmap`；A 还在起协程的线程上取栈、在跑完它的线程上还栈，两头的缓存对不上。D′ 把复用交给分配器：64 KiB 以上的块不归哪根线程，还给系统之前任何线程都能复用。代价是起得密、每根活不到 1 µs 时比 B、E 慢 25–30%；10 µs 以上的活持平（spawn_10us：B 2735–2814、D′ 2811–2839、E 加定期修剪 2758–2793 ns；fanout_cpu 三者 1353–1381 ms）。

## [`sync.cpp`](../src/runtime/sync.cpp)

相关设计见 [设计文档](superpowers/specs/2026-10-05-sync-and-timeout-design.md)。

协程感知的同步原语：`mutex`、`condition_variable`、`channel`。

等待队列是 `detail::list_node`（`include/culib/detail/list.h`）串起来的侵入式双向循环链表，照 Linux 的 `list_head`：表头是不带数据的节点，空表指向自己，所以入队、出队、超时摘除都不分首尾，也不用另记「在不在队里」——摘下的节点自成空表，再摘一次什么也不做。挂起凭据从 `list_node` 派生，活在等待者自己的栈上（见本页 `park.h` 一节），**所以一次等待零分配**。

等待者和唤醒者可能在不同的线程上，所以每个对象带一把锁，护着等待队列和对象自己的状态（锁的 `held_`、channel 的缓冲区）：channel 用 `std::mutex`，其余用 `detail::spin_lock`（见 [`spin_lock.h`](#spin_lockh) 一节）。这把锁只圈住几次读写，从不跨挂起持有：等待者在锁里排好队、放锁，再挂起；唤醒在锁里只摘下等待者、做一次比较交换（`scheduler_claim()`），放了锁再把它们排回就绪队列（`scheduler_deliver()`）。没人等的锁放开时不建这一批，加上这条快路径以后，两根协程来回交替和原来持平（同场十一轮，中位数 210–212 ns 对 213–214 ns）。`notify_*` 和 `close()` 不挂起，所以 `main` 和后台线程也能调。

### 两种模式

平时 `unlock()` 放开锁（`held_` 置假），再叫醒队首。醒来的那根要和刚来的一起抢，抢不到就回到队首，不从队尾重排。有等待者从第一次排队算起等了 1 毫秒以上还没抢到，就进饥饿模式：`unlock()` 直接把锁交给队首，`held_` 保持为真，只是换了主人；刚来的不抢，排到队尾。接手的那根是最后一个，或者它其实没等满 1 毫秒，就退回平时的做法。Go 的 `sync.Mutex` 从 1.9 起也是这两种模式。

原来只有直接交接这一种：先来先服务，但每次交接时锁都空占着，直到拿到锁的那根协程被调度起来，这期间别人只能排队。WSL2 上（i7-12700，GCC 11.4 `-O2`，4 根工作线程），同一个程序先后链接两种实现，轮流各跑两轮，每次拿到锁在锁里做二十次自增：

| | 4 根协程争用 | 64 根协程争用 |
| --- | --- | --- |
| 只直接交接（原来） | 69–83 万次/s | 60–61 万次/s |
| 两种模式（现在） | 336–348 万次/s | 179–189 万次/s |
| 对照：协程里用 `std::mutex` | 531–556 万次/s | 499–557 万次/s |

代价是公平性：64 根协程时，单次拿锁最长从 0.6–0.7 毫秒变成 2.3–3.2 毫秒。用协程锁写日志的那个对照（见[日志](log.md#线程与协程)）里，4 根协程从 16 万行/s 涨到 72 万行/s。

`std::mutex` 在这里仍然更快：锁里只有几十纳秒的活，它拿不到时先在用户态空转，锁多半在这期间就放开了；`wavvix::mutex` 拿不到就挂起协程，再被叫醒、排队、调度。没有照 Go 加自旋（拿不到锁时先空转 4 轮、每轮 30 次 `pause` 再挂起）：在原型里量过，4 根协程能到 417–451 万次/s，但单次拿锁最长到了 8 毫秒，空转期间占着工作线程。

直接交接有一个必须处理的边角：交给一个刚好超时走掉的等待者就是死锁。那根协程已经被排回就绪队列，不会再回来拿这把锁。所以 `scheduler_wake()` 要能报告「这次没叫醒」（比较交换输给了超时的一方），直接交接、叫醒队首和 `notify_one()` 都靠它跳过超时者、换下一个。

**放行一大批时的直接交接。** 普通线程 `notify_all` 放行 1 万根等在一扇门上的协程，它们醒来都要拿回同一把锁。8 根工作线程时锁很快进了饥饿模式：2 万次拿锁里 8 千多次是直接交接，排队挂起近 2 万次（4 根工作线程时没有交接，挂起约 8 千到 1 万次）；perf 的采样六成落在这把锁内部的自旋锁上，锁里做的是排队和叫醒。试过两样，同场 11 到 15 轮，放行、依次交接、来回交替都在噪声以内：直接交接时把接手的协程排到本线程队列的最前面（Go 的 `semrelease` 交接时把等待者放进 `runnext`），没有留下；锁里只摘下等待者、放了锁再排回就绪队列（Go 的 `semrelease` 也是放了队列的锁再 `ready`），为了让自旋锁里只有内存操作，后来还是这样做了（见[闲着的工作线程](#闲着的工作线程)）。`notify_all` 拆成先摘下、再逐个送到两遍时，1 万个凭据各碰两遍，慢了一倍多；现在是摘下时就把协程串成一批，送到时整串接进队列，只碰一遍。Go 交接时还由 `Unlock` 让出 P、马上跑接手的 goroutine（`goyield`），照做的话 `unlock` 就成了挂起点。实际负载里一大批协程同时抢一把锁、剖析结果又指向这里时再看。

channel 不交棒：放进元素或腾出位置时叫醒一个等待者，它醒来后在锁里重新检查，被别的协程抢先了就再排队。值的次序由缓冲区保证，不靠等待者的次序。

## [`net_socket.cpp`](../src/net/net_socket.cpp)

相关设计见 [统一 socket 设计](superpowers/specs/2026-10-13-unified-socket-design.md)。

统一 `socket` 的公共组合层：所有权与移动、惰性创建、协议与阶段校验、完整传输循环、报文语义。公共行为见[网络用法](net.md)。

原先 `tcp_listener` / `tcp_stream` / `udp_socket` 各写一份句柄生命周期、绑工规则、超时形状和错误处理，三份高度重复。合并后对象里要紧的状态就几样：原生句柄、协议，和一个内部阶段值（closed、bound、connecting、listening、connected 等，connecting 保护还在进行中的 connect；具体枚举是实现细节）。公开操作入口比较阶段，不合法就返回错误——不引入状态机或取消框架，阶段校验是几次整数比较。套接字建出来（`bind`、没绑定过的 `connect`、`accept` 返回的新连接）就登记到运行时的事件引擎上（`scheduler_adopt()`），之后不属于哪根线程，对象里也不记线程。

`read_exactly` 和 `write` 在库内循环，整个循环共享一份单调时钟预算，每轮不重置截止时间。失败时已消费或已发出的前缀不回滚，也不提供进度字段；不隐式关闭套接字，因为对向可能还有别的协程在等同一个连接。`recv_from` 的截断保持旧语义：报文已被消费并返回 `out_of_range`。

主机名 `connect` 先解析、后计时：解析直接调 `getaddrinfo`，它无法按时限中止，所以 DNS 不计入连接超时，候选按系统顺序共用同一份超时。已显式绑定的套接字只尝试地址族一致的候选，每次重试前按当前实际本地端点重新绑定，绑不上就报错——绝不悄悄换本地源地址。每次失败的尝试都关掉那次用的原生句柄；已有连接不受无效参数或不支持操作的影响。`close()` 只还句柄、保留协议，同一对象可再次 `bind` / `connect`。

平台资源操作（建套接字、绑定、accept、connect、端点查询、Windows overlapped 调用与 AcceptEx / ConnectEx 上下文、UDP ICMP 抑制、POSIX 非阻塞与 close-on-exec）集中在 `net_socket_posix.cpp` / `net_socket_win.cpp`，经私有的 `net_socket_detail.h` 相接；公共 `net.h` 不包含平台头文件；内部地址编解码使用平台的 sockaddr。旧的 `net_tcp*` / `net_udp*` 实现随合并删除，不留并行旧路径。合并后的实现已在 CI 的三平台矩阵上通过（例如 `754ad6f` 的运行 39264413596）。

## [`fs_win.cpp`](../src/fs/fs_win.cpp)

### 复制前怎么判断是不是同一个文件

覆盖复制会先清空目标，所以源和目标是同一个文件（同一路径，或者经 junction、硬链接绕回来）时，必须在写盘之前拒绝。身份只认系统给的卷号加 FileIndex：两边的 FileIndex 都不为 0 时（NTFS、SMB2 以上），硬链接的两个名字值相同，直接比较即可。

任何一边的 FileIndex 为 0 就认不出身份。这时报错、拒绝覆盖，不找别的退路：

- FAT、exFAT 和一部分网络重定向器不维护持久的 64 位索引，`GetFileInformationByHandle` 给的是兼容层合成的值（chkdsk 或重新挂载以后不保证不变），或者干脆是 0。「卷号相同、0 等于 0」会把同一个卷上不相干的两个文件当成同一个。
- 不拿最终路径兜底：索引为 0 的重定向器同样可能支持硬链接，同一个文件的两个名字可以各有各的最终路径。「路径不同」证明不了「文件不同」，也没有别的可查询的东西能排除这种别名；问得出 GUID 路径也不构成身份。
- `CopyFileW` 的文档没有承诺会拒绝同一个文件（它甚至直接覆盖符号链接指向的目标），没有可以依赖的行为。身份不明时，唯一安全的做法是拒绝。

## [`term_win.cpp`](../src/cli/term_win.cpp)

相关设计见 [设计文档](superpowers/specs/2026-10-01-test-term-table-design.md)。

term 的 Windows 侧：判断是不是控制台、读 NO_COLOR，以及**开 VT 模式**。

NO_COLOR 通过 GetEnvironmentVariableW 查询进程实时环境，避免 CRT 环境副本看不到 os::setenv 后的修改，也避开 MSVC 对 std::getenv 的弃用警告。判断只需要所需缓冲区长度，不读取字符串、不分配内存；缺失和空值都允许上色。Windows 不依赖 TERM 约定。

**VT 开不起来就不上色**，不退回旧版控制台 API。原设计
（2026-10-01-test-term-table-design.md 5.5）写了那条退路：刷新流、记下当前属性、
SetConsoleTextAttribute、写内容、再恢复。这里**故意不做**，两个理由：

  1. 那段本机一行都测不了（wine 的控制台不是真控制台），而它要在用户的控制台上
     改全局状态——恢复那一步写错就把人家的终端颜色弄乱，是那种「用完之后才发现」
     的坏。kqueue 那边用过同一把尺子：**编译不了的平台上，每多一点状态都是在加
     未验证的面积。**
  2. 降级是优雅的：老系统上只是没颜色，功能一点不少。VT 从 Windows 10（2015）
     就有了，而 README 的下限是 VS2015。

**什么条件下补上**：原来写的是「有人在 Windows 10 以前的控制台上要颜色」。最低版本
定成 Windows 10 之后（路线图第 6 节）这个条件不会再成立；Win10 上开不起来 VT 只剩
1507 这一版和勾了「使用旧版控制台」两种情况，降级成纯文字就够了。

## [`log.cpp`](../src/cli/log.cpp)

相关设计见 [日志](log.md)。

logger、sink、登记表和轮转。结构上要紧的有三件事：

  1. 消息在调用方栈上写好，析构时在锁外面拼成整行（`detail::record`），所有 sink 共用这一行。
     每个 sink 在自己的锁里一次系统调用写一整行，所以多个线程同时写不会把半行和半行交错在一起。
  2. 锁的次序是 logger、sink、控制台，都是 std::mutex，不是 wavvix::mutex。锁里是阻塞的系统调用、
     不挂起，所以 catch 块里、拿着 std::mutex 时都能写日志。等慢盘时卡住的工作线程由监控线程交接名额。
  3. 默认 logger、登记表和控制台的锁都是函数内静态的指针，指向永不释放的对象：main 返回时可能还有
     协程在写日志。

## [`term.cpp`](../src/cli/term.cpp)

term 里和平台无关的那部分：颜色模式、「该不该上色」的判断、ANSI 颜色码。

**库里只有这个文件和测试框架（`src/testing/test.cpp`）引入 <iostream>。** 判断「这个流是不是 std::cout」
要比较地址，而公共头文件不能引入 <iostream>（开发约定：公共头文件不引入 <iostream>）。
代价是 GCC 13 以前的 libstdc++ 会因此多一个 main 之前的静态对象——但用到
std::cout 的程序本来就有它。日志的控制台 sink 不经过 iostream，整行拼好用一次 `fwrite` 写给 stderr。

**是不是终端、环境变量只看一次。** 第一次问某根标准流该不该上色时查一次 `isatty`（Windows 上是

## [`os_win.cpp`](../src/platform/os_win.cpp)

os 的 Windows 实现。

和 POSIX 的实质区别只有一处：优雅退出走 SetConsoleCtrlHandler，而**它的回调在一根
由系统创建的独立线程里跑**，不是信号上下文。所以那里的限制不是「只能调
async-signal-safe 的函数」，而是「别在那根线程上做耗时的事」——Windows 给的时间很短
（关机时约 5 秒，之后强杀进程）。接口形状不变：只翻一个标志。
