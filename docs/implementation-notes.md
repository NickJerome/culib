# 实现说明

这里记录实现文件原先写在文件头的结构、设计理由与平台取舍。数据结构旁边仍保留维护局部不变量所需的注释；完整历史与验证记录见各节的设计文档。

## 构建依赖

系统链接依赖统一由 `culib` 目标公开传递，测试和使用方通过 `add_deps("culib")` 继承。
Windows 的网络实现需要 `ws2_32`；当前 macOS 实现使用 POSIX 与 kqueue，已移除文件监听器
留下的 `CoreServices` / `CoreFoundation` 链接项。CI 在 macOS 源码依赖示例运行后输出
`otool -L`，便于核对使用方实际加载的动态库。

## [`defer.h`](../include/culib/defer.h)

守卫宏优先用 `__COUNTER__` 生成变量名，支持同一行展开多个 `defer`，也避免 MSVC
开启 `/ZI` 时 `__LINE__` 无法直接拼接的问题。缺少计数器的编译器退回行号，此时同一
作用域的一行只能展开一次。C++11 不保证复制消除，移动时转移 `active_`，保证只有
接收者析构时执行回调；正确性不依赖编译器是否省略移动。

## [`io_engine.h`](../src/runtime/io_engine.h)

相关设计见 [设计文档](superpowers/specs/2026-10-05-event-engine-design.md)。

事件引擎的内部接口。不是公共头文件，使用方不该包含。

抽象取**完成**形状：「帮我读，读完叫我」，不是「等到可读，你自己去读」。那个决定
和它的理由见 superpowers/specs/2026-10-04-scheduler-design.md 第 2 节，账单
（就绪形状在 Windows 上要付什么）见 2026-10-05-event-engine-design.md 第 2 节。

### 分工

**引擎不碰调度，调度器不认识后端。** 接触面只有 io_request 和它里面那个挂起凭据：

  - 引擎负责「这次操作完成了，结果是这些」，把请求追加到完成批次；
  - 调度器从请求取出凭据，把对应的协程排回运行队列。

凭据（park_token）对引擎是**不透明的**：它存着、交回来，一个字段都不读。
请求离开等待链后，完成批次复用它的 `next` 指针组成 FIFO，不分配堆内存。
`io_engine_wait()` 因此不会因同时完成的请求过多而在 `noexcept` 中触发容器扩容。

所以引擎里**一行都不能碰 wavvix::sleep_for**——协程版的 sleep 自己就是靠引擎的
wait() 实现的，在 wait() 里调它就是自己等自己。（这个坑是 Photon 的 master engine
头文件注释里明写着的，照抄过来。）

### 为什么是自由函数加不透明指针

三个后端的状态没有三方共有的部分（epoll 和 kqueue 共用 fd 下标表，IOCP 要句柄关联），
所以 io_engine 只在这里前置声明；调度器只拿指针。

### 跨线程通知

每根工作线程启动时都给自己的事件引擎打开内部的 `io_engine_enable_notify()`。别的线程用 `io_engine_notify()` 打断它的 `io_engine_wait()`：派来协程、跨线程唤醒、全局等待队列来了活、runtime 叫停，都走这一条。通知只打断等待，不增加 I/O 完成数，也不进入协程的 `park_token` 队列。

Linux 的 epoll 用非阻塞 `eventfd`；macOS 用 `EVFILT_USER` 和 `NOTE_TRIGGER`；Windows 直接向 IOCP 投递空完成项。通知失败时运行时打印诊断后终止：东西已经放进对方的收件口，叫不醒那根线程就没有别的恢复办法。改成 runtime 以后，三个后端的通知由 [`60417e4` 的三平台 CI](https://github.com/NickJerome/culib/actions/runs/38411545278) 验证。

## [`io_engine_posix.h`](../src/runtime/io_engine_posix.h)

相关设计见 [设计文档](superpowers/specs/2026-10-05-event-engine-design.md)。

两个 POSIX 后端（epoll 和 kqueue）真正共享的那部分。不是公共头文件。

**抽出来的理由是开发机没有 macOS。** 当时连 `<sys/event.h>` 都不可用，
所以让 kqueue 尽可能复用已在 Linux 上测试的完成逻辑，独有部分只负责登记兴趣。
随后 kqueue 在 macOS CI 上编译并通过测试；见[事件引擎的实现验证](superpowers/specs/2026-10-05-event-engine-design.md)。

两个后端在接管 fd 时用边沿触发登记读写两个方向，之后不再改兴趣集，所以除了建引擎、
接管和等待这三处系统调用，其余都在这里共用：`io_enqueue()` 先试一次、做不了就排队，
`io_dequeue()` 撤掉超时的请求，`io_dispatch()` 处理一个 fd 上的读写事件。

两个后端共用按 fd 索引的等待表。扩容使用不抛异常的分配；若分配失败，`io_engine_arm()`
在请求入队前返回 `ENOMEM`，原有等待项保持有效。完成批次复用请求节点的链指针，
不需要扩容容器。

套接字也由引擎建：`io_open_socket()` 和 `io_accept_socket()` 在两个后端里各实现一份，网络层只管调用。Linux 用 `SOCK_NONBLOCK | SOCK_CLOEXEC` 和 `accept4`，一次系统调用就建好，也没有「建好了、还没设 CLOEXEC」的窗口让另一根线程的 fork + exec 把 fd 带进子进程。macOS 没有这两个标志和 `accept4`，建好以后补 4 次 `fcntl`，再设 `SO_NOSIGPIPE`。以前为了 GCC 4.8 那个 CI 用的 CentOS 5（glibc 2.5），Linux 上也是补 `fcntl`：一根协程连、一根协程接各 1000 次，`strace -c` 数到的系统调用从 16625 次降到 8622 次，其中 `fcntl` 从 8004 次降到 0（2026-10-13，WSL2，GCC 11.4 release）。

`epoll_wait()` 与 `kevent()` 被信号打断后，会按单调时钟扣除已经等待的时间，再传入剩余超时；否则连续信号会反复重启完整时限，使一次限时 I/O 或睡眠远超调用方指定的时长。无限等待仍直接重试。

## [`io_engine_linux.cpp`](../src/runtime/io_engine_linux.cpp)

相关设计见 [设计文档](superpowers/specs/2026-10-05-event-engine-design.md)。

Linux 的 epoll 后端。此前曾实现 io_uring；它只服务于套接字公共接口，普通文件 I/O 没有接入公共 API，额外的环管理、运行期探测和每请求字段没有实际调用方，因此移除。x86_64 / GCC 11.4 下 `sizeof(io_request)` 从 160 字节降到 88 字节。历史设计仍在 [io_uring 设计](superpowers/specs/2026-10-08-io-uring-design.md)。2026-10-15 起文件 I/O 以一个作用面窄得多的私有环重新接入（只覆盖协程文件读写，见本页 `io_uring_linux.cpp` 一节）；上面那段历史结论针对的是当时的套接字后端，不适用于它。

「完成」形状在一个「就绪」后端上要多做的事，就是**醒来之后当场做一次系统调用**——
那段在 io_engine_posix.h 的 io_complete() 里，和 kqueue 后端共用同一份。本文件只管
epoll 独有的那件事：怎么登记。

**接管时用 `EPOLLIN | EPOLLOUT | EPOLLET` 登记一次，之后不再改。** 早先取水平触发、
每次等待前 `epoll_ctl` 登记、完成后撤销，理由是边沿触发要求「一直读到 EAGAIN」，
像是「一个 fd 一个常驻读循环」的用法（设计文档 6.1）。但两条已有的规则正好补上了这个要求：

- **每次读写先直接试一次。** 已经就绪的数据不靠通知也拿得到，所以某次事件来时没人在等、
  事件被丢掉，也不会让后来的请求漏掉数据。
- **事件来了把这个方向排着的请求一直做到 EAGAIN 或者队列空。** 同方向有人排队时新请求不试、
  直接排到后面，所以排着的请求一定在等一次还没来的事件。

`connect` 之前就登记，新建套接字在登记那一刻是可写的；但 `epoll_wait` 取事件时会重新检查
当前状态，连接还在进行中，这个过期的可写不会被报出来，不会把没连上的 `connect` 当成成功。

同一根工作线程上两根协程经 TCP 回环来回传 1 字节（WSL2，GCC 11.4 `-O2`，绑在同一个 CPU 上，
新旧交替各跑 3 遍）：每个来回从 5.87–5.95 µs 降到 4.71–4.80 µs；系统调用从 12 次降到 8 次，
少掉的正是每次等待时登记、撤销兴趣的 4 次 `epoll_ctl`。代码也少了一套「已登记掩码」的状态。

fd 关闭时内核自动把它从 epoll 里摘掉；号码被复用后，新句柄第一次 I/O 前会再接管一次。

## [`io_uring_uapi.h`](../src/runtime/io_uring_uapi.h)

Linux 文件环用的固定 UAPI 布局与常量。不是公共头文件，使用方不该包含；`#error` 把目标限定在 Linux x86_64 / arm64。

**单份固定布局，不因系统头是否存在换实现。** 旧用户态的内核头（GCC 4.8 那个 Debian 7 容器是 3.2 时代的）没有 io_uring 的声明，新头又随内核版本增长；io_uring 的 mmap 偏移、SQE / CQE 布局和 425 / 426 两个系统调用号在 x86_64 / arm64 上是稳定的 ABI，所以库自带一份最小布局（`io_uring_params`、SQ / CQ offsets、SQE、CQE），布局断言全在编译期。与现代真实内核头的对照编译在 `tests/process/io_uring_uapi.cpp`：逐字段 `offsetof`、`sizeof` 与常量（系统调用号、mmap 偏移、READ / WRITE opcode、NODROP 与 RW_CUR_POS 特性位）对着 `<linux/io_uring.h>` 断言，只在装有现代内核头的环境由 xmake 目标 `file_uring_uapi_check` 显式构建（CI 的 Linux 任务各跑一次）。旧 GCC 容器不编这个对照：它没有现代头，也不需要——它编译生产代码时只见到私有头。这也是当年移除套接字后端时缺的一块：那时布局跟着 `<liburing.h>` 或系统头走，旧环境的头装不出新常量。

生产代码经 libc 的 `syscall()` 取 425 / 426，不引第三方库，不注册文件描述符、不用 SQPOLL。

## [`io_uring_linux.cpp`](../src/runtime/io_uring_linux.cpp) 与 [`fs/file_linux.cpp`](../src/fs/file_linux.cpp)

Linux 协程文件读写的原生路径。接口与语义的权威描述见 [io_uring 文件接入设计](superpowers/specs/2026-10-15-io-uring-files-design.md)；这里记结构与平台取舍。

### 只在初始化选择一次

`io_engine_prepare_file()` / `scheduler_prepare_file()` 返回三态：1 是 native，0 是阻塞池，负数是初始化的 errno；2 只是引擎内部「还没初始化」的哨兵。选择发生在每根工作线程首次非零长度的协程文件读写前：建环、按 `io_uring_params` 的特性位和一次无副作用的 opcode 探测（无效 fd 的 READ / WRITE，不引用用户缓冲区；支持的 opcode 应回 EBADF，回 EINVAL 时归一成 EOPNOTSUPP）确认能力，结果缓存到引擎销毁。`fs::file::read` / `write` 在提交任何真实请求前只读一次缓存。

错误分两类，**不算同一件事**：

- `ENOSYS`、`EPERM`、`EACCES`、`EOPNOTSUPP`：内核不支持或被 seccomp / 权限拦下，是**能力**问题——清掉环，缓存 0，这次和之后的读写都走 `call_blocking`。旧内核与受限容器因此照常可用，全库的 Linux 内核下限不变。
- `ENOMEM`、`EMFILE` 等其余错误：资源或实现问题——清掉环，缓存负 errno，由这一次读写经 `fs` 的 `result` 报出去，不静默降级成阻塞池。

初始化成功后**运行期绝不切换后端**：真实 I/O 错误、提交失败都直接从 `result` 报出来，失败不重发到另一个后端；协程外的调用与 Windows / macOS 一直走 `call_blocking`。

### 环的结构

每根工作线程一个固定 256 项的环：原始 `syscall` + `mmap`，SQ / CQ 两个独立映射按各自的 offsets 取头（SQ 间接数组初始化成恒等映射），SQE 数组第三个映射。acquire / release 配对读写头尾。一个请求一个 SQE、一次 `enter`，没有文件合批。未收完成的请求数不超过 min(SQ, CQ) 容量，超额沿 `request.next` 排 FIFO，没有每请求分配；收完成时释放名额、推进 FIFO，失败项也交回完成队列，不卡后继。

`enter` 失败先看 `sq_head`：已前进说明内核已消费 SQE，请求仍在途，等 CQE，不重提；未前进才回滚本次 `sq_tail` 并报告错误（EINTR 未消费可重试）。cancel 只能摘下还没提交的排队项；在途的必须等自然完成。

### 与套接字同轮公平

环建好时以 `EPOLLIN` 加入该线程既有的 epoll 集合，套接字路径一行不改。`epoll_wait` 报出的环 fd 事件不在事件循环里逐个处理——唤醒后收尾那一轮统一收 CQ，运行期不因它终止进程；等待前后各收一轮 CQ，已有完成时仍做零超时的 `epoll_wait`，热文件请求不会饿死套接字，也不会错过远程唤醒。引擎的 pending 计数是套接字与文件之和。

### 不做的

不恢复套接字 io_uring 后端，不加公开后端选择、环境变量、liburing、SQPOLL、注册缓冲区、fixed files、调用方合批、每操作探测或失败后重提交；日志代码与日志草案不动，也没有任何「日志路径因此加速」的说法。性能要有正式路径对原 baseline 的对照测量后才谈，原型的数字不作数。

## [`io_engine_macos.cpp`](../src/runtime/io_engine_macos.cpp)

相关设计见 [设计文档](superpowers/specs/2026-10-05-event-engine-design.md)。

事件引擎的 kqueue 后端。

「完成」形状多付的那次系统调用在 io_engine_posix.h 的 io_complete() 里，和 epoll
后端共用同一份——**这是为了缩小 kqueue 独有的实现面**。开发机没有 macOS，
但后续已由 macOS CI 验证编译和行为；见本页前面的 `io_engine_posix.h` 说明。

和 epoll 一样在接管时登记一次：一次 `kevent()` 提交 EVFILT_READ 和 EVFILT_WRITE 两条
过滤器，都带 `EV_CLEAR`。`EV_CLEAR` 让过滤器在事件取走后清掉状态，再有新数据或新空间
才再报，效果相当于 epoll 的边沿触发，上面 epoll 那节的两条规则在这里同样成立。
`nevents` 传 0 时只提交不收事件，登记失败通过返回值和 `errno` 报告。

等待时不提交任何变更，所以返回的事件里不会出现 `EV_ERROR`，原来那条「整个方向报废、
把排着的请求全部收掉」的分支随之删掉。未连接的套接字不报可写，`connect` 不会被提前当成完成。

早先每次等待前登记、完成后撤销，还讨论过把变更攒到下一次 `kevent()` 一起提交；
接管时登记一次之后，等待路径上已经没有变更要提交，这个问题不再存在。

## [`io_engine_win.cpp`](../src/runtime/io_engine_win.cpp)

相关设计见 [设计文档](superpowers/specs/2026-10-05-event-engine-design.md)。

事件引擎的 IOCP 后端。

**这一边不用模拟任何东西。** IOCP 原生就是「完成」形状：发出一个 overlapped 操作，
完成包回来时结果已经在里面——epoll / kqueue 那边要在醒来之后补一次 read / write，
这里一次都不用。参照实现为了把 IOCP 塞进「就绪」形状付了什么（`\Device\Afd`、
硬编码的 IOCTL_AFD_POLL、一个自管道、一套重提交状态机，外加一整套平行的完成式
API），见 superpowers/specs/2026-10-05-event-engine-design.md 第 2 节。
那张账单是选定这个形状的全部理由。

写的时候本机只有 MinGW 交叉编译 + wine，真 MSVC 是推上 CI 才第一次编到、跑到的
（`3a766aa` 那次全绿，`3e8ed8d` 记录）。

取消操作后始终等对应完成包。`CancelIoEx` 报 `ERROR_NOT_FOUND` 时，操作可能已完成，
但完成包仍在 IOCP 队列；此时释放请求栈帧会让包里的 `OVERLAPPED` 地址悬空。
Windows 测试先确认读操作完成，再取消并取包，覆盖这个时序。

句柄关联由创建句柄的调用方完成，引擎不缓存“已关联的句柄值”，因为系统会复用这个数值。完成项通过 OVERLAPPED 地址找到请求，完成键无需另存索引。后端未启用 FILE_SKIP_COMPLETION_PORT_ON_SUCCESS：同步成功同样等待完成包，保证内核持有 OVERLAPPED 期间请求一直存活；不为省去一次让出再增加一套同步完成分支。读方向的 ERROR_HANDLE_EOF / ERROR_BROKEN_PIPE 统一返回 0 字节，写方向保留错误，与 POSIX 语义一致。

## [`park.h`](../src/runtime/park.h)

相关设计见 [设计文档](superpowers/specs/2026-10-05-sync-and-timeout-design.md)。

一次挂起的凭据。不是公共头文件。

调度器、事件引擎、同步原语三方共用它，所以它放在比三者都低的一层。

### 为什么要有这个东西

第三期之前，调度器有两条互不相干的挂起路径：等定时器（`sleeping` 容器）和等 I/O
（引擎拿着）。第五期要的是「等 X，但最多等这么久」——**超时和同步原语需要的是同一
件事**，而那件事两条路径都给不了：定时器那条没法被提前叫醒，I/O 那条没有时限。

所以两条并成一条：**挂起，直到有人叫醒我或者到点**。

  - `sleep_for` 是「没人会叫我的 park」，所以它必然超时返回；
  - 等 I/O 是「引擎会叫我的 park」，加上时限就是带超时的读写；
  - `mutex::lock` 是「持有者会叫我的 park」，加上时限就是 `try_lock_for`。

一个机制，三种用法，而调度器里只剩一个挂起容器。

### 它活在哪

**挂起协程自己的栈上**，和 io_request 一样，所以不需要任何分配。协程第一次运行后就绑在一根工作线程上，挂起期间栈不会动，所以把它的地址交给别人是安全的——这正是 `mutex` 的等待队列里能串它的原因。

凭据是否还在挂起集合里，由 `wait_set` 的成员标记 `parked` 决定；超时和唤醒都先从集合移除，再排入就绪队列，同一根协程不会被排两次。协程让出后，调度器先将凭据加入集合，才处理后续的唤醒。

### 跨线程唤醒

挂起集合和就绪队列只由所在的工作线程读写。凭据的 `home` 记着等待者在哪根线程上，由登记的一方（同步原语的 `enqueue()`、`join()`、`call_blocking()`）在凭据对别的线程可见之前填好。`scheduler_wake()` 在 `home` 上直接把协程排回就绪队列；在别的线程上只把凭据放进 `home` 的收件口、通知那根线程的事件引擎，`home` 在下一轮开头取出凭据，走同一条 `rouse()`。

带时限的等待还要处理唤醒和超时同时发生。凭据的 `state` 从 `waiting` 出发，唤醒者比较交换成 `woken`，超时的等待者比较交换成 `given_up`，先换成的一方说了算：唤醒者输了就换下一个等待者（见本页 `sync.cpp` 一节的交棒），等待者输了就当作被唤醒。等待者输了以后不能马上返回：唤醒者可能还没把凭据放进收件口，而凭据在等待者的栈上。所以 `scheduler_give_up()` 输了以后继续挂起，直到 `home` 取出凭据、把 `delivered` 置位才返回。`delivered` 只由 `home` 线程读写，不需要原子操作。

唤醒者在收件口的锁里发通知：`home` 要先拿这把锁才能取走凭据，所以通知发完之前等待者不会醒，它所在的协程不会结束，runtime 也就不会拆掉那根线程的事件引擎。

`mutex.does_not_lose_the_lock_when_a_waiter_times_out` 在一根线程上把超时和放锁排在同一时刻；`mutex.timed_waiters_on_several_workers_never_lose_the_lock` 让 8 根协程在 4 根线程上以 20 µs 的时限抢一把持有时会让出的锁。临时插桩计数显示，后者连跑 50 次里等待者共输掉 631 次比较交换，其中 549 次要再挂起一次等唤醒送到；50 次全部通过，ThreadSanitizer 下连跑 10 次无报告（2026-10-13，WSL2，GCC 11.4 release）。

## 协程栈

[`stack.cpp`](../src/mem/stack.cpp) 在协程第一次运行时向分配器要栈（`mem::aligned_alloc`，按页对齐、按整页取整），协程结束时还回去，运行时不缓存栈。控制块和可调用对象另在一块堆内存里，不在栈顶。**release 构建不设保护页**，栈溢出不会被拦住：越界的写入落到分配器里紧挨着的内存上，可能是另一根协程的栈，也可能是别的对象。debug 构建把每根栈的最低一页设成不可访问，用来排查；还给分配器之前先恢复成可读写。

### 为什么 release 不设保护页

在 Linux 上，保护页每根栈要多占映射：改了保护的那一页把一段映射拆成两段。默认的 `vm.max_map_count` 是 65530，每根带保护页的栈占 2 个映射，并发协程数卡在约 3.2 万根，再多就分配不到栈，打印诊断后终止。ws / API 服务器常要数十万根。这个上限只能在宿主机上改：容器里 `/proc/sys` 是只读的，`docker run --sysctl vm.max_map_count=...` 直接被拒绝（`not allowed`）。在 6.13 以下的内核上，任何形式的保护页都要占映射。

撞到上限时坏掉的不只是协程：映射数用完后，进程里任何需要新映射的分配都会失败。旧实现（每根栈各自 `mmap`）同时挂起 30 万根协程的实测里，第 32746 根 `spawn` 返回 `resource_exhausted`，接着调度器自己的定时堆扩容失败，整个进程以 `std::bad_alloc` 退出。

栈改由分配器给出以后的实测（2026-10-13，WSL2，GCC 11.4，1 根工作线程，每根协程挂在 `sleep_for` 上）：

| 构建 | 同时挂起 | 映射数 | 每根常驻内存 |
| --- | --- | --- | --- |
| release | 1 万 / 3 万 / 30 万 | 46 → 86 / 165 / 1040 | 4.8 / 4.8 / 4.0 KiB |
| debug | 1 万 / 2 万 | 46 → 20086 / 40126 | 4.8 KiB |

release 的映射只随分配器向系统要的大块增长，30 万根只多约 1000 个；debug 每根 2 个，和上面的估算一致。

Boost.Context 默认也不设保护页：`default_stack` 是用 `std::malloc` 分配的 `fixedsize_stack`，带保护页的 `protected_fixedsize_stack` 要显式选。

### debug 构建保留保护页

不设保护页时，溢出的症状出现在别的协程上，开发者看不出原因。旧实现里实测协程 A 递归 300 层、每层写满 1 KiB，越界写进紧挨在下面的协程 B：不设保护页时 A 正常结束，B 的挂起凭据被写坏，再也醒不过来，程序卡住，没有任何输出；有保护页时 A 在越界的那一刻 SIGSEGV，gdb 的调用栈直接指向第 254 层递归。所以 debug 构建保留保护页：开发和测试时溢出当场崩溃，CI 的 debug 与 sanitizer 任务也一直带着它。代价是 debug 构建在 Linux 默认设置下最多约 3.2 万根并发协程（见上表）。

### 代价有多大

把栈填满固定字节、协程结束时从栈底往上扫，量每根协程最深用到多少栈（WSL2，GCC 11.4，`-O2`）：

| 代码 | 最深用栈 |
| --- | ---: |
| culib 全部测试里的协程（1294 根） | 4.1 KiB |
| `snprintf` 格式化浮点数 / `ostringstream` | 3.4 / 3.9 KiB |
| 抛出并捕获异常 | 3.4 KiB |
| `std::sort` 100 万个 `int` | 1.0 KiB |
| `net::resolve("github.com")`，走 DNS | 11.5 KiB |

普通代码在 240 KiB 的默认栈上有 20 倍余量。会用超的只有递归深度随输入增长的代码，栈开多大只是把门槛往后挪：

| 代码 | 每单位输入用的栈 | 240 KiB 能撑到 |
| --- | ---: | ---: |
| `std::regex_match`，GCC 11.4 的 libstdc++ | 约 0.7 KiB / 字符 | 第 347 个字符时用完（gdb 看到 3835 层调用） |
| 递归下降解析，每层一个 `std::string` | 约 80 B / 层，`-O0` 约 110 B | 约 3000 层 |
| `unique_ptr` 串成的链表析构 | 约 12 B / 节点，`-O0` 约 144 B | 约 2 万个节点，`-O0` 约 1700 个 |

`std::regex` 的栈用量取决于标准库：libstdc++ 在 GCC 15 及以前每个字符递归一圈 `_M_dfs`，GCC 16 起改成压进堆上的 `_M_frames`；MSVC（14.44）的 `_Match_pat` 也递归，x64 上 600 层后抛 `regex_error(error_stack)`，这 600 层在 240 KiB 栈上够不够没量过；libc++ 用堆上的 `vector<__state>`。这些规则写进了[协程运行时](runtime.md#栈溢出)。

### 不做的

| 试过什么 | 结果 | 什么条件下重开 |
| --- | --- | --- |
| release 构建也给每根栈设保护页（原来的做法） | Linux 默认设置下并发协程卡在约 3.2 万根，容器里改不了上限 | 不重开 |
| 用环境变量在任何构建里打开保护页 | 能在 release 程序里排查，但 Windows 要单独写读环境变量的代码，CI 也要专门打开；debug 构建自动带上已经覆盖开发和测试 | 出现只能在 release 程序里复现的栈溢出时 |
| 只给一部分栈设保护页（folly fibers 的做法） | 溢出时是崩溃还是写坏内存，取决于这是第几根栈 | 不重开 |
| 保护页能设上就设，失败不报错（Photon 的做法） | 照抄 Photon 两种分配器的系统调用实测：每根栈占 3 个映射，从第 21836 根起悄悄没有保护页 | 不重开 |
| `MADV_GUARD_INSTALL`，Linux 6.13 起保护页不占映射 | 实测 10 万根保护页不增加映射；但更老的内核要退回 `mprotect`，行为随内核版本变化 | 最低支持的 Linux 内核到 6.13 时 |
| 栈底放 canary，切换时检查 | 检查到时相邻的栈已经被写坏，溢出的写入还可以直接越过 canary | 不重开 |
| 共享栈（coost、libaco） | 挂起时栈被拷走，指向栈的指针失效。culib 的 park 凭据、`io_request`（Windows 上含 `OVERLAPPED`）都在栈上；libaco 的实测程序里子协程的写入悄悄丢了 | 不重开 |
| 像 Go 那样按需增长 | 要编译器在每个函数开头插检查，还要找到并改写所有指向栈的指针，C++ 都做不到。GCC 的 `-fsplit-stack` 只有 Linux 有，而且要求所有库都这样编译 | 不重开 |

## [`scheduler.cpp`](../src/runtime/scheduler.cpp)

协程运行时：工作线程、全局等待队列、收件口、跨线程唤醒和 `call_blocking` 的后台线程。公共行为见[协程运行时](runtime.md)。

### 结构

`runtime_state` 一个进程只有一个（`active_runtime`），持有工作线程、全局等待队列、空闲线程名单和后台线程。每根工作线程一个 `vcpu`，只由那根线程读写：就绪队列、挂起集合（`wait_set`）、事件引擎和当前协程。别的线程只能往它的收件口（`inbox`）里放东西——一把锁护着两条链，唤醒的凭据和派来的协程——再通知它的事件引擎。

`ready` 是一条侵入式 FIFO，链指针在协程的控制块里，入队不分配。每轮开始时记下队列长度，只运行这些协程；运行中新取到、唤醒和让出的协程追加到队尾，留到下一轮。弹出发生在恢复之前，所以协程结束后可以立即释放自己的栈。

### 挂起只有一种

第三期时这里有两条互不相干的挂起路径（等定时器一个容器、等 I/O 由引擎拿着），第五期并成一条 **park**：挂起，直到有人叫醒我或者到点。于是

  - `sleep_for` 是「没人会叫我的 park」；
  - 等 I/O 是「引擎会叫我的 park」，带上时限就是带超时的读写；
  - `mutex::lock` 是「持有者会叫我的 park」，带上时限就是 `try_lock_for`。

凭据（park_token）活在**挂起协程自己的栈上**，所以调度器这边只存指针，一次挂起零分配。详见本页 `park.h` 一节。

### 工作线程的一轮

1. 收件口有东西就整条取走：凭据走 `rouse()`，派来的协程排进就绪队列。
2. 本地没有就绪协程时从全局等待队列取一根；一直有活时每 61 轮也取一根，排着的协程不用等那些一直让出的协程结束。一次只取一根：一次取一批的话，排在批里后面的协程要等前面的跑完，而别的线程可能正闲着。
3. 到点的定时等待按时限先后排回就绪队列。
4. 就绪队列空：runtime 在叫停就退出；否则登记为空闲，睡在事件引擎上，直到最早的时限、I/O 完成或别的线程的通知。
5. 否则运行轮首那些协程。就绪队列一直不空时，如果有 I/O 在等，再不等待地收一次完成。

**空闲登记和全局队列用同一把锁。** `idle_begin()` 在锁里看队列：有活就不睡，没有就把自己挂上空闲名单。`push_waiting()` 在同一把锁里入队，再从名单上摘下一根线程、通知它的引擎。所以「看到队列是空的」和「登记为空闲」之间插不进一次入队，唤醒不会丢。通知也在锁里发：睡着的线程要先拿这把锁把自己从名单上摘掉才能退出，所以它的引擎此刻一定还在。工作线程每轮先不加锁地读一眼原子计数 `queued`，队列空时不碰锁。

### 叫停

`runtime` 析构时先等 `live` 归零（还没结束的协程，含排着还没开始的），再在锁里设停止标志、通知每根线程的引擎，然后 join 工作线程，最后停掉后台线程。工作线程只在就绪队列空、且看到停止标志时退出；`live` 为零意味着它不会再有挂起的协程。退出前它再拿一次那把锁，等叫停的一方把通知发完，才销毁自己的引擎。

这带来一条跨文件的不变量：**runtime 在还有协程挂着时不结束**，而 IOCP 后端的 OVERLAPPED 生命周期正是靠这条兜住的（它住在挂起协程的栈上，必须活到完成包取回来为止）。改叫停条件前先看本页 `io_engine_win.cpp` 一节和事件引擎设计。

库不检测死锁：唤醒可以来自别的工作线程、`main` 和后台线程，「再没有协程能被唤醒」在这里判断不出来。原来单线程的 `run()` 能报死锁，是因为它知道没有别的线程。

### 协程的生命周期

`coroutine` 构造时分配控制块（和可调用对象在同一块）与 `task_state`，提交到全局等待队列或者目标线程的收件口。`task_state` 一开始有两份引用：句柄一份，协程一份。协程结束时，工作线程先销毁控制块（可调用对象已在协程里析构，栈还给分配器），再在 `task_state` 的锁里置完成、唤醒 join 的一方，最后释放协程那份引用、把 `live` 减一。所以 `join()` 返回时，捕获对象的析构已经结束。`detach()` 只释放句柄那份引用。

在协程里 `join()` 挂起当前协程，凭据挂在 `task_state` 上；在协程外用一个栈上的 `std::condition_variable` 阻塞当前线程。

### call_blocking

每次调用的可调用对象、队列节点和挂起凭据都在等待协程的栈上；节点用 `next` 串进后台线程共用的队列，没有逐次的堆分配。后台线程执行完函数后用 `scheduler_wake()` 唤醒等待者，走普通的跨线程唤醒；之后不能再碰节点，它随等待者的栈帧消失。收件口那把锁的释放与获取让后台线程写出的结果在协程恢复后可见。

后台线程第一次用到时才建：入队时空闲的线程比排队的调用少，且总数不到 64 根，就再起一根。runtime 停后台线程时所有协程都已结束，不会再有调用在路上，只需置关闭标志、叫醒并 join。函数抛出的异常由公共头文件里的包装捕获，在等待的协程里重新抛出，后台线程本身看不到异常。

### 试过的全局队列和栈

2026-10-13 在原型上量（WSL2，20 核里绑 5 核，GCC 11.4 `-O2`，release 库）。每种做法按轮换的顺序各跑 3 遍，表里取中位数。场景：

- spawn_*：4 根工作线程上各一根协程不停地起子协程，每批 64 根，等完再起，共 80 万根；子协程什么都不做、算 1 µs 或算 10 µs。
- fanout_io / fanout_main：4 根工作线程；一根协程（或 `main`）起 10 万根，每根 `sleep_for(1ms)` 模拟一次 I/O，再全部 join。fanout_cpu 同上，但每根算 50 µs。
- single_io：1 根工作线程，同 fanout_io。
- sporadic：4 根工作线程大多闲着，`main` 每隔 200 µs 起一根，量从起到开始跑隔了多久。
- channel_pool：8 根协程从 channel 里取 10 万个活，每个算 10 µs。
- TCP 回显：服务器和压测客户端各 4 根工作线程，各绑 5 个核；长连接 1000 条，短连接 64 路并发，每次来回 64 字节。

**全局等待队列**：互斥锁加侵入式链表，对照 Photon 的 `LockfreeMPMCRingQueue`（65536 格，满了让 `coroutine(f)` 等空位）。两边的栈都在第一次运行时才分配。

| 场景 | 互斥锁 + 链表 | 无锁环 |
| --- | --- | --- |
| spawn_empty | 399 ns / 根 | 241 ns / 根 |
| spawn_1us | 615 ns / 根 | 489 ns / 根 |
| spawn_10us | 2738 ns / 根 | 2727 ns / 根 |
| fanout_io / fanout_main | 293 / 264 ms | 293 / 250 ms |
| fanout_cpu | 1341 ms | 1468 ms |
| single_io | 396 ms | 311 ms |
| sporadic，中位 / 99% | 12.7 / 76.1 µs | 13.1 / 78.5 µs |
| channel_pool | 286 ms | 285 ms |
| TCP 长连接 | 72.8–78.2 万次/秒 | 57.5–78.1 万次/秒 |
| TCP 短连接 | 14.3–16.5 万次/秒 | 13.7–16.8 万次/秒 |

TCP 两行是另一组运行的范围。短连接的头几遍两边都只有约 1.5 万次/秒，内核的 TIME_WAIT 攒满 65536 个之后才跳到十几万：瓶颈在内核找本地端口，和队列无关，表里只算攒满以后的几遍。

环只在「起得密、每根活很短」时快，10 µs 以上的活和两种 TCP 负载持平；fanout_cpu 反而慢，因为 10 万根超过了环的容量，`main` 要等空位。环还得处理满：Photon 的 WorkPool 在 mode -1 下，任务往已满的池里提交会死锁。实现 171 行，互斥锁版 38 行。

**栈**：全局队列都是互斥锁加链表。

## [`sync.cpp`](../src/runtime/sync.cpp)

相关设计见 [设计文档](superpowers/specs/2026-10-05-sync-and-timeout-design.md)。

协程感知的同步原语：`mutex`、`condition_variable`、`channel`。

等待队列是串在挂起凭据 `next` / `prev` 上的侵入式 FIFO。**所以一次等待零分配**——凭据活在等待者自己的栈上（见本页 `park.h` 一节）。超时的等待者靠 `prev` 在常数时间内把自己摘掉。

等待者和唤醒者可能在不同的工作线程上，所以每个对象带一把 `std::mutex`，护着等待队列和对象自己的状态（锁的 `held_`、channel 的缓冲区）。这把锁只圈住几次读写，从不跨挂起持有：等待者在锁里排好队、放锁，再挂起；唤醒在锁里发出，跨线程的送达走收件口。`notify_*` 和 `close()` 不挂起，所以 `main` 和后台线程也能调。

### 交棒，不是放开

`unlock()` **不把锁放开让大家抢**，而是直接交给队首那个等待者：`held_` 保持为真，只是换了主人。这样才有「先来先服务」——放开让抢的话，一个刚好在跑的协程可以插队，而队首那个可能永远排不上（barging）。

交棒有一个必须处理的边角：**交给一个刚好超时走掉的等待者就是死锁**。那根协程已经被排回就绪队列，不会再回来拿这把锁。所以 `scheduler_wake()` 要能报告「这次没叫醒」（比较交换输给了超时的一方），交棒和 `notify_one()` 都靠它跳过超时者、换下一个。

channel 不交棒：放进元素或腾出位置时叫醒一个等待者，它醒来后在锁里重新检查，被别的协程抢先了就再排队。值的次序由缓冲区保证，不靠等待者的次序。

## [`net_socket.cpp`](../src/net/net_socket.cpp)

相关设计见 [统一 socket 设计](superpowers/specs/2026-10-13-unified-socket-design.md)。

统一 `socket` 的公共组合层：所有权与移动、惰性创建、协议与阶段校验、完整传输循环、报文语义。公共行为见[网络用法](net.md)。

原先 `tcp_listener` / `tcp_stream` / `udp_socket` 各写一份句柄生命周期、绑工规则、超时形状和错误处理，三份高度重复。合并后对象里要紧的状态就几样：原生句柄、所属工作线程、协议，和一个内部阶段值（closed、bound、connecting、listening、connected 等，connecting 保护还在进行中的 connect；具体枚举是实现细节）。公开操作入口比较阶段，不合法就返回错误——不引入状态机或取消框架，阶段校验是几次整数比较。

`read_exactly` 和 `write` 在库内循环，整个循环共享一份单调时钟预算，每轮不重置截止时间。失败时已消费或已发出的前缀不回滚，也不提供进度字段；不隐式关闭套接字，因为对向可能还有别的协程在等同一个连接。`recv_from` 的截断保持旧语义：报文已被消费并返回 `out_of_range`。

主机名 `connect` 先解析、后计时：协程里经现成的 `call_blocking`，协程外同步；`getaddrinfo` 无法按时限中止、`call_blocking` 也不能取消，所以 DNS 不计入连接超时，候选按系统顺序共用同一份超时。已显式绑定的套接字只尝试地址族一致的候选，每次重试前按当前实际本地端点重新绑定，绑不上就报错——绝不悄悄换本地源地址。每次失败的尝试都关掉那次用的原生句柄；已有连接不受无效参数或不支持操作的影响。`close()` 只还句柄、保留协议，同一对象可再次 `bind` / `connect`。

平台资源操作（建套接字、绑定、accept、connect、端点查询、Windows overlapped 调用与 AcceptEx / ConnectEx 上下文、UDP ICMP 抑制、POSIX 非阻塞与 close-on-exec）集中在 `net_socket_posix.cpp` / `net_socket_win.cpp`，经私有的 `net_socket_detail.h` 相接；公共 `net.h` 不包含平台头文件；内部地址编解码使用平台的 sockaddr。旧的 `net_tcp*` / `net_udp*` 实现随合并删除，不留并行旧路径。这批改动尚未取得 CI 结果，不能沿用 2026-10-08 那套接口的绿色记录。

## [`term_win.cpp`](../src/cli/term_win.cpp)

相关设计见 [设计文档](superpowers/specs/2026-10-01-test-term-table-design.md)。

term 的 Windows 侧：判断是不是控制台、读 NO_COLOR，以及**开 VT 模式**。

NO_COLOR 通过 GetEnvironmentVariableW 查询进程实时环境，避免 CRT 环境副本看不到 os::setenv 后的修改，也避开 MSVC 对 std::getenv 的弃用警告。判断只需要所需缓冲区长度，不读取字符串、不分配内存；缺失和空值都允许上色。Windows 不依赖 TERM 约定。

**VT 开不起来就不上色**，不退回旧版控制台 API。原设计
（2026-10-01-test-term-table-design.md 5.5）写了那条退路：刷新流、记下当前属性、
SetConsoleTextAttribute、写内容、再恢复。这里**故意不做**，两个理由：

  1. 那段本机一行都测不了（wine 的控制台不是真控制台），而它要在用户的控制台上
     改全局状态——恢复那一步写错就把人家的终端颜色弄乱，是那种「用完之后才发现」
     的坏。kqueue 那边用过同一把尺子：**编译不了的平台上，每多一点状态都是在加
     未验证的面积。**
  2. 降级是优雅的：老系统上只是没颜色，功能一点不少。VT 从 Windows 10（2015）
     就有了，而 README 的下限是 VS2015。

**什么条件下补上**：原来写的是「有人在 Windows 10 以前的控制台上要颜色」。最低版本
定成 Windows 10 之后（路线图第 6 节）这个条件不会再成立；Win10 上开不起来 VT 只剩
1507 这一版和勾了「使用旧版控制台」两种情况，降级成纯文字就够了。

## [`log.cpp`](../src/cli/log.cpp)

相关设计见 [设计文档](superpowers/specs/2026-10-05-log-design.md)。

日志的实现：级别、输出目标、轮转。

结构上只有两件事要紧：

  1. **一行日志在调用方栈上拼好，再整段交给 sink。** 所以多个线程同时写不会把半行
     和半行交错在一起——锁只圈住「交出去」那一下，格式化不在锁里面。
  2. **sink 是进程全局的，所以用 std::mutex 不用 wavvix::mutex。** 日志也在协程外写
     （`main`、`call_blocking` 的后台线程、使用方自己的线程），而 `wavvix::mutex` 只能在
     协程里加锁。锁只圈住「交出去」那一下，不会长时间卡住工作线程。

## [`os_win.cpp`](../src/platform/os_win.cpp)

os 的 Windows 实现。

和 POSIX 的实质区别只有一处：优雅退出走 SetConsoleCtrlHandler，而**它的回调在一根
由系统创建的独立线程里跑**，不是信号上下文。所以那里的限制不是「只能调
async-signal-safe 的函数」，而是「别在那根线程上做耗时的事」——Windows 给的时间很短
（关机时约 5 秒，之后强杀进程）。接口形状不变：只翻一个标志。
