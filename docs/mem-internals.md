# 分配器实现

本文写给改分配器的人：结构、快慢路径、并发约定、内存归还、误用检查、测量，以及试过但不做的事。用法见[分配器用法](mem.md)。

代码在 `src/mem/allocator/`：`allocator.cpp` 是全部分配逻辑和公开接口；`native.h` 加 `native_posix.cpp` / `native_win.cpp` 是它用到的平台设施（一把锁、线程退出回调、fork 钩子、时钟、随机种子、致命错误输出）；内存页操作在 `src/mem/pages*`，和协程栈共用。`allocator.cpp` 不包含平台头文件，也不直接调用系统内存接口。

## 结构

| 层次 | 大小 | 说明 |
| --- | --- | --- |
| chunk | 64 MiB，按 64 MiB 对齐 | 任何地址 `& ~(64 MiB - 1)` 就是它所在 chunk 的起点。最多 16384 个（1 TiB），只增不减 |
| chunk 头 | 开头 64 KiB | 空闲位图、已提交位图（各 2 KiB）、描述符表的提交记录 |
| 描述符表 | 接着 128 KiB | 每个 slice 一个页描述符，间隔 128 字节；按 64 KiB 一段、用到才提交 |
| slice | 64 KiB | 每个 chunk 1024 个，前 3 个是头部，从第 4 个开始可分配 |
| 页 | 1 或 8 个 slice | 8 KiB 以内的尺寸档一页一个 slice（64 KiB）；8–64 KiB 的一页 8 个 slice（512 KiB），每页至少 8 块 |
| 大块 | 若干连续 slice | 64 KiB 以上，直接占 slice，起点至少 64 KiB 对齐 |
| 超大块 | 单独保留 | 一个 chunk 装不下的块。开头 64 KiB 放一个 chunk 头记下大小和偏移，块从偏移处开始 |

尺寸档沿用 mimalloc 的分法：64 字节以内每 16 字节一档，之后每翻一倍分四档，块大小都是 16 的倍数，共 49 档，最大一档 64 KiB。

页描述符 64 字节：三条空闲链（`free` 拥有者分配用、`local_free` 拥有者释放用、`thread_free` 其他线程释放用，原子）、拥有者（原子，空表示大块或拥有者已退出）、队列前后指针、块大小（0 表示大块）、`used`、`capacity`、`reserved`（已切出的块，后面的内存从没写过）、`slices`（0 表示这页已还掉）、尺寸档、是否在满页队列、`back`。

中等页占 8 个 slice，落在后 7 个 slice 里的地址查到的是那个 slice 自己的描述符。建页时给后面几个描述符记下离页头隔了几个 slice（`back`），定位时减回去，不用分支：

```cpp
const std::size_t index = (at & (chunk_size - 1)) >> slice_shift;
const std::size_t back = desc_at(c, index)->back;
result.p = desc_at(c, index - back);
result.offset = (at & (slice_size - 1)) + (back << slice_shift);
```

描述符间隔 128 字节而不是 64：相邻两页的描述符分属不同线程时，不共用一对缓存行，原型上实测更快。描述符表按 64 KiB 一段，在用到时提交；64 KiB 同时满足 4 KiB、16 KiB（Apple Silicon）和 64 KiB 的系统页，`mprotect` 的地址总是对齐的。

## 分配和释放

每个线程一个堆：每个尺寸档一个可用页队列和一个满页队列。快路径只看可用队列的队首页：

```cpp
inline void* alloc_bin(int bin) {
    page* const p = t_heap->available[bin].first;
    if (!p || !p->free) {
        return alloc_small_slow(bin);
    }

    return pop(p);
}
```

释放时先检查误用（见下文），然后看页的拥有者是不是自己：是就挂到 `local_free`、减 `used`；不是（大块，或别的线程的页）就用 CAS 挂到 `thread_free`。

慢路径按顺序找：可用队列里的页（先收回 `thread_free`，再把 `local_free` 接到 `free`，还有没切过的块就再切 4 KiB）→ 满页队列，每次最多看 4 页 → 已退出线程留下的页 → 新页。分完的页挪进满页队列，等其他线程释放；本线程释放时如果页在满页队列里，就挪回可用队列。

页空了就还掉，但每个尺寸档如果只剩这一页就留着，免得分配和释放交替时反复换页；每 1024 次慢路径还掉一次各档留着的空页。

`local_free` 和 `free` 分开，是为了让快路径定期掉进慢路径：只要 `free` 用完，慢路径就会顺便收回 `thread_free`。合成一条的话，一个分配和释放一样多的线程永远不进慢路径，别的线程还回来的块就一直收不回。

线程退出时：空页还掉，还有活块的页交给按尺寸分档的共享池（`abandoned`），拥有者清空；其他线程在慢路径上按尺寸接手。堆结构放进空闲链表留给下一个线程。

## 并发

全局只有一把锁（POSIX 的 pthread mutex、Windows 的 SRWLOCK），常量初始化、从不析构，进程收尾阶段一直可用。它保护 chunk 列表、slice 位图、描述符表的提交记录、共享池和空闲堆链表，只在慢路径上取。不取锁的地方：

- `thread_free`：其他线程只用 CAS 往上压，拥有者一次 `exchange` 整串摘走，不存在 ABA。
- 拥有者字段：释放时 relaxed 读，只用来决定走哪条路；接手共享池的页时 release 写。
- 共享池每档的头指针：慢路径先无锁看一眼是不是空的，是空的就不取锁。
- 归还时间 `purge_at`：锁外只读。
- 地址位图：只在建 chunk、分配和释放超大块时改（原子 or/and），释放时 relaxed 读。地址能交给 `free`，说明分配它的那次操作已经先于这次释放发生，位图一定已经看得到。

线程退出：POSIX 用 pthread key 的析构，Windows 用 FLS 回调。退出回调跑过之后，同一线程后面的析构里还可能分配（例如排在后面的 TLS 析构）。这时不能再登记新堆——POSIX 上它不会再被回收，Windows 上 FLS 不会第二次调用回调——所以用一个临时堆：分配完立刻交给共享池。退出标志在 POSIX 上是线程局部变量，在 Windows 上放在原生 TLS 槽里，因为 FLS 回调运行时，MinGW 模拟的 C++ TLS 可能已经清掉了。

登记线程退出回调和 fork 钩子时都可能分配内存（glibc 的 `pthread_atfork` 会分配；key 编号超过 32 时 `pthread_setspecific` 也会），所以都在锁外进行，并且先把新堆装进 `t_heap` 再登记，嵌套的分配直接用它。

fork：之前取锁，之后父进程解锁、子进程重建锁。子进程里其他线程的堆没人用了，它们的页里的块释放时走 `thread_free`，不会再收回，和 glibc 对其他线程缓存的处理一样。

## 内存归还

每个 chunk 两张 slice 位图：

| 空闲 | 已提交 | 含义 |
| --- | --- | --- |
| 1 | 0 | 可分配，读出来是零 |
| 1 | 1 | 可复用的旧内存，也是归还的对象 |
| 0 | 1 | 正在用 |

slice 被释放后不马上还：第一次有 slice 空出来时定一个 1 秒后的时间，到点后在下一次取锁的慢路径（或每 1024 次慢路径的定期检查）把所有空闲且已提交的 slice 一次还掉；`collect()` 马上还。还失败的仍记作已提交，下次再试。超大块释放时立刻整段还掉。

大块 `calloc` 拿到的 slice 如果一片都没提交过，读出来就是零，不再清零。只要有一片是旧内存，整块照常清零。

系统接口的差别全在 `pages` 里：

| 平台 | 保留 | 提交 | 归还 |
| --- | --- | --- | --- |
| Linux，允许 overcommit（默认） | 映射成可读写，`MAP_NORESERVE` | 什么都不做，第一次写才分配物理页 | `MADV_DONTNEED` |
| Linux 严格 overcommit（`vm.overcommit_memory=2`），macOS | 映射成 `PROT_NONE` | `mprotect` 成可读写 | 用 `MAP_FIXED` 重新映射成 `PROT_NONE`：物理页立刻释放，提交额度退回 |
| Windows | `VirtualAlloc(MEM_RESERVE)` | `MEM_COMMIT` | `MEM_DECOMMIT` |

Linux 默认那一行全程不改映射。改映射（`mprotect`、`MAP_FIXED`）要拿进程级的映射写锁，期间其他线程的缺页都得等；多线程反复归还、复用内存的负载上，这一点让原型比 mimalloc 慢了 3 倍（测量见下）。严格 overcommit 下，可读写的映射会立刻全额记账，每个进程白占整个 chunk 的提交额度，所以第一次保留时读一次 `/proc/sys/vm/overcommit_memory`，是 2 就走第二行。glibc（`check_may_shrink_heap`）、jemalloc（`os_overcommits`）、mimalloc（`unix_detect_overcommit`）都读这个文件做同样的判断。

macOS 的 `MADV_DONTNEED` 不会马上减少进程占用的内存（mimalloc 为此改用 `MADV_FREE_REUSABLE`），所以 macOS 走第二行，和现在的协程栈一样用 `MAP_FIXED` 重新映射。

## 大块、超大块和对齐

大块在所有 chunk 里从低地址找第一段足够长的连续空闲 slice，找不到就建新 chunk。要求对齐超过 64 KiB 时，起点下标按对齐的 slice 数对齐；chunk 本身按自身大小对齐，下标对齐就是地址对齐。

超大块（一个 chunk 装不下，约 64 MiB 以上）单独保留一段按 64 MiB 对齐的地址，开头 64 KiB 放一个 chunk 头记下保留的总大小和块的偏移，释放时整段立刻还掉。块必须落在保留区的第一个 chunk 里，`chunk_of` 才找得回头部，所以对齐最多 32 MiB；更大的对齐返回空指针。

小块的 `aligned_alloc` 挑块大小是对齐倍数的那一档：页从 64 KiB 边界开始，档里每一块都对齐，交出去的指针就是块的起点，释放时不需要额外的标记。代价是小块高对齐会浪费一些空间（例如 `aligned_alloc(4096, 10)` 占一个 4 KiB 的块）。

Windows 不能只释放保留区的一部分，按 64 MiB 对齐保留时先多保留一段探出对齐的地址、整段放掉，再在那个地址上重新保留；两步之间可能被别的线程占走，所以最多试 8 次。

## 误用检查

`free` 的检查顺序：

1. 地址所在的 64 MiB 在地址位图里有没有标记。没有就看超大块的位图，还没有就是「不是本分配器给出的指针」。用户态地址不超过 2^48，每 64 MiB 一位，每张图 512 KiB，在静态区里，用到的那几个字才占物理内存。
2. 定位页（上面那段代码），页的 `slices` 为 0 说明这页已经还掉了。大块、超大块的重复释放都落在这一条或上一条。
3. 偏移必须落在块的起点上：大块偏移必须是 0；小块偏移要小于 `capacity × block_size`，并且是块大小的整数倍。落在大块后面 slice 里的地址查到的是一个已还掉的描述符，或者被 `back` 引回前面的某页之后偏移越界，都会报错。
4. 小块重复释放：释放时在块的第二个字写入 `free_key`（第一次建堆时生成的随机值），分配时清零；再次释放时它还是 `free_key`，就是重复释放。块至少 16 字节，第二个字总是在块里。

报错时把原因和地址拼成一行写到 stderr，不分配内存，然后 `abort`；Windows 上先解除本线程的 FLS 回调，免得 `ExitProcess` 在已经写坏的堆上再整理一遍，把退出码从 3 改成 `0xC0000005`。

代价用 callgrind 数指令（`irbench`，一百万次分配加一百万次释放；指令数不受机器忙闲影响），每次分配或释放平均执行的指令：

| 负载 | 原型（同一套结构，无检查） | 本实现去掉检查 | 只留前两项 | 四项全留（本实现） |
| --- | ---: | ---: | ---: | ---: |
| 256 个槽位随机替换，8–520 字节 | 53.1 | 59.5 | 60.5 | 71.5 |
| 两万个 64 字节块整批分配再释放 | 43.7 | 48.4 | 49.4 | 60.4 |
| 主线程分配、另一线程释放 | 51.6 | 55.1 | 56.1 | 67.1 |

第 1 项不花额外代价：超大块的路由本来就要查那张位图（去掉检查后仍比原型多的 6 条，就是这次查询，加上 GCC 把 `alloc` 拆成外壳和主体的 4 条）。第 2 项每次 1 条。第 3、4 两项合计每次 11 条，几乎都在 `free` 里，其中有一条 32 位除法。

放到分配最密集的几项测试上（覆盖库，原型 = 100%，3 轮）：

| 测试 | 只留前两项 | 四项全留 |
| --- | ---: | ---: |
| larsonN-sized | 111% | 131% |
| glibc-thread | 104% | 113% |
| alloc-testN | 109% | 111% |
| glibc-simple | 106% | 113% |
| alloc-test1 | 104% | 109% |
| 几何平均 | 107% | 115% |

「只留前两项」比原型慢的那部分不是检查，是库的结构：`malloc` 跨编译单元调用 `alloc`、errno 的处理，以及上面那 6 条（原型是把整个分配器内联进覆盖库的）。

## 生成的代码

Linux 的 malloc 覆盖库要装进任意进程，打包上有几条约束（合起来的效果见「测量」一节的同场对比）：

- 不编入 `new.cpp`。它要用 `std::get_new_handler` 和 `std::bad_alloc`，共享库就得依赖 libstdc++，加载进 C 程序时 cfrac、glibc-simple、mleak 这类小程序的峰值 RSS 白多 1.1–1.5 MB。C++ 程序的 `operator new` 由 libstdc++ 实现，内部调用的正是覆盖后的 `malloc`。
- `-fvisibility=hidden`，只导出 C 入口。否则 `malloc` 调 `wavvix::mem::alloc` 要经过 PLT，每次多一次间接跳转。
- `-fno-exceptions`，不生成清理代码，不依赖 libgcc_s。
- 不用动态初始化的函数内静态变量（要靠 libstdc++ 的 `__cxa_guard`），不用 `std::bitset::count`（没有 POPCNT 指令时调用 libgcc 的 `__popcountdi2`）。

公开函数里不能有取地址的局部变量：Ubuntu 的 GCC 默认开着栈保护，有这种变量的函数每次调用都要设、查一遍栈金丝雀。`alloc` 曾因大块路径里一个 `bool zeroed` 每次多 12 条指令，现在大块路径单独成函数。

## 测量

在 WSL2（i7-12700，20 个逻辑核）上用 mimalloc-bench 的 21 项测试，GCC 11.4 release。每个分配器在每个位置各跑一次（轮数等于分配器个数，每轮轮换出场顺序），两组测试前都先满载 30 秒耗掉睿频预算：这台机器闲置一分钟后，头十几秒的全核负载会快 25%，固定出场顺序会让排在前面的分配器白占便宜。只比较同一次运行里的倍数，不比较绝对值。

**rptest 的同步补丁。** mimalloc-bench 的 rptest 用一个计数器同步工作线程：每轮结束加一，等它回到 0。主线程等到计数够了再清零，可第一个被放行的线程只要睡 10 ms、跑完一轮就会把计数加回去，没在这段窗口里被调度到的线程就永远等不到 0，整个程序卡死（gdb 抓到过：计数 16，16 个线程做完第二轮、4 个停在第一轮，全在 rptest 自己的轮询里，没有线程在分配器里）。分配器越快窗口越短，原型的快变体 21 次卡了 6 次，mimalloc 也卡过一次 5.3 小时。这里的 rptest 都用只改了同步的补丁版：等「代数」变化而不是等计数回到 0，计时部分不变；补丁后 124 次没有卡死。

**本实现的全套结果**（覆盖库；glibc = 100%，越低越好；21 项；glibc、jemalloc 5.2.1（Ubuntu 22.04 自带的包，默认配置）、mimalloc 3.5.3（关透明大页）、本实现同场各 4 轮）：

| | jemalloc | mimalloc 关大页 | 本实现 |
| --- | ---: | ---: | ---: |
| 用时几何平均 | 102% | 84% | 91% |
| 峰值 RSS 几何平均 | 130% | 117% | 113% |

对 jemalloc：用时 89%，RSS 87%，21 项里 10 项更快、14 项更省。差得最多的几项：malloc-large（本实现 94%，jemalloc 272%）和 xmalloc（63% 对 183%）本实现快；larson（77% 对 64%）和 rptest（99% 对 91%）jemalloc 快。对 mimalloc（关大页）：用时 109%，RSS 97%，17 项更省。各项明细见本节末尾。

jemalloc 的 release 构建默认不查重复释放这类误用（要在编译时加 `--enable-opt-safety-checks`），空出来的内存默认 10 秒后才归还，arena 默认是 CPU 数的 4 倍。

只分配一点内存的小程序（C 程序，`LD_PRELOAD` 覆盖库；20 个线程时每个线程各分配两块并停住）：

| | 常驻 | 20 个线程时常驻 | 虚拟地址 | 共享库大小 |
| --- | ---: | ---: | ---: | ---: |
| glibc | 1.4 MB | 1.6 MB | 2.7 MB | — |
| jemalloc | 3.6 MB | 3.9 MB | 17 MB | 744 KB |
| mimalloc | 2.0 MB | 2.1 MB | 1.0 GB | 274 KB |
| 本实现 | 1.6 MB | 1.8 MB | 68 MB | 27 KB |

本实现虚拟地址里的 64 MiB 是第一个 chunk 的保留，不占物理内存；mimalloc 默认按 1 GiB 保留 arena。jemalloc 5.2.1 在 Linux 上参与编译的源码约 3.7 万行（有效代码 2.7 万），本实现约 1600 行（有效代码 1270）。

**chunk 的大小。** chunk 越大，能在 chunk 里复用的块越大、碎片越少；越小，占的虚拟地址越少。第一次保留要多映射一倍找出对齐的位置，所以进程至少要有两个 chunk 那么多的虚拟地址余量。原型用的是 1 GiB：

| | 1 GiB | 64 MiB（本实现） |
| --- | --- | --- |
| `ulimit -v 256 MiB` / `ulimit -v 1 GiB` 下第一次分配 | 失败 / 失败 | 成功 / 成功 |
| 小程序的虚拟地址 | 1.0 GB | 68 MB |
| 反复分配、每页写一字节、释放 100 MiB 的块，每次 | 1.7 ms，1280 次缺页 | 28.3 ms，25601 次缺页 |
| 同上，300 MiB | 6.0 ms，3840 次缺页 | 87.2 ms，76801 次缺页 |
| malloc-large（5–25 MiB 的块）的峰值 RSS | 523 MB | 581 MB，用时持平 |

64 MiB 以上的块不再复用，只是退回到 glibc 和 jemalloc 的做法：同样反复分配 100 MiB，glibc 每次 31.8 ms、jemalloc 27.6 ms，它们分别从 32 MiB、8 MiB 起就单独映射。需要反复使用这么大的缓冲区时，由使用方留着复用。malloc-large 的峰值多 11%，是因为块不能跨 chunk：64 MiB 的 chunk 被切碎后，新块放不进刚释放的位置，只好用别的 chunk。其他测试（mstress、alloc-test、cfrac）在噪声范围内没有变化。glibc 每个线程 arena 的保留也是 64 MiB。分配、释放快路径的指令条数不变（只有移位和掩码的立即数不同）；多出来的 55 条在找连续空闲 slice 的 `find_run` 里，位图从 256 个字缩到 16 个字，编译器把循环展开了。

**结构的由来。** 先前一轮（6 个分配器各 6 轮）对比了几种结构，都没有误用检查：

| | mimalloc | mimalloc 关大页 | 64 KiB 页 | + 中等档 | + 中等档 + madvise |
| --- | ---: | ---: | ---: | ---: | ---: |
| 用时几何平均 | 85% | 83% | 88% | 88% | 87% |
| 峰值 RSS 几何平均 | 187% | 119% | 108% | 108% | 113% |
| rptest 用时 | 116% | 96% | 131% | 122% | 96% |

最后一列就是本实现的结构，只是当时 chunk 是 1 GiB。默认（开透明大页）的 mimalloc 用时快 2%，内存多用 66%。

**rptest 慢 3 倍的原因。** 补丁版 rptest，4 轮中位数，百万次操作每秒：

| 变体 | 不跨线程 | 默认（跨线程） | 缺页（不跨线程） |
| --- | ---: | ---: | ---: |
| mimalloc 关大页 | 4.69 | 0.89 | 31k |
| 原型 | 0.79 | 0.70 | 50k |
| + 中等档 | 1.55 | 0.76 | 34k |
| + 中等档，空 slice 不归还 | 2.50 | 0.94 | 24k |
| + 中等档，空页晚还 | 2.12 | 0.71 | 33k |
| + 中等档，只在第一次用时 mprotect | 1.77\* | 0.73\* | 35k |
| **+ 中等档 + madvise** | **4.86** | **0.97** | 35k |

\* 另一轮测的，机器更忙；同一轮里 + 中等档为 1.12 / 0.68，+ madvise 为 3.14 / 0.84。

madvise 那一行的缺页次数和「+ 中等档」一样，却快 3 倍，区别只在归还和提交时改不改映射。

**rptest 的 RSS 不能直接比。** 跨线程的配置下，分配器越快，在途的跨线程块越多，测试程序自己的存活数据在 46–137 MiB 之间变化。用 rptest 自己报的「进程内存减去存活数据」才是分配器的额外开销：本结构 45–78 MiB，不做 madvise 时 49–58 MiB，mimalloc 72–94 MiB，不归还时 75–112 MiB。

**xmalloc。** 40 个线程跑在 20 个逻辑核上时比 mimalloc 慢 1 倍，20 个线程时持平（0.34–0.44 秒，噪声范围内）。超额订阅时，测试程序自己的队列锁和本分配器的全局锁都可能在持有者被抢占时排队；具体机制没有查。

## 不做的

| 试过什么 | 结果 | 什么条件下重开 |
| --- | --- | --- |
| 空出来的 slice 不归还 | 在只有中等档的结构上：不跨线程快 61%，跨线程快 24%；额外内存 75–112 MiB（对比 49–58）。改用 madvise 之后收益更大，这条没有意义 | 不重开 |
| 空页留在队列里，到定期整理时再还（约 10 行） | 不跨线程快 37%，跨线程慢 7% | profile 显示换页卡在全局锁上 |
| Linux 上只在第一次用时 `mprotect`、归还只用 `MADV_DONTNEED`（一套行为，约 2 行） | 只拿回 madvise 收益的三分之一（1.77 对 3.14 百万次每秒） | 不重开 |
| 中等页里空闲的块也还给系统，或者把中等页做小 | espresso 峰值在用的 slice 从 2 MiB 涨到 5 MiB，RSS 多 1.8 MB：中等页只要有一个活块，写过的块就一直占着物理内存 | 小工具的常驻内存成为问题时 |
| 全局锁换成无锁结构或分片 | xmalloc 40 线程时比 mimalloc 慢 1 倍，20 线程时持平 | 真实负载的线程数超过核数、跨线程释放又多时 |
| 严格 overcommit 时不做检测、只写进文档 | 碰上的人看到的是「程序起不来」或「别的进程分配失败」，联想不到分配器 | 不重开 |
| 释放后写入的检查（填充、canary）| 要在每次释放时写满整块、分配时校验，热路径的代价远大于上面四项检查 | 不重开，用 ASan |
| chunk 用 1 GiB | 64 MiB 以上、1 GiB 以内的块释放后 1 秒内能复用，反复分配释放快约 15 倍；但进程的虚拟地址上限低于约 2 GiB 时，第一次分配就失败，程序起不来（mimalloc 靠保留失败后改用 128 MiB 的回退分支躲开） | 不重开；要复用大缓冲区，由使用方留着 |
| 现代 C++ 包装：`allocator<T>`、RAII 句柄 | 覆盖全局 `new/delete` 后，标准容器和智能指针已经走本分配器，三个平台的 CI 有检查；`allocator<T>` 只服务「不全局覆盖、只让某几个容器用本分配器」，还会改变容器的类型（`vector<int, allocator<int>>` 不能当 `vector<int>` 传）；`std::pmr` 要 C++17 | 出现不能全局覆盖、又要让特定容器走本分配器的调用方时 |
| 覆盖库开 LTO，把 `alloc` / `free` 内联进 `malloc` / `free` | 每次分配或释放少 4 条指令（79.0 对 74.8，原型 59.7）；Clang 的 LTO 在 CI 上还要额外的链接器插件 | 覆盖库成为真实部署的主要方式时 |

## 没覆盖的

- macOS 没有本机，只有 CI 覆盖正确性（[`09f952d` 的运行](https://github.com/NickJerome/culib/actions/runs/38219833032)里 arm64 / x86_64 × debug / release 的分配器测试全部通过），没有测性能；`mprotect` 那条路径在 Linux 上只有严格 overcommit 时才走，CI 的 Linux 机器默认不是严格模式，这条路径的实际覆盖来自 macOS。
- Windows 只验证了正确性（本机 MSVC 2022 x64 release / debug；CI 上 MSVC x64 跑全部分配器测试，MinGW x86_64 跑 `culib_test` 和 `mem_test_stress`），没有测性能。
- 全套测量只在 Linux 上做过，而且宿主机同时在跑别的程序，单项各轮之间最多差 ±27%（lua），本实现最多 ±22%（alloc-testN），几何平均更稳。
- glibc-thread 的峰值 RSS 是 mimalloc（关大页）的 1.6 倍（13.8 MB 对 8.9 MB），没有查原因。
