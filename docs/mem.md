# 分配器

- 日期：2026-10-22
- 代码：`include/cu/mem.h`，`src/mem/`，`src/override/new.cpp`，`src/platform/` 里的 `memory*`、`thread_exit*`

## 1. 做什么

culib 自己的分配器（路线图 4.6）：

- 依赖 `culib_new_override` 这个目标，全局的 new / delete 就改用它：标准容器、`std::string`、协程的控制块都从这里分配。serve 用它。
- 另有 C 风格的 `cu::mem::alloc`、`aligned_alloc`、`free`，给要直接管内存的代码用。
- 不换 malloc。

## 2. 接口

| 分类 | 签名 | 说明 |
| --- | --- | --- |
| 接入 | xmake 里 `add_deps("culib_new_override")` | 全局 new / delete（含数组、nothrow、带大小的 delete）改用 `cu::mem`。按对齐的 new（C++17）不换，标准库自己的那一对照常配对 |
| 直接用 | `void* cu::mem::alloc(std::size_t size)` | 失败返回空指针，至少按 16 字节对齐 |
| | `void* cu::mem::aligned_alloc(std::size_t alignment, std::size_t size)` | alignment 是 2 的幂、最大 32 KiB，否则返回空指针 |
| | `void cu::mem::free(void* p)` | 空指针什么也不做 |

用的时候要知道的：

- 任何线程分配的块都能在任何线程还；协程挂起以后换了线程再还也行。
- 同一块还两次，打印诊断后终止。两次之间这块又被分配出去了的查不出来。
- 不支持在 fork 出来的子进程里接着分配：fork 时父进程里别的线程正拿着分配器的锁，子进程会卡住。

## 3. 取舍

### 代码怎么分

| 文件 | 管什么 |
| --- | --- |
| `src/mem/region.h/.cpp` | 64 MiB 一段的地址切成 64 KiB 的页：哪些页空着、哪些空页还占着内存；要页、交回页、把空页的内存还给系统 |
| `src/mem/allocator.cpp` | 尺寸档、页头、每根线程的堆、快慢路径、大块、重复释放、什么时候还内存 |
| `src/override/new.cpp` | 全局的 new / delete，只在 `culib_new_override` 里 |
| `src/platform/memory_*` | 保留地址、提交、还内存、还地址；Linux 上标成不用透明大页 |
| `src/platform/thread_exit_*` | 线程退出时通知一次：pthread 键的析构函数、Windows 的 FLS 回调 |

全进程一把自旋锁，只在慢路径上拿：要页、交回页、退出的线程留下的页、还内存。

### 小块

- 8 KiB 以内分 32 档：64 字节以内每 16 字节一档，之后每翻一倍分四档。
- 64 KiB 一页、一页一种大小，页头 128 字节放在页的开头：块的地址掩掉低 16 位就是页头，不用另外查表。8 KiB 那一档每页 7 块，浪费 1/8，mimalloc 的设计目标也是 1/8。
- 新页每次切 4 KiB 的块，没切到的部分不碰，也就不占物理内存。

### 每根线程一个堆

- 每档一串有空位的页、一串分完的页。分配只看第一页的空闲链。
- 每页三条空闲链：主人分配用的、主人还的、别的线程还的。别的线程还块，用一次 CAS 压到那一页上，之后不再碰那一页：主人随时可能把它收空、还掉。主人在空闲链用完时一次摘走整串。页里没收回的块都算在用，所以别的线程还到一半时，这一页不会被当成空页还掉。
- 分完的页，每次慢路径顺带看最多 4 页有没有别的线程还回来的块（上一版的做法）。
- 页空了就交回，每档留着最后那一页，免得分配和释放交替时来回换页；留着的页每 1024 次慢路径交回一次。

### 线程退出

- 空页交回，还有块的页按大小放进共享池，别的线程缺这个大小时接手。堆留给下一根新线程。
- 退出通知发过以后同一根线程又要分配（排在后面的线程局部变量的析构里），用一个临时的堆：分配完立刻交出去。

### 大块

- 超过 8 KiB 的块占若干连续的 64 KiB 页，在地址段的位图里从低到高找第一处够长的空位，头也在第一页开头。一段装不下的（约 64 MiB 以上）单独向系统要，还的时候整段还掉。
- 原来的打算是每块单独要一段映射、按大小留着。没这么做：每遇到一个新的大小就要进一次内核，每个活着的块还占一个映射（Linux 默认最多 65530 个，和协程栈共用）。

### 还给系统

- 交回的页先留着内存，下次要页时直接用。第一次有页空出来时定一个 1 秒后的时刻，到点以后谁先看到谁把所有空页的内存还给系统，地址留着。
- 小块的慢路径每 64 次看一眼，页空了交回时看一眼，要大块每 64 次看一眼；系统线程每一轮也看（`mem_purge`），它一次最多还 1 ms，剩下的过 10 ms 再来，免得耽误定时器和 I/O。看一眼要读一次时钟，所以还大块时不看。
- 三个平台：Linux 用 `MADV_DONTNEED`，映射不变，之后不用重新提交；macOS 原地重新映射一段不可访问的页，物理页当场释放；Windows 用 `MEM_DECOMMIT`。Linux 上整段地址标成不用透明大页：块稀疏地落在 64 MiB 里，开着透明大页的系统上碰一个字节就可能占满 2 MiB。

### 重复释放

- 空着的块的第二个字写成一个进程里随机的值，分配时清零：再还一次时它还是那个值，就终止（glibc 的 tcache 也这么查）。大块还掉时把页头的 kind 清成 0，再还一次就落到「不是 cu::mem 给出的指针」那条诊断上。
- 作者定的：只查这一种。上一版查四种（不是本分配器的指针、已经还掉的页、块中间的地址、重复释放），分配密集的测试慢 15%，还要一张地址图。

## 4. 测量

2026-10-22，和路线图、运行时文档同一台机器。同一份 `mem_bench` 只用 new / delete 和 `std::thread`：不链接覆盖库就是系统的分配器，链接 `culib_new_override` 就是 culib 的，链接上一版（`3720dcb`）的覆盖库就是上一版的。几个程序同场轮流跑 5 轮取中位数，括号里是整个程序用掉的 CPU 秒数。

Linux（WSL2，GCC 11.4 `-O2`，限在 8 个逻辑核上）：

| 场景 | glibc | 上一版 | culib |
| --- | --- | --- | --- |
| 一根线程反复 new / delete 64 字节，每对 | 8.4 ns（0.09 s） | 5.0 ns（0.05 s） | 3.7 ns（0.04 s） |
| 一根线程，256 个格子随机换掉，8 到 520 字节，每对 | 12.0 ns（0.12 s） | 8.3 ns（0.08 s） | 7.0 ns（0.07 s） |
| 先 new 100 万个 64 字节，再全部 delete，每次 | 18.4 ns（0.05 s） | 12.0 ns（0.03 s） | 12.4 ns（0.03 s） |
| 8 根线程各做第二项，每对（墙上时间除以总对数） | 2.0 ns（0.44 s） | 1.5 ns（0.31 s） | 1.2 ns（0.24 s） |
| 一根线程 new、另一根线程 delete，每块 | 86 ns（1.72 s） | 21 ns（0.41 s） | 18 ns（0.36 s） |

几处取舍的依据：

| 问题 | 量到的 | 怎么定的 |
| --- | --- | --- |
| 查重复释放 | 同一份代码查和不查同场 7 轮（Linux）：64 字节反复分配 3.70 → 3.76 ns，随机换 6.5 → 6.9 ns，一根 new 一根 delete 17.8 → 18.5 ns，8 根线程 1.15 → 1.39 ns | 作者定：只查这一种 |
| 慢路径之外还内存时看不看时钟 | 每次还大块都看一眼，64 KiB 到 1 MiB 的块每对 65 ns，不看 37 ns；只靠每 1024 次慢路径看一眼，200 MB 放掉 1.5 s 后还剩 136 到 148 MiB | 还大块时不看；页空了交回时看，慢路径每 64 次看一眼 |
| 测量程序防止 new / delete 被优化掉的那个变量 | 8 根线程写同一个变量时，三个分配器都像抢锁一样慢（glibc 10.3 ns，culib 10.4 ns，上一版 5.8 ns）；每根线程一个变量以后是上表的数 | 每根线程一个 |

serve 换上它以后看不出差别（`5ffc574` 加上这个分配器还没查重复释放的那一版，三轮轮流）：每秒请求数 12.2 到 12.7 万对 11.4 到 12.6 万，每个请求的 CPU 27.5 到 29.0 µs 对 27.8 到 29.8 µs。那里的时间花在系统调用上。

比别人慢的两处：

- Linux 上的大块比 glibc 慢一倍：每次都要拿全局锁、在位图里找一段连续的页。glibc 的块从它自己的缓存里来。
- Windows 上放掉以后，系统的分配器当场把内存还了；culib 要等 1 秒，这一秒里要同样大小的块直接用，不进内核。

代码约 1000 行有效代码：`allocator.cpp` 575 行，`region.cpp` 199 行，覆盖 new 的文件 83 行，线程退出的通知 68 行，其余是头文件。上一版去掉 malloc 覆盖库也有约 1430 行。

## 5. 不做的事

| 不做 | 为什么 | 什么条件下重开 |
| --- | --- | --- |
| 换掉 malloc（Linux 的 LD_PRELOAD 覆盖库，上一版有） | 作者选了只换 new / delete | C 程序或第三方库里的 malloc 成了瓶颈时 |
| 分完的页「遗弃」，由第一个往里还块的线程接管（mimalloc v3） | 要一套所有权位，加上接管、放弃的协议；每次慢路径看 4 页够用 | 慢路径扫分完的页在参考程序里量得出来时 |
| 别的线程还块时，把这一页挂到主人的一张表上 | 那一页可能在还块和挂表之间被主人收空、还掉，mimalloc 正是避开了这个窗口 | 不重开 |
| 每个大块单独一段映射、按大小留着 | 见第 3 节 | 不重开 |
| 线程退出时整个堆留给下一根新线程 | 只有新线程能用那些页，还得定时去收里面的空页 | 不重开 |
| 查四种误用 | 见第 3 节 | 出了这几种 bug、又很难查的时候 |
| fork 钩子（上一版有） | serve 不 fork | 有 fork 以后接着分配的使用方时 |
| 严格 overcommit（`vm.overcommit_memory=2`）时退还提交额度 | `MADV_DONTNEED` 不改映射，还过内存的页仍算在提交额度里；改映射要拿进程的映射写锁 | 要在严格 overcommit 的机器上跑时 |
| 换掉按对齐的 new（C++17） | 覆盖 new 的文件按 C++11 编 | 有大量按对齐 new 的使用方时 |
| `calloc`、`realloc`、`usable_size`、主动还内存的 `collect` | 没有调用方 | 有调用方时 |
| 大块更快：每根线程手边留一两个刚还的大块 | 见第 4 节；比起碰一遍这块内存可以不计 | 大块的分配在参考程序里量得出来时 |
| Windows 上大块只提交用到的页 | 现在一个 9 KiB 的块占 64 KiB 的提交额度 | 提交额度在 Windows 上成了问题时 |

## 6. 测了什么

- `tests/mem_test.cpp`：每种大小的块互不重叠；对齐；大块和单独要的大块；别的线程还回来的块再用上，不要新页；接手退出的线程留下的页，不要新页；空页的内存还给系统；8 根线程互相还块，内容不坏；协程换了线程再还。`tests/override/`：换上 new 的覆盖以后，标准容器、线程、协程照常能用。`tests/fault/`：小块、大块各还两次，打印诊断后终止。
- 反向验证过：主人不收别的线程还的块、空页从不还给系统、不接手退出的线程留下的页、大块还回来不交回，各让对应的测试失败。
- 本机：Windows MSVC debug / release、MSYS2 UCRT64 的 MinGW；Linux GCC debug / release、Clang、关掉异常和 RTTI、ASan + UBSan、Clang 14 的 TSan；GCC 4.8 和 macOS（照 SDK 抄的头文件桩）只做了类型检查。
- 没测：macOS 上的运行（只有 CI）；性能只在 Linux 和 Windows 上量过；mimalloc-bench（要换 malloc）；8 根以上的线程。
