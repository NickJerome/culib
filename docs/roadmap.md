## 1. 目的

先学习和练手；做好以后，作者自己拿来开发、上生产。没有外部使用方，不为别人准备 CMake 和英文文档。

可靠优先：不丢唤醒，不悄悄写坏内存，出了问题查得出来。速度够用就行。

Linux、Windows、macOS 同等对待。

只做通用设施。HTTP、TLS、加密、压缩、图像这类具体的协议和格式由应用处理；参考程序用到时写在程序里，不进库。

## 2. 判据

- 库的每个改动，理由要么来自参考程序，要么来自正确性问题。在参考程序里找不到用处的模块不做。
- 性能工作分开两处：
  - 实验在仓库外做。想学的机制照样可以试、可以量，结论写进对应模块文档里「试过的」那张表，写明什么条件下重开。
  - 主线只收两种改动：修了真问题的；收益大、又不多带规则的。收益在参考程序的负载上量。
- 和 Go 的记分板只当护栏：慢好几倍，或者出现卡住、长尾时才改。

## 3. 参考程序

放在 `apps/` 下，每个有自己的 xmake 目标和测试，CI 一起编。库和程序在同一个提交里改，接口一改坏，程序马上编不过。

### 3.1 serve：静态文件 HTTP 服务器

它用到几乎全部服务器侧的模块：网络和协程（一个连接一根协程）、文件、日志、优雅退出、时间和字符串。

第一版只做这些：

- GET 和 HEAD；
- keep-alive；
- 目录默认返回 `index.html`；
- 按扩展名给 Content-Type；
- 常见的错误码；
- 路径不许跳出根目录。

不做 TLS。

做完的标准：

- 慢客户端和闲着的连接都有超时；
- 收到 Ctrl+C 或 SIGTERM 时，不再接新连接，等在途的请求结束再退出，等待时间有上限；
- 长时间压测下，常驻内存和句柄数不往上涨；
- 三个平台的 CI 里各起一次服务、取一个文件、再停掉。

压测得到的吞吐、p99 延迟和每个闲连接占的内存，是判断运行时改动值不值的依据。

### 3.2 第二个：批量处理文件的 CLI

比如查重复文件，主要检验 flag、fs 和 term。serve 写完再定。

## 4. 根本决定

| 决定 | 内容 |
| --- | --- |
| 协程 | 有栈。写法像线程：任何函数里都能挂起，第三方库的回调里也行 |
| 语言 | C++11 |
| 栈 | 照 `std::thread`：每根固定 1 MiB，保护页一直开着，用到哪页才占哪页内存，溢出当场崩溃，调用方不用选。代价是 Linux 默认的 `vm.max_map_count` 下，同时最多约 3.2 万根 |
| 调度 | 多根工作线程，协程可以换线程，细节见下面 4.1 |
| 接口 | `cu::coroutine` 的行为全部照 `std::thread`，`cu::this_coroutine` 对应 `std::this_thread`，见下面 4.2 |
| 名字 | 名字空间 `cu`，内部实现放 `cu::detail`；头文件写成 `<cu/xxx.h>`；宏前缀 `CU_`；库名 culib |

没有选的几种，见第 7 节。

### 4.1 调度

队列：

- 每根工作线程一个「下一根」格子（一个原子变量）和一个本地队列，另有一个全局队列。两种队列是同一种：用控制块里的指针串起来的一串协程，加一把自旋锁，不限长。
- 协程叫醒的协程进叫醒者这根线程的格子，格子里原来那根挪进本地队列。I/O 线程和普通线程叫醒的进全局队列。
- 格子让「叫醒对方马上就等」的一对协程留在同一根线程上接着跑，不排队、不被偷、不叫醒别的线程。

取活的顺序：每 61 次先看一眼全局队列；格子，连着从格子里跑 3 次就让一次；本地队列；全局队列；去别的线程的本地队列里偷一半；都没有就睡。偷的时候锁上对方拿走一半（最多 128 根），放开，再锁上自己放进去，任何时候都不同时拿两把队列锁。

叫醒：往空格子里放不叫醒任何线程；往本地队列或全局队列里放时，只有没线程在找活才叫醒一根，找到活的那根再叫醒下一根。活放在本地队列里时，不丢唤醒靠一对 `seq_cst` 屏障加睡前把所有队列再查一遍。

一根系统线程：等 I/O（epoll / kqueue / IOCP，最多等到最近的定时器）、跑定时器、监控。监控只在有工作线程忙时每 1 ms 查一次（占一个核的约 1%）：

- 一根线程这 1 ms 一根协程都没跑完，就把它格子里的协程挪进全局队列；
- 一根线程在同一根协程里待了超过 10 ms、还有活等着，就补一根工作线程，多出来的闲下来再退；
- 有活没人干、又没线程在找活，就兜底叫醒一根。

依据（2026-10-21，WSL2，i7-12700，8 根工作线程）：原型里协程用整数代替，同场比较几种队列，带锁的本地队列比最快的无锁写法（Go 式环）慢不到一成，比只有格子快一到两个数量级（很多协程同时就绪时）。另做了一个真协程原型（换栈用上一版的汇编），和上一版、Go 1.24.5 同场：让出和经 channel 来回传消息比上一版快约 1.6 倍、比 Go 快 2.5 到 5 倍；起协程和「一次叫醒 64 根」落后，前者是原型的控制块用了 glibc 的 `malloc`，后者是一次只叫醒一根找活的线程、起步慢。

第一步写调度器时一起处理这两处：控制块每根线程手边留一批，别的线程释放时还回去；一次叫醒一批时的起步，在真实现里量了再定。2026-10-21 在真实现里量了（8 根工作线程）：一次叫醒 64 根每轮 65 µs，Go 72 µs，不用另做；起协程 185 ns，Go 164 ns，CPU 是 Go 的 3 倍，但 malloc 只占其中 25 到 30 ns，serve 里看不出来，所以控制块缓存先不做（作者定的，见第 7 节）。其余测量见 [运行时文档](runtime.md)。

本地队列原来照 Go 定成 256 格的数组环，满了一半挪进全局队列。定长是 Go 无锁队列的要求，我们的队列带锁，用不着。2026-10-21 改成和全局队列同一种链表，同场量过：8 根工作线程时 1000 根协程一起让出从 23 ns 降到 12 ns，起协程从 155 ns 涨到 180 ns（Go 165 ns）；只有 1 根工作线程时 1000 根一起让出从 49 ns 涨到 59 ns（Go 84 ns）；serve 看不出差别。作者选了链表，原来的写法记在第 7 节。

工作线程平时开进程能用的核数：Linux 上看亲和性和容器的 CPU 配额，配额向上取整、不到 2 个核按 2 个算，和 Go 1.25 一样；macOS 和 Windows 用系统的逻辑核数。没有配置项。

### 4.2 `cu::coroutine`

会用 `std::thread` 就会用它，行为一样：

- 构造时传入可调用对象和参数，参数按值拷（或移动）进协程，成员函数指针配对象或指针也行，要传引用用 `std::ref`；构造完就开始排队跑。
- `join()` 等它跑完：在协程里调，挂起当前协程，线程去跑别的；在普通线程上调，阻塞这根线程。`detach()` 放手，协程跑完自己清理，进程退出时还没跑完的随进程结束。
- 析构或被移动赋值时还能 join，进程终止；协程已经跑完、只是没 join，也算还能 join。
- 协程函数里漏出的异常走 `std::terminate`。
- 另有 `joinable()`、`get_id()`、`swap()`；`id` 可以比较、做 `std::hash` 的键、用 `<<` 输出。
- `cu::this_coroutine` 有 `get_id()`、`yield()`、`sleep_for()`、`sleep_until()`。不在协程里调用时，`get_id()` 返回空 id，其余三个等同于 `std::this_thread` 的同名函数。

和 `std::thread` 不一样的只有四处：

- `std::thread` 抛 `system_error` 的几种误用（对不能 join 的对象调 `join()` 或 `detach()`、协程 join 它自己、内存不够起不了协程），这里打印诊断后终止，因为公共头文件不抛异常。
- 析构或移动赋值时还能 join，`std::thread` 直接调 `std::terminate`，这里先打印一句诊断再终止。两边退出码都是 134。
- 没有 `native_handle()` 和 `hardware_concurrency()`：协程没有系统句柄，核数照样用 `std::thread::hardware_concurrency()` 查。
- 线程可以在 catch 块里等，协程不能：在 catch 块里挂起时打印诊断后终止。正在处理的异常记在线程上，同一根线程上的协程共用一份。2026-10-21 实测，两根协程在 catch 块里交错挂起，回来以后 `throw;`：GCC 上 A 重抛出 B 的异常、B 重抛出 A 的，程序照常退出；MSVC 上 A 重抛出 B 的异常，接着进程崩溃。挂起前查一次 `std::current_exception()`，GCC 上 2.4 ns，MSVC 上 16 ns。异常展开途中（析构函数里）挂起同样不对，但不查：GCC 4.8 上接住 `rethrow_exception` 抛出的异常以后，`std::uncaught_exception()` 一直为真（libstdc++ PR 62258），会把正常的挂起当成误用。

2026-10-21 在原型上验证过（Linux，GCC 11.4 `-std=c++11` 和 `-std=c++17`，1 根和 8 根工作线程）：函数加参数、成员函数指针、`std::ref`、在普通线程和协程里 join、`detach()`、放进 `vector`、`swap`、`id` 的比较、哈希和输出；四种误用（join 和 detach 不能 join 的对象、协程 join 自己、给还能 join 的对象赋值）、漏出异常、跑完了没 join，都是上面写的结果。原型没有定时器，`sleep_for()` 和 `sleep_until()` 当时没验证，超时那一步实现时补了测试（见[运行时文档](runtime.md)）。

### 4.3 错误

- 可能失败的函数返回 `cu::result<T, E>`，`E` 默认是 `cu::error`。库自己的函数一律报 `cu::error`；开发者给自己的代码定义自己的错误类型，在调库的地方换一次。
- `cu::error` 是一个种类加一句消息。种类是库对自己的失败的分类，固定 10 种：unknown、invalid_argument、out_of_range、resource_exhausted、not_found、already_exists、permission_denied、timeout、unsupported、io。系统错误码按一张固定的表换成种类，比如端口被占是 already_exists、句柄用完是 resource_exhausted，表里没有的算 io。
- 造 `cu::error` 只有 `make_error(kind, message)` 一种写法，构造函数是私有的：`error` 也是常用的变量名和 `result` 的成员函数名，`error(...)` 会被它们遮住。
- 消息和诊断都用英文。消息的格式照 Go：`操作 对象: 系统原话`，比如 `open /srv/index.html: No such file or directory`。Windows 上的系统原话和 Go 一样先取英文版，系统没装英文时才用系统语言；中文 Windows 上不这么做的话，一句消息里前半句英文、后半句中文。
- 失败时调 `value()`、成功时调 `error()`，打印诊断后终止，release 也查。开发者自己的错误类型，库不知道怎么打印，诊断里只有一句 `cu::result::value() called on an error`。
- `cu::string_view` 和测试框架（`TEST`、`EXPECT`、`--filter`、`--list`）照搬上一版，只改名字。`defer` 和 `fatal` 只在库内部用。

### 4.4 网络和文件

第一步的接口：

- `cu::net::listen("host:port")` 返回 `listener`，`listener::accept()` 和 `cu::net::connect("host:port")` 返回 `connection`。两个类型分开，用错角色编译不过；都只能移动，析构时关闭。
- 地址写成一个字符串，和 Go 一样。`":8080"` 收所有 IPv4 和 IPv6 地址，`"0.0.0.0:8080"` 只收 IPv4，`"[::]:8080"` 只收 IPv6；端口写 0 由系统挑，用 `local_address()` 查。第一步只认数字 IP，域名解析以后单独加。
- `connection::read(buffer, capacity)` 读到一些就返回，返回 0 表示对端关了。`write(data, size)` 全部写完才算成功，失败时前面可能已经写出去一部分。同一时刻最多一根协程读、一根协程写。
- 会等的调用（accept、connect、read、write）在协程里挂起协程，在普通线程上阻塞这根线程。
- 默认行为照 Go，不留选项：Linux 和 macOS 设 `SO_REUSEADDR`，Windows 不设（设了别的程序能抢走端口）；关掉 Nagle；子进程不继承；写断开的连接不触发 SIGPIPE；监听队列用系统上限；accept 时对端已经断开的，库在内部接着等，句柄用完返回 resource_exhausted，由调用方等一会儿再试。
- `cu::fs::read_file(path)` 把整个文件读进内存，照 Go 的 `os.ReadFile`：按文件大小多分配一个字节，读到它就知道到头了。
- `connect` 的 host 空着、写 `0.0.0.0` 或 `[::]` 时连本机，和 Go 一样。Linux 和 macOS 自己这么做，Windows 不认，库里统一换成环回地址；所以 `connect(server.local_address().to_string())` 在三个平台上都能用。
- 一次读写最多 1 GiB，和 Go 一样：macOS 一次超过 `INT_MAX` 字节报 `EINVAL`，Windows 的长度是 32 位的。调用方看不出区别，`read` 只是读到的少一些，`write` 自己分几次写。
- `read_file` 读目录时三个平台都报 unsupported，消息是 `open <path>: is a directory`（Windows 打开目录报的是拒绝访问）。
- `read_file` 读的时候阻塞所在的工作线程，不另做：排在这根线程后面的协程由监控交给别的线程（4.1），都忙时补一根线程。2026-10-21 实测，8 根工作线程时，卡住的线程「下一根」格子里的协程约 1.5 ms 后在别的线程上跑起来；只有 1 根时约 11 ms。
- Windows 上 Winsock 起不来、拿不到 AcceptEx 和 ConnectEx 时打印诊断后终止，和建不了完成端口一样：支持的系统上不会发生。
- Windows 上连一个没人监听的本机端口，要约 2 秒才报错（系统收到 RST 以后还会重发 SYN），Linux 和 macOS 立刻报。这是系统的行为，库不改。
- Windows 上一次 `write` 不管多大，系统都先整块收下、替它缓冲（2026-10-23 实测 256 MiB 用了 58 ms），对端不读时到下一次写才等。这也是系统的行为，库不改。
- 从别的协程关掉正在等的句柄（优雅退出要用）、域名解析和 UDP，各放到后面的一步。

超时（作者 2026-10-22 定照异步框架的做法，2026-10-23 定接口）：

- 会等的调用默认一直等。要限时就把这一段包在 `cu::timeout(时长, 函数)` 里，照 tokio 的 `timeout`：函数里的 read、write、accept、connect 共用一个截止时刻，到点返回 timeout，消息照 Go，例如 `read 127.0.0.1:51234: i/o timeout`。一个时限可以包住好几次调用，比如收完整个请求头。
- 和 tokio 不一样的一处：tokio 到点就扔掉里面那段操作，C++ 没法从外面停住一段普通代码。这里是到点时正在等的那个调用返回 timeout，之后里面再调会等的函数只试一次、不等，由函数把错误 return 出来。所以函数必须返回 `cu::result`，忘了 return 编译报错。
- 可以套着用，里面的时限只会更紧；在里面新起的协程不受它管，tokio 里 spawn 出去的任务也是这样。时长不为正时只试一次，和 tokio 一样（Go 直接报超时，连试都不试）。
- 只管 net 里会等的调用。mutex、condition_variable、`sleep_for`、join 不管：它们没有返回值能报超时，条件变量要限时用 `wait_for`。
- 读超时以后连接照样能用，没读到的数据下次还能读到；写超时的时候前面可能已经写出去一部分。

依据：读过 Go 1.25.3（net、net/http、internal/poll、runtime/netpoll）、tokio 和 hyper、Asio 和 Beast、brpc 的源码。读写这一层都默认不超时，超时由调用方加：Go 设在连接上，tokio 和 Asio 包在每次操作外面；默认值都出在知道协议的那一层，比如 hyper 的请求头 30 秒、Beast 建议的 WebSocket 空闲 300 秒、brpc 一次 RPC 500 ms。Go 另外默认开 TCP keepalive。实现和测量见[运行时文档](runtime.md)。

依据：读过 Go 1.24.5（net、internal/poll、os）、Rust 标准库（std::net、fs）和 PhotonLibOS（net）的源码。2026-10-21 在 Linux 原型上（epoll，一根工作线程）跑过第一步的 serve：curl 和 1000 个请求（50 个同时）全部 200；端口被占、文件不存在、权限不够、写域名、连不上，消息和种类都对；`":8082"` 用 IPv4 和 IPv6 都能连上。

### 4.5 mutex 和 condition_variable

- `cu::mutex`、`cu::condition_variable` 的接口照 `std::mutex`、`std::condition_variable`（作者 2026-10-22 确认）。在协程里等只挂起协程，在普通线程上阻塞线程，两边可以混着用；拿着锁可以挂起，换了线程再放。
- 放锁时叫醒排在最前面的那根，它和刚来的一起抢；抢输一次，下一次放锁直接交给它（作者定的）。8 根协程抢一把锁时每次 12.5 ns，Go 33 ns；单次拿锁最久等 16 ms，Go 4.8 ms。
- `wait_for`、`wait_until` 是第一处照异步框架的超时做法写的：给这次等待配一个定时器，到点取消等待、返回超时。它们有自己的时长参数，不受 `cu::timeout`（4.4）管。
- `notify_all` 叫醒一大群比 Go 慢、一直不挂起的协程抢锁时等锁的等得久，两处先不做，原因和重开条件在[运行时文档](runtime.md)第 4、5 节（作者定的）。

### 4.6 分配器

- 给谁用：依赖 `culib_new_override`，全局的 new / delete 改用它；另有 C 风格的 `cu::mem::alloc` / `aligned_alloc` / `free`。不换 malloc（作者 2026-10-22 定）。
- 结构照 mimalloc 最核心的那一点：64 KiB 的页一页一种大小，每根线程一个堆，别的线程还块用一次 CAS 压到那一页上。上一版的大部分（64 MiB 的 chunk 和 slice 描述符表、中等页、malloc 覆盖库、fork 钩子）不做（作者定的）。大块是地址段里连续的页，空出来的页留 1 秒再还给系统。
- 释放时只查重复释放（作者定的）。
- 细节、测量和不做的事见[分配器文档](mem.md)。

## 5. 模块和顺序

| 基础 | result 与错误、string_view、optional、defer、fatal、strings、lexical_cast | 用，只做用得到的部分 |
| 测试 | `TEST` / `EXPECT` | 用，第一天就要有 |
| 平台 | os（停止信号、环境变量）、time（时钟、HTTP 日期） | 用 |
| 内存 | 分配器（`cu::mem`、`culib_new_override`） | 用 |
| 运行时 | 换栈、栈池、调度器、定时器、I/O 引擎、mutex / condition_variable、`cu::coroutine` | 用 |
| I/O | net（TCP）、fs（打开、读、查询、路径） | 用 |
| 上层 | log、flag | 用 |
| 以后再说 | term、config、bytes、UDP、channel、目录遍历 | 等第二个参考程序，或者真有需要时 |

顺序是先打通一条最细的路，再一层层加厚：

1. 在三个平台上跑通「一根工作线程 + TCP + 只会返回一个文件的 serve」。Windows 的换栈和 IOCP 在这一步就要有。2026-10-21 完成，`e9aaba2..c75388e`。
2. 之后每一步只加一样东西，比如多线程和偷任务、超时、真正的文件服务、日志、优雅退出。加什么由 serve 的需要来定；每一步都在三个平台的 CI 上跑通。多线程和偷任务 2026-10-21 完成，`b8bc921..1a1c166`；定时器和 `sleep_for()` 同一天完成，`dd66dba`；栈池 2026-10-22 完成，`161a8c9`；mutex / condition_variable 同一天完成，`5ffc574`；自己的分配器也是同一天完成，`998eced`（作者 2026-10-21 定目标：要做高性能、低占用的内存和协程库；2026-10-22 定了这个顺序）；读写超时 2026-10-23 完成。下一步还没定，候选：serve 用上超时；工作线程闲下来时自己查一次 I/O，单个连接一问一答时服务端的 CPU 是 Go 的 1.7 到 2.4 倍（见[运行时文档](runtime.md)第 4 节）。

## 6. 约定和流程

- 代码在 `v2` 分支上从空目录开始写，上一版留在 master（`3720dcb`）上对照。v2 能替换上一版时，先在 v2 上把 master 记成父提交，再让 master 快进到 v2，不改写历史。
- 写代码的约定见 [CLAUDE.md](../CLAUDE.md)，大多照搬上一版。
- 每个模块一份文档，写五件事：做什么、接口、取舍、不做的事和重开条件、测了什么没测什么。测量数字只在用来支撑某个决定时才写。
- CI 的结果只更新 CLAUDE.md 里的那一个链接，不按提交逐个记进文档。
- 每个模块动手之前，先把接口表和一个能编译运行的完整例子（源码加实际输出）给作者看，确认了再写。
- CI 第一步就全部打开：三个平台的 debug 和 release、MinGW、GCC 4.8、ASan/UBSan、TSan、头文件检查。

## 7. 考虑过、没有选的

| 选项 | 为什么没选 | 什么条件下重开 |
| --- | --- | --- |
| 在上一版的代码上接着改 | 机制之间开始互相打补丁，难查的 bug 都出在新加的机制上。从空目录重来，每个机制都重新问一次为什么需要 | — |
| 无栈协程（C++20 的 `co_await`） | 写法会传染：会挂起的函数都得写成协程，普通函数和第三方库的回调里不能挂起；引用参数和 lambda 捕获有生命周期的坑。好处是每根协程只占它的帧（演示里 216 字节），也没有栈带来的平台问题 | 每根协程占的内存成了实际问题时 |
| 共享栈 | 挂起期间，指向局部变量的指针不能交给别人用；协程不能换线程；切换时要拷栈 | 不重开 |
| 像 Go 那样会长的栈 | 要编译器配合，C++ 做不到 | 不重开 |
| C++17 或 C++20 | C++11 能编的系统最多。代价是 string_view、optional 要自己写，公共类型的定义不能随使用方的标准变 | 出现必须用新标准才能写的东西时 |
| release 构建不设保护页 | 栈溢出时会悄悄写坏别的协程的栈 | 不重开 |
| 保护页用 `MADV_GUARD_INSTALL`，不多占映射 | 6.13 以下的内核没有，要多一条代码路径 | 最低支持的 Linux 内核到 6.13 时，同时去掉 3.2 万根的上限 |
| 栈 256 KiB | 每根协程的页表少 1.5 KiB，但能递归的深度少了四倍 | 页表占的内存成了实际问题时 |
| 每根线程一个调度器，协程不换线程 | 一根协程阻塞或者长时间计算，同一线程上的协程都得等；阻塞调用要交给线程池，用起来不像线程 | 不重开 |
| 只有一个带锁的全局队列 | 8 根线程时两根协程来回传消息掉到每秒约 6 万次：协程一放进去就叫醒一根睡着的线程，被它抢走，每次都换线程 | 不重开 |
| 全局队列加格子，没有本地队列 | 很多协程同时就绪时，每次都过全局锁，每调度一次约 380 ns，带本地队列约 20 ns | 不重开 |
| 中心分派：一根调度线程把每根协程分给闲着的工作线程 | 每次调度至少两次线程叫醒，来回传消息每秒约 4 万次；做成无锁（MPSC 加收件格）也一样，慢在叫醒不在锁；调度线程被系统晚调度时所有协程一起停 | 不重开 |
| BEAM 式：每线程队列，由一根线程定期算迁移计划，各线程照着搬 | 比偷一半多一套计划和搬运；没有长期负载不均衡的场景时看不出收益 | 参考程序出现长期负载不均衡时 |
| 无锁本地队列：Go 式（一个放、多个取）、PhotonLibOS 的 MPMC 环和批量 MPMC 环 | 最快的 Go 式只比带锁队列快不到一成，Photon 的两种不比它快；多一份要写对、要压测的无锁代码；Photon 的两种在占了位的线程被切走时别人要等 | 带锁队列在参考程序里成了瓶颈时；先在实验里做 |
| PhotonLibOS 的非对称自旋锁 | 照抄原样，主人和偷的线程会同时进锁（压力测试里主人加锁 2000 万次，同时在锁里几千到几万次），原因是存和读之间没有完整屏障；加了 `seq_cst` 屏障就不再出现，但也不比普通自旋锁快 | 不重开 |
| 本地队列用 256 格的数组环，满了一半挪进全局队列（Go 的做法） | 定长是 Go 无锁队列的要求，带锁的队列用不着；多一种存法，多一段「满了挪一半」。和链表同场比，数组环起协程快 14%，只有一根工作线程时 1000 根一起让出快 17%；多根工作线程时 1000 根一起让出慢一倍 | 起协程的开销在参考程序里量得出来时 |
| 8 个独立格子代替本地队列 | 只在很多协程一直有活时有用，一次叫醒一批时帮得不多 | 不重开 |
| 闲线程先空转一会儿再睡 | 只让 8 根线程的来回传消息从每秒约 6 万次提到约 10 万次 | 有数据显示叫醒延迟成了问题时 |
| 控制块每根线程手边留一批，别的线程释放时还回去 | 原来定在多线程那一步做。真实现里 malloc 只占起协程的 25 到 30 ns，serve 每个请求约 30 µs，看不出来 | 起协程的开销在参考程序里量得出来时 |
| 只有一个调度线程 | 只用一个核，阻塞调用和重计算都要交给线程池 | 不重开 |
| 新仓库 | 要重新配 CI，对照旧代码也不方便 | — |
| 自底向上，一层层做完 | serve 到最后才出现，中间没有使用方 | — |
| `cu::coroutine` 析构时自动等它跑完（`std::jthread` 的做法） | 作者要求行为和 `std::thread` 一致：会用 `std::thread` 的人不用重新学，漏了 join 当场报出来 | — |
| `cu::coroutine` 析构时自动放手（Go 的 `go` 语句的做法） | 同上；而且协程可能比它引用的局部变量活得久 | — |
| 错误种类固定 10 种，开发者不能定义自己的 | 开发者只能把自己的情况硬塞进最接近的种类 | — |
| 种类开放：开发者定义新的种类，比较时比地址（Go 的做法） | C++11 里种类写在头文件里，每个 .cpp 各有一份，判断悄悄失效、编译不报错（原型验证过）；要写对每个种类得写两处；比地址没法用 `switch` | 最低标准到 C++17（有 `inline` 变量）时 |
| 错误消息用中文 | 作者选了英文：放进日志不混语言，形状和 Go 一样 | — |
| 网络合成一个 `socket` 类型（上一版） | 用错角色只能在运行时报错；合并想省掉的重复代码在库内部就能消掉 | — |
| 地址的 IP 和端口分开传（上一版） | 配置和命令行里地址本来就写成 `:8080`，分开传要调用方自己拆 | — |
| `"0.0.0.0:8080"` 也同时收 IPv6（Go 的做法） | 写什么就收什么更好懂 | — |
| `":8080"` 只收 IPv4 | 实现最省事，但一个监听接不到 IPv6 的连接；同时收两种只多几行 | — |
| `connect(":8080")` 报 missing host（原型的做法） | 调用方连自己监听的 `local_address()`（`"[::]:port"`）时得自己换成环回地址；Go 连本机，Linux 和 macOS 也这么做 | — |
| 超时用截止时刻（Go 的 `SetDeadline`） | 作者选了异步框架的做法：同一个办法管所有会等的操作。截止时刻设在句柄上，只管这个句柄的读写 | — |
| 超时用每次读写的时长（上一版；Java 的 `setSoTimeout`、Rust 的 `set_read_timeout`） | 同上：时长也设在句柄上 | — |
| 超时作为每个会等的函数多带的一个时长，如 `read(buffer, size, 30s)` | 2026-10-22 做过原型，作者 2026-10-23 换成 `cu::timeout`：每个函数要多一个重载；一个时限要管好几次调用时（收完整个请求头），每次都得自己算还剩多少时间 | — |
| 库给读写定一个默认时限，比如 60 秒没动静就超时（Apache 的做法） | Go、tokio、Asio 的读写层都默认一直等，默认值出在知道协议的那一层；放在读写层会打断本来就该长时间等的连接 | — |
| 到点直接停住里面那段代码（tokio 扔掉 future、Kotlin 抛 CancellationException） | C++ 没法从外面停住一段普通代码；不用异常时只能让等的调用报错，由函数自己 return | 不重开 |
| 连接默认开 TCP keepalive（Go 的做法：15 秒没动静开始探，每 15 秒一次，9 次不应答就断） | 这一步不做，三个平台设 keepalive 的写法不一样 | 出现长时间闲着的连接、要自动发现对端断电断网时 |
| 放锁时照 Go：从排队算起等满 1 ms 还抢输，才直接交 | 测出来和现在的做法一样（8 根抢一把锁每次 12.1 ns，最久等 16 ms），要多读时钟 | — |
| 放锁时有人排着就直接交，先来先得 | 最久只等 0.3 ms，但 8 根抢一把锁时每次 64 ns，慢 5 倍：每次拿锁都要挂起、叫醒一次 | 参考程序里等锁的最长延迟比吞吐要紧时 |
| 放锁时从不直接交，一直一起抢 | 一直拿着锁的协程能让等的那根等上几百毫秒（量到 282 ms） | 不重开 |
| 分配器用每线程缓存加全局中心（tcmalloc、Go 的分法） | 块散在各线程的缓存里，整页很难空出来还给系统；一批换一批的全局中心要一把锁 | — |
| 分配器照上一版全做（chunk 和 slice 描述符表、中等页、四种误用检查、malloc 覆盖库） | 约 1500 行；作者要简单的，按需再加 | — |
