# 路线图

- 日期：2026-10-21
- 状态：生效中。这是重写用的路线图。上一版的代码和文档留在 master 上，最后一个提交是 `3720dcb`。

## 1. 目的

先学习和练手；做好以后，作者自己拿来开发、上生产。没有外部使用方，不为别人准备 CMake 和英文文档。

可靠优先：不丢唤醒，不悄悄写坏内存，出了问题查得出来。速度够用就行。

Linux、Windows、macOS 同等对待。

只做通用设施。HTTP、TLS、加密、压缩、图像这类具体的协议和格式由应用处理；参考程序用到时写在程序里，不进库。

## 2. 判据

- 库的每个改动，理由要么来自参考程序，要么来自正确性问题。在参考程序里找不到用处的模块不做。
- 性能工作分开两处：
  - 实验在仓库外做。想学的机制照样可以试、可以量，结论写进对应模块文档里「试过的」那张表，写明什么条件下重开。
  - 主线只收两种改动：修了真问题的；收益大、又不多带规则的。收益在参考程序的负载上量。
- 和 Go 的记分板只当护栏：慢好几倍，或者出现卡住、长尾时才改。

## 3. 参考程序

放在 `apps/` 下，每个有自己的 xmake 目标和测试，CI 一起编。库和程序在同一个提交里改，接口一改坏，程序马上编不过。

### 3.1 serve：静态文件 HTTP 服务器

它用到几乎全部服务器侧的模块：网络和协程（一个连接一根协程）、文件、日志、优雅退出、时间和字符串。

第一版只做这些：

- GET 和 HEAD；
- keep-alive；
- 目录默认返回 `index.html`；
- 按扩展名给 Content-Type；
- 常见的错误码；
- 路径不许跳出根目录。

不做 TLS。

做完的标准：

- 慢客户端和闲着的连接都有超时；
- 收到 Ctrl+C 或 SIGTERM 时，不再接新连接，等在途的请求结束再退出，等待时间有上限；
- 长时间压测下，常驻内存和句柄数不往上涨；
- 三个平台的 CI 里各起一次服务、取一个文件、再停掉。

压测得到的吞吐、p99 延迟和每个闲连接占的内存，是判断运行时改动值不值的依据。

### 3.2 第二个：批量处理文件的 CLI

比如查重复文件，主要检验 flag、fs 和 term。serve 写完再定。

## 4. 根本决定

| 决定 | 内容 |
| --- | --- |
| 协程 | 有栈。写法像线程：任何函数里都能挂起，第三方库的回调里也行 |
| 语言 | C++11 |
| 栈 | 照 `std::thread`：每根固定 1 MiB，保护页一直开着，用到哪页才占哪页内存，溢出当场崩溃，调用方不用选。代价是 Linux 默认的 `vm.max_map_count` 下，同时最多约 3.2 万根 |
| 调度 | 多根工作线程，协程可以换线程，细节见下面 4.1 |
| 接口 | `cu::coroutine` 的行为全部照 `std::thread`，`cu::this_coroutine` 对应 `std::this_thread`，见下面 4.2 |
| 名字 | 名字空间 `cu`，内部实现放 `cu::detail`；头文件写成 `<cu/xxx.h>`；宏前缀 `CU_`；库名 culib |

没有选的几种，见第 7 节。

### 4.1 调度

队列：

- 每根工作线程一个「下一根」格子（一个原子变量）和一个带自旋锁的本地队列（256 格）；另有一个带锁的全局队列。
- 协程叫醒的协程进叫醒者这根线程的格子，格子里原来那根挪进本地队列。本地队列满了，一半挪进全局队列。I/O 线程和普通线程叫醒的进全局队列。
- 格子让「叫醒对方马上就等」的一对协程留在同一根线程上接着跑，不排队、不被偷、不叫醒别的线程。

取活的顺序：每 61 次先看一眼全局队列；格子，连着从格子里跑 3 次就让一次；本地队列；全局队列；去别的线程的本地队列里偷一半；都没有就睡。偷的时候锁上对方拿走一半，放开，再锁上自己放进去，任何时候都不同时拿两把队列锁。

叫醒：往空格子里放不叫醒任何线程；往本地队列或全局队列里放时，只有没线程在找活才叫醒一根，找到活的那根再叫醒下一根。活放在本地队列里时，不丢唤醒靠一对 `seq_cst` 屏障加睡前把所有队列再查一遍。

一根系统线程：等 I/O（epoll / kqueue / IOCP，最多等到最近的定时器）、跑定时器、监控。监控只在有工作线程忙时每 1 ms 查一次（占一个核的约 1%）：

- 一根线程这 1 ms 一根协程都没跑完，就把它格子里的协程挪进全局队列；
- 一根线程在同一根协程里待了超过 10 ms、还有活等着，就补一根工作线程，多出来的闲下来再退；
- 有活没人干、又没线程在找活，就兜底叫醒一根。

依据（2026-10-21，WSL2，i7-12700，8 根工作线程）：原型里协程用整数代替，同场比较几种队列，带锁的本地队列比最快的无锁写法（Go 式环）慢不到一成，比只有格子快一到两个数量级（很多协程同时就绪时）。另做了一个真协程原型（换栈用上一版的汇编），和上一版、Go 1.24.5 同场：让出和经 channel 来回传消息比上一版快约 1.6 倍、比 Go 快 2.5 到 5 倍；起协程和「一次叫醒 64 根」落后，前者是原型的控制块用了 glibc 的 `malloc`，后者是一次只叫醒一根找活的线程、起步慢。

第一步写调度器时一起处理这两处：控制块每根线程手边留一批，别的线程释放时还回去；一次叫醒一批时的起步，在真实现里量了再定。

### 4.2 `cu::coroutine`

会用 `std::thread` 就会用它，行为一样：

- 构造时传入可调用对象和参数，参数按值拷（或移动）进协程，成员函数指针配对象或指针也行，要传引用用 `std::ref`；构造完就开始排队跑。
- `join()` 等它跑完：在协程里调，挂起当前协程，线程去跑别的；在普通线程上调，阻塞这根线程。`detach()` 放手，协程跑完自己清理，进程退出时还没跑完的随进程结束。
- 析构或被移动赋值时还能 join，进程终止；协程已经跑完、只是没 join，也算还能 join。
- 协程函数里漏出的异常走 `std::terminate`。
- 另有 `joinable()`、`get_id()`、`swap()`；`id` 可以比较、做 `std::hash` 的键、用 `<<` 输出。
- `cu::this_coroutine` 有 `get_id()`、`yield()`、`sleep_for()`、`sleep_until()`。不在协程里调用时，`get_id()` 返回空 id，其余三个等同于 `std::this_thread` 的同名函数。

和 `std::thread` 不一样的只有三处：

- `std::thread` 抛 `system_error` 的几种误用（对不能 join 的对象调 `join()` 或 `detach()`、协程 join 它自己、内存不够起不了协程），这里打印诊断后终止，因为公共头文件不抛异常。
- 析构或移动赋值时还能 join，`std::thread` 直接调 `std::terminate`，这里先打印一句诊断再终止。两边退出码都是 134。
- 没有 `native_handle()` 和 `hardware_concurrency()`：协程没有系统句柄，核数照样用 `std::thread::hardware_concurrency()` 查。

2026-10-21 在原型上验证过（Linux，GCC 11.4 `-std=c++11` 和 `-std=c++17`，1 根和 8 根工作线程）：函数加参数、成员函数指针、`std::ref`、在普通线程和协程里 join、`detach()`、放进 `vector`、`swap`、`id` 的比较、哈希和输出；四种误用（join 和 detach 不能 join 的对象、协程 join 自己、给还能 join 的对象赋值）、漏出异常、跑完了没 join，都是上面写的结果。原型没有定时器，`sleep_for()` 和 `sleep_until()` 没验证。

### 4.3 错误

- 可能失败的函数返回 `cu::result<T, E>`，`E` 默认是 `cu::error`。库自己的函数一律报 `cu::error`；开发者给自己的代码定义自己的错误类型，在调库的地方换一次。
- `cu::error` 是一个种类加一句消息。种类是库对自己的失败的分类，固定 10 种：unknown、invalid_argument、out_of_range、resource_exhausted、not_found、already_exists、permission_denied、timeout、unsupported、io。系统错误码按一张固定的表换成种类，比如端口被占是 already_exists、句柄用完是 resource_exhausted，表里没有的算 io。
- 造 `cu::error` 只有 `make_error(kind, message)` 一种写法，构造函数是私有的：`error` 也是常用的变量名和 `result` 的成员函数名，`error(...)` 会被它们遮住。
- 消息和诊断都用英文。消息的格式照 Go：`操作 对象: 系统原话`，比如 `open /srv/index.html: No such file or directory`。
- 失败时调 `value()`、成功时调 `error()`，打印诊断后终止，release 也查。开发者自己的错误类型，库不知道怎么打印，诊断里只有一句 `cu::result::value() called on an error`。
- `cu::string_view` 和测试框架（`TEST`、`EXPECT`、`--filter`、`--list`）照搬上一版，只改名字。`defer` 和 `fatal` 只在库内部用。

### 4.4 网络和文件

第一步的接口：

- `cu::net::listen("host:port")` 返回 `listener`，`listener::accept()` 和 `cu::net::connect("host:port")` 返回 `connection`。两个类型分开，用错角色编译不过；都只能移动，析构时关闭。
- 地址写成一个字符串，和 Go 一样。`":8080"` 收所有 IPv4 和 IPv6 地址，`"0.0.0.0:8080"` 只收 IPv4，`"[::]:8080"` 只收 IPv6；端口写 0 由系统挑，用 `local_address()` 查。第一步只认数字 IP，域名解析以后单独加。
- `connection::read(buffer, capacity)` 读到一些就返回，返回 0 表示对端关了。`write(data, size)` 全部写完才算成功，失败时前面可能已经写出去一部分。同一时刻最多一根协程读、一根协程写。
- 会等的调用（accept、connect、read、write）在协程里挂起协程，在普通线程上阻塞这根线程。
- 默认行为照 Go，不留选项：Linux 和 macOS 设 `SO_REUSEADDR`，Windows 不设（设了别的程序能抢走端口）；关掉 Nagle；子进程不继承；写断开的连接不触发 SIGPIPE；监听队列用系统上限；accept 时对端已经断开的，库在内部接着等，句柄用完返回 resource_exhausted，由调用方等一会儿再试。
- `cu::fs::read_file(path)` 把整个文件读进内存，照 Go 的 `os.ReadFile`：按文件大小多分配一个字节，读到它就知道到头了。
- `connect` 的 host 空着、写 `0.0.0.0` 或 `[::]` 时连本机，和 Go 一样。Linux 和 macOS 自己这么做，Windows 不认，库里统一换成环回地址；所以 `connect(server.local_address().to_string())` 在三个平台上都能用。
- 一次读写最多 1 GiB，和 Go 一样：macOS 一次超过 `INT_MAX` 字节报 `EINVAL`，Windows 的长度是 32 位的。调用方看不出区别，`read` 只是读到的少一些，`write` 自己分几次写。
- `read_file` 读目录时三个平台都报 unsupported，消息是 `open <path>: is a directory`（Windows 打开目录报的是拒绝访问）。
- `read_file` 读的时候阻塞所在的工作线程。第一步只有一根工作线程，一次慢读会让所有协程一起等；是交给别的线程读，还是像 Go 那样阻塞时把工作线程让出去，到多工作线程那一步再定。
- Windows 上 Winsock 起不来、拿不到 AcceptEx 和 ConnectEx 时打印诊断后终止，和建不了完成端口一样：支持的系统上不会发生。
- Windows 上连一个没人监听的本机端口，要约 2 秒才报错（系统收到 RST 以后还会重发 SYN），Linux 和 macOS 立刻报。这是系统的行为，库不改。
- 超时、从别的协程关掉正在等的句柄（优雅退出要用）、域名解析和 UDP，各放到后面的一步。超时用 Go 的截止时刻还是上一版的每次调用传时长，到那一步再定。

依据：读过 Go 1.24.5（net、internal/poll、os）、Rust 标准库（std::net、fs）和 PhotonLibOS（net）的源码。2026-10-21 在 Linux 原型上（epoll，一根工作线程）跑过第一步的 serve：curl 和 1000 个请求（50 个同时）全部 200；端口被占、文件不存在、权限不够、写域名、连不上，消息和种类都对；`":8082"` 用 IPv4 和 IPv6 都能连上。

## 5. 模块和顺序

下层不依赖上层。

| 层 | 模块 | 第一版 serve 用不用 |
| --- | --- | --- |
| 基础 | result 与错误、string_view、optional、defer、fatal、strings、lexical_cast | 用，只做用得到的部分 |
| 测试 | `TEST` / `EXPECT` | 用，第一天就要有 |
| 平台 | os（停止信号、环境变量）、time（时钟、HTTP 日期） | 用 |
| 运行时 | 换栈、栈池、调度器、定时器、I/O 引擎、mutex / condition_variable、`cu::coroutine` | 用 |
| I/O | net（TCP）、fs（打开、读、查询、路径） | 用 |
| 上层 | log、flag | 用 |
| 以后再说 | term、config、bytes、UDP、channel、自己的 malloc、目录遍历 | 等第二个参考程序，或者真有需要时 |

顺序是先打通一条最细的路，再一层层加厚：

1. 在三个平台上跑通「一根工作线程 + TCP + 只会返回一个文件的 serve」。Windows 的换栈和 IOCP 在这一步就要有。
2. 之后每一步只加一样东西，比如多线程和偷任务、超时、真正的文件服务、日志、优雅退出。加什么由 serve 的需要来定；每一步都在三个平台的 CI 上跑通。

## 7. 考虑过、没有选的

| 选项 | 为什么没选 | 什么条件下重开 |
| --- | --- | --- |
| 在上一版的代码上接着改 | 机制之间开始互相打补丁，难查的 bug 都出在新加的机制上。从空目录重来，每个机制都重新问一次为什么需要 | — |
| 无栈协程（C++20 的 `co_await`） | 写法会传染：会挂起的函数都得写成协程，普通函数和第三方库的回调里不能挂起；引用参数和 lambda 捕获有生命周期的坑。好处是每根协程只占它的帧（演示里 216 字节），也没有栈带来的平台问题 | 每根协程占的内存成了实际问题时 |
| 共享栈 | 挂起期间，指向局部变量的指针不能交给别人用；协程不能换线程；切换时要拷栈 | 不重开 |
| 像 Go 那样会长的栈 | 要编译器配合，C++ 做不到 | 不重开 |
| C++17 或 C++20 | C++11 能编的系统最多。代价是 string_view、optional 要自己写，公共类型的定义不能随使用方的标准变 | 出现必须用新标准才能写的东西时 |
| release 构建不设保护页 | 栈溢出时会悄悄写坏别的协程的栈 | 不重开 |
| 保护页用 `MADV_GUARD_INSTALL`，不多占映射 | 6.13 以下的内核没有，要多一条代码路径 | 最低支持的 Linux 内核到 6.13 时，同时去掉 3.2 万根的上限 |
| 栈 256 KiB | 每根协程的页表少 1.5 KiB，但能递归的深度少了四倍 | 页表占的内存成了实际问题时 |
| 每根线程一个调度器，协程不换线程 | 一根协程阻塞或者长时间计算，同一线程上的协程都得等；阻塞调用要交给线程池，用起来不像线程 | 不重开 |
| 只有一个带锁的全局队列 | 8 根线程时两根协程来回传消息掉到每秒约 6 万次：协程一放进去就叫醒一根睡着的线程，被它抢走，每次都换线程 | 不重开 |
| 全局队列加格子，没有本地队列 | 很多协程同时就绪时，每次都过全局锁，每调度一次约 380 ns，带本地队列约 20 ns | 不重开 |
| 中心分派：一根调度线程把每根协程分给闲着的工作线程 | 每次调度至少两次线程叫醒，来回传消息每秒约 4 万次；做成无锁（MPSC 加收件格）也一样，慢在叫醒不在锁；调度线程被系统晚调度时所有协程一起停 | 不重开 |
| BEAM 式：每线程队列，由一根线程定期算迁移计划，各线程照着搬 | 比偷一半多一套计划和搬运；没有长期负载不均衡的场景时看不出收益 | 参考程序出现长期负载不均衡时 |
| 无锁本地队列：Go 式（一个放、多个取）、PhotonLibOS 的 MPMC 环和批量 MPMC 环 | 最快的 Go 式只比带锁队列快不到一成，Photon 的两种不比它快；多一份要写对、要压测的无锁代码；Photon 的两种在占了位的线程被切走时别人要等 | 带锁队列在参考程序里成了瓶颈时；先在实验里做 |
| PhotonLibOS 的非对称自旋锁 | 照抄原样，主人和偷的线程会同时进锁（压力测试里主人加锁 2000 万次，同时在锁里几千到几万次），原因是存和读之间没有完整屏障；加了 `seq_cst` 屏障就不再出现，但也不比普通自旋锁快 | 不重开 |
| 8 个独立格子代替本地队列 | 只在很多协程一直有活时有用，一次叫醒一批时帮得不多 | 不重开 |
| 闲线程先空转一会儿再睡 | 只让 8 根线程的来回传消息从每秒约 6 万次提到约 10 万次 | 有数据显示叫醒延迟成了问题时 |
| 只有一个调度线程 | 只用一个核，阻塞调用和重计算都要交给线程池 | 不重开 |
