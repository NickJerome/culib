# 运行时

- 日期：2026-10-21
- 代码：`include/cu/coroutine.h`，`src/runtime/`，`src/platform/cpu_count*`

## 1. 做什么

协程和跑协程的线程：

- `cu::coroutine` 起协程、等它跑完，行为照 `std::thread`（路线图 4.2）。
- 几根工作线程跑协程，协程可以换线程（路线图 4.1）。
- 一根系统线程等 I/O 事件，跑定时器，顺带看着工作线程（监控）。
- 协程栈：每根 1 MiB，保护页一直开着。

## 2. 接口

| 分类 | 签名 | 说明 |
| --- | --- | --- |
| 起和等 | `coroutine(F&& f, Args&&... args)` | 参数按值拷进协程，构造完就开始排队跑 |
| | `void join()` / `void detach()` / `bool joinable() const` | 和 `std::thread` 一样 |
| | `id get_id() const` / `void swap(coroutine&)` | `id` 能比较、做哈希键、用 `<<` 输出 |
| 当前协程 | `this_coroutine::get_id()` | 不在协程里返回空 id |
| | `this_coroutine::yield()` | 排到本线程本地队列的末尾；不在协程里等于 `std::this_thread::yield()` |
| | `this_coroutine::sleep_for(duration)` / `sleep_until(time_point)` | 挂起当前协程，到点由系统线程叫醒，只保证不早醒；不在协程里等于 `std::this_thread` 的同名函数 |

用的时候要知道的三件事，都写在头文件里：

- 协程挂起以后可能在另一根线程上接着跑，`thread_local` 变量和 `std::this_thread::get_id()` 不要跨挂起点用。
- 协程里可以调会阻塞线程的函数，也可以一直算：排在后面的协程会被别的线程接走，都忙时运行时补一根线程。
- 不能在 catch 块里挂起，真的要等时打印诊断后终止。

## 3. 取舍

### 代码怎么分

每块只管自己的状态，对外只露几个函数；上层用下层，反过来不行。

| 层 | 文件 | 管什么 |
| --- | --- | --- |
| 入口 | `scheduler.h/.cpp` | 对外的几个函数：排进就绪、挂起、叫醒、让出、睡 |
| | `system_thread.h/.cpp` | 系统线程的循环，三个平台共用：定时器、攒批、监控、等 I/O |
| 装配 | `runtime.h/.cpp` | 全进程一份：全局队列、线程池、监控 |
| 线程 | `worker.h/.cpp` | 一根工作线程：取活、跑协程，没活时去睡 |
| | `thread_pool.h/.cpp` | 工作线程有几根、谁在睡、该叫醒谁；补线程和多余的退出 |
| | `monitor.h/.cpp` | 每 1 ms 看一遍工作线程 |
| 协议 | `park.h` | 挂起和叫醒的握手 |
| | `context_switch.h/.cpp` | 切进、切出一根协程，协程的第一帧 |
| 数据结构 | `coroutine_list.h` | 一串协程，不加锁 |
| | `run_queue.h` | 就绪队列：一串协程加一把自旋锁；本地队列和全局队列都是它 |
| | `stack.h/.cpp` | 协程栈和栈的缓存，含每根线程手边的 16 根 |
| | `timer.h/.cpp` | 定时器堆 |
| 平台 | `io_*.cpp`、`stack_*.cpp`、`asm/` | 事件引擎（每次等一次 I/O）、栈的映射、换栈的汇编 |

唯一的互相引用是偷任务带来的：`worker` 偷活时要经线程池找到别的 `worker`。

### 线程数

平时开「进程能用的核数」根工作线程：Linux 上是亲和性允许的核数，再和容器的 CPU 配额（`/sys/fs/cgroup` 下的 `cpu.max`，或 v1 的两个文件）比，取小的；配额向上取整，不到 2 个核按 2 个算，和 Go 1.25 一样。macOS 和 Windows 用 `std::thread::hardware_concurrency()`。没有配置项。

### 队列、取活和叫醒

照路线图 4.1。实现时定下的几处：

- 本地队列和全局队列是同一种 `run_queue`：一串协程（`coroutine_list`，用控制块里的 `next` 串起来）加一把自旋锁，不限长。偷的时候锁上对方拿走一半（向上取整，最多 128 根），放开，再锁上自己放进去。
- 从全局队列取的时候一次取一批：每根活着的线程分一份再多拿一根，最多 128 根，多的放进自己的本地队列，Go 的 `globrunqget` 也这么取。每 61 次先看一眼全局队列时只取一根。
- 让出的协程排到本地队列末尾，不叫醒别的线程：这根线程接着就会取。其他线程都闲着时，监控连着两次看到「有活没人干」就叫醒一根来偷，所以一群一直让出的协程最多晚 2 ms 分到别的线程上。
- 闲着的线程各睡在自己的条件变量上，叫醒时取最后睡下的那根。
- 找活的线程找到了，而它是最后一根在找的，就再叫醒一根。

### 监控

在系统线程上，有工作线程忙时每 1 ms 看一遍，都闲着时一直睡；工作线程从闲着变成忙时，由它自己叫醒监控：

- 一根线程这一个间隔里一根协程都没跑完，把它「下一根」格子里的协程挪进全局队列；
- 有线程在同一根协程里待了 10 ms 以上、还有活排着、又没有闲着的线程，就补一根。补的线程总数不超过 256；卡住的线程恢复以后，多出来的线程闲下来就退出，但不少于平时的根数；
- 有活没人干、又没线程在找活，连着两次看到就叫醒一根。

C++ 分不出阻塞的系统调用和一直在算，两种都会补线程。所以 `fs::read_file` 这类会阻塞线程的调用不另做处理，路线图 4.4 留到这一步定的事就这么定了。

Windows 上系统线程的超时按系统节拍到期，默认约 15.6 ms，所以另用一个高精度定时器，经「等待完成包」接到完成端口上，到点时端口里多一个包（Go 也这么做）。定时器只在上一次的包取回来以后才重设，I/O 多的时候不用每取一批完成包都多三次系统调用。

### 定时器

- 定时器放在等它的协程的栈上，堆里只存它的时刻和指针：比较只读堆的数组，不去碰散在各协程栈上的定时器。堆是 4 叉的。
- 堆分成 16 份，每根线程固定往其中一份里放，各有一把自旋锁，工作线程之间不抢同一把锁。
- 系统线程每一轮先叫醒所有到点的定时器，再等 I/O，等到下一个定时器、下一次监控和 I/O 事件里最早的那个。这个循环在 `system_thread.cpp`，三个平台共用；等一次 I/O 的那一步（`io_poll`）由各平台的事件引擎实现。新放的定时器成了它那一份里最早的，就叫醒系统线程重新算。
- 系统线程叫醒的协程（到点的、等到 I/O 的）先攒成一批，这一轮处理完再一起排进全局队列，只拿一次锁、只看一次要不要叫醒工作线程。
- 精度：Linux 上 `epoll_wait` 的超时按毫秒向上取整，macOS 的 `kevent` 精确到纳秒，Windows 用监控那个高精度定时器。

### 栈

全局缓存留 64 根，每根工作线程手边再留 16 根：跑完的协程把栈还到手边，下一根先从手边拿。

### catch 块

挂起之前查一次 `std::current_exception()`，在 catch 块里就终止，见路线图 4.2。

## 4. 测量

几处取舍的依据：

| 问题 | 量到的 | 怎么定的 |
| --- | --- | --- |
| 本地队列用锁 | 只有 1 根工作线程时，同一份代码去掉锁，让出从 32 ns 降到 22 ns（数组环那一版量的） | 照 4.1 留着锁：比 Go 快 4 倍，参考程序里还没看到它成为瓶颈 |
| 本地队列用链表还是 256 格的数组环 | 8 根工作线程时，1000 根一起让出 23 → 12 ns，起协程 155 → 180 ns；1 根时，1000 根一起让出 49 → 59 ns；让出、来回传消息、一次叫醒 64 根、1 万根睡眠、serve 都看不出差别 | 作者定：链表，和全局队列同一种 |
| 全局栈缓存一把锁 | 8 根线程起协程 365 ns（只有 1 根时 141 ns），手边留 16 根栈以后 185 ns | 手边留栈 |
| 全局队列一根一根取 | 8 根线程起协程 191 ns、CPU 0.30 s；一次取一批以后 151 ns、0.10 s，和 Go 一样；1 万根各睡 100 次，每睡一次 1.3 µs 降到 0.9 µs。让出、来回传消息、一次叫醒 64 根没有变化 | 一次取一批 |
| 定时器堆只存指针，一个堆一把锁 | 1 万根各睡 100 次，每睡一次 5.0 µs：取堆顶往下比较时次次去读别的协程栈上的时刻，工作线程转着等这把锁。时刻放进堆的数组、改 4 叉以后 2.1 µs，叫醒的协程攒批 1.5 µs，堆分 16 份 1.3 µs | 照现在的写法 |
| 系统线程攒的一批满 64 根就先放 | 墙上时间快 1.5%，CPU 多 10% | 不做，一轮处理完再放 |
| Linux 上用 `epoll_pwait2` 精确到纳秒 | `sleep_for(1ms)` 中位 1.16 ms 降到 1.10 ms，1 万根各睡 100 次的墙上时间 1.26 s 降到 1.19 s；每睡一次多 0.1 µs CPU（系统线程醒得勤了），还要给老内核留一条路 | 不做 |
| 监控每 1 ms 一查 | 一根协程卡在系统调用里 5 秒，Linux 上监控用掉 57 ms CPU，Windows 上 65 ms，约单核的 1%；都闲着时 5 秒用 0.2 ms | 照 4.1 |
| 卡住的线程格子里的协程 | 8 根时约 1.5 ms 后在别的线程上跑起来（20 次里最长 2.2 ms）；只有 1 根时约 11 ms（判定卡住 10 ms，再补一根线程） | 照 4.1 |
| Windows 上等 1 ms | 直接设超时等了 15.5 ms，高精度定时器加等待完成包 1.5 ms，高精度定时器配 APC 不触发 | 等待完成包 |
| catch 块检查 | 每次挂起 GCC 2.4 ns，MSVC 16 ns | 查 |
| 换栈的 `resume`、`suspend` 和 `worker::run` 一定内联 | 拆成几个文件以后它们各成了一层函数，让出从 32 ns 涨到 44 ns，来回传消息从 100 ns 涨到 120 ns；切到另一根栈以后，每往回返回一层，CPU 就猜错一次返回地址。一定内联以后回到 32 ns 和 102 ns | 一定内联（`CU_DETAIL_ALWAYS_INLINE`） |
| 栈 1 MiB | 挂起的协程每根 6.2 KiB，其中 2 KiB 是页表；256 KiB 时 4.7 KiB，64 KiB 时 4.3 KiB，那一页栈省不掉 | 作者定：维持 1 MiB |

同时活着的协程多时，栈的映射和释放很贵：1 万根各挂起一次，起来时内核态 CPU Linux 145 到 185 ms、Windows 300 到 750 ms，全部结束时 Linux 400 到 460 ms、Windows 约 1000 ms。栈缓存只留 64 根、每根工作线程手边 16 根，多出来的每根都单独映射、单独还给系统，还的时候系统要让各个核刷新 TLB。上面「各睡 100 次」在 Windows 上的 2.5 µs 多半是这个。留到自己的分配器那一步和栈池一起做。

serve 在压力下（每个请求一条新连接，4 个 ab 同时压，serve 限在 0-7 号核上，几个版本轮换先后各跑 3 轮）：

| | 一根工作线程（`b8bc921`） | 现在 | Go 写的同样的程序 |
| --- | --- | --- | --- |
| 每秒请求数 | 6.1 到 6.4 万 | 10.2 到 12.5 万 | 12.4 到 12.8 万 |
| p50 / p99（ab 只给整毫秒） | ≤2 / ≤3 ms | ≤1 / ≤2 ms | ≤1 / ≤2 ms |

## 5. 不做的事

| 不做 | 为什么 | 什么条件下重开 |
| --- | --- | --- |
| 无锁本地队列 | 见路线图第 7 节；这里量到锁在让出上占约 10 ns | 参考程序里本地队列的锁成了瓶颈时 |
| 分清阻塞和计算，只给阻塞的线程补线程 | 要看每根线程实际用了多少 CPU 时间，三个平台各一份代码；一直算的协程多时线程会多到 256 根，由系统分时 | 参考程序因为线程太多吃亏时 |
| 闲线程先空转一会儿再睡 | 见路线图第 7 节；serve 每个请求因此多 2 次 futex 调用、1 到 5 µs CPU | 有数据显示叫醒延迟或叫醒的 CPU 成了问题时 |
| 按 `/proc/self/cgroup` 找本进程所在的 cgroup | 容器里 `/sys/fs/cgroup` 就是容器自己那一层；宿主上 systemd 给服务设的 `CPUQuota=` 看不到 | 要在宿主上用 systemd 限核部署时 |
| Windows 上看进程亲和性和作业对象的 CPU 上限 | 没有这样部署的需要 | 要在受限的作业对象里跑时 |
| 控制块缓存：每根线程手边留一批控制块，别的线程释放时还回去 | 路线图 4.1 原来定了要做。实测 malloc 只占起协程的 25 到 30 ns：换成只分不还的分配（缓存能做到的上限），8 根线程时 177 ns 降到 152 ns，CPU 0.28 s 降到 0.24 s；比 Go 多出的 CPU 主要是几根线程抢着偷几乎不干活的协程，后来全局队列一次取一批，这部分 CPU 已经和 Go 一样。serve 每个请求约 30 µs，控制块分配占不到 0.1% | 起协程的开销在参考程序里量得出来时 |
| Linux 上用 `epoll_pwait2` 让定时器精确到纳秒 | 见上面第 4 节：定时器准一些，每睡一次多 0.1 µs CPU | 要亚毫秒的定时器时 |

## 6. 测了什么

- `tests/coroutine_test.cpp`：`std::thread` 的那些行为；`sleep_for` 睡够时长、睡到过去的时刻立刻返回、睡着时同一根线程上别的协程照跑、按时刻先后醒、普通线程上等于 `std::this_thread`。`tests/scheduler_test.cpp`：一直不让出的协程不挡别的协程；阻塞在系统调用里的协程不挡它刚起的那根（格子里的）；协程分到几根线程上；64 根协程各 300 次跨线程 join；4 根普通线程和协程互相等；1000 根协程一起睡到同一刻，一根都不早醒。`tests/fault/`：误用、栈溢出、在 catch 块里挂起。
- 反向验证过：去掉监控挪格子那一步，「不挡刚起的那根」失败；用 `taskset -c 0` 限在一个核上、去掉补线程，三条失败（不让出的那条 10 秒后放弃）。
- `tests/run_queue_test.cpp`：一串协程和就绪队列的先后次序；4 根线程放、4 根线程一根一根或者一批一批地取，每根协程恰好出来一次。`tests/park_test.cpp`：挂起和叫醒的握手，叫醒在挂起之前、途中、之后三种先后。
- 本机：Linux GCC debug / release、ASan + UBSan、Clang 14 的 TSan（多核 5 遍、单核 2 遍，0 条警告）；Windows MSVC debug / release、MSYS2 UCRT64 的 MinGW；GCC 4.8 和 macOS（照 SDK 抄的头文件桩）只做了类型检查。
- 没测：macOS 上的运行（只有 CI）；8 根以上工作线程；容器限核时的行为；补到很多线程时的内存。
