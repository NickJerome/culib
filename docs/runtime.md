# 运行时

- 日期：2026-10-22
- 代码：`include/cu/coroutine.h`、`include/cu/sync.h`，`src/runtime/`，`src/platform/` 里的 `cpu_count*`、`memory*`、`thread_stack*`

## 1. 做什么

协程和跑协程的线程：

- `cu::coroutine` 起协程、等它跑完，行为照 `std::thread`（路线图 4.2）。
- 几根工作线程跑协程，协程可以换线程（路线图 4.1）。
- 一根系统线程等 I/O 事件，跑定时器，顺带看着工作线程（监控）。
- 协程栈：每根 1 MiB，保护页一直开着。跑完的栈留着给下一根协程用，高峰过去才还给系统。
- `cu::mutex`、`cu::condition_variable`：行为照 `std::mutex`、`std::condition_variable`，协程和普通线程都能用（路线图 4.5）。

## 2. 接口

| 分类 | 签名 | 说明 |
| --- | --- | --- |
| 起和等 | `coroutine(F&& f, Args&&... args)` | 参数按值拷进协程，构造完就开始排队跑 |
| | `void join()` / `void detach()` / `bool joinable() const` | 和 `std::thread` 一样 |
| | `id get_id() const` / `void swap(coroutine&)` | `id` 能比较、做哈希键、用 `<<` 输出 |
| 当前协程 | `this_coroutine::get_id()` | 不在协程里返回空 id |
| | `this_coroutine::yield()` | 排到本线程本地队列的末尾；不在协程里等于 `std::this_thread::yield()` |
| | `this_coroutine::sleep_for(duration)` / `sleep_until(time_point)` | 挂起当前协程，到点由系统线程叫醒，只保证不早醒；不在协程里等于 `std::this_thread` 的同名函数 |
| 互斥量 | `cu::mutex`：`lock()` / `try_lock()` / `unlock()` | 满足 Lockable，配 `std::lock_guard`、`std::unique_lock`；拿着它可以挂起，换了线程再放 |
| 条件变量 | `cu::condition_variable`：`notify_one()` / `notify_all()` | |
| | `wait(lock)`、`wait_for(lock, rel_time)`、`wait_until(lock, abs_time)`，各有带条件的重载 | 配 `std::unique_lock<cu::mutex>`，返回值和 `std::condition_variable` 的一样 |

用的时候要知道的三件事，都写在头文件里：

- 协程挂起以后可能在另一根线程上接着跑，`thread_local` 变量和 `std::this_thread::get_id()` 不要跨挂起点用。
- 协程里可以调会阻塞线程的函数，也可以一直算：排在后面的协程会被别的线程接走，都忙时运行时补一根线程。
- 不能在 catch 块里挂起，真的要等时打印诊断后终止。

## 3. 取舍

### 代码怎么分

每块只管自己的状态，对外只露几个函数；上层用下层，反过来不行。

| 层 | 文件 | 管什么 |
| --- | --- | --- |
| 公共接口 | `coroutine.cpp`、`sync.cpp` | `cu::coroutine`、`cu::mutex`、`cu::condition_variable` 背后的函数 |
| 入口 | `scheduler.h/.cpp` | 对外的几个函数：排进就绪、挂起、叫醒、让出、睡 |
| | `system_thread.h/.cpp` | 系统线程的循环，三个平台共用：定时器、攒批、监控、等 I/O |
| 装配 | `runtime.h/.cpp` | 全进程一份：全局队列、线程池、监控 |
| 线程 | `worker.h/.cpp` | 一根工作线程：取活、跑协程，没活时去睡 |
| | `thread_pool.h/.cpp` | 工作线程有几根、谁在睡、该叫醒谁；补线程和多余的退出 |
| | `monitor.h/.cpp` | 每 1 ms 看一遍工作线程 |
| 协议 | `park.h` | 挂起和叫醒的握手 |
| | `context_switch.h/.cpp` | 切进、切出一根协程，协程的第一帧 |
| 数据结构 | `coroutine_list.h` | 一串协程，不加锁 |
| | `run_queue.h` | 就绪队列：一串协程加一把自旋锁；本地队列和全局队列都是它 |
| | `stack.h/.cpp` | 协程栈：空闲表、每根工作线程手边的 16 根，闲了还给系统 |
| | `timer.h/.cpp` | 定时器堆 |
| 平台 | `io_*.cpp`、`asm/` | 事件引擎（每次等一次 I/O）、换栈的汇编 |
| | `src/platform/memory_*`、`thread_stack_*` | 按页保留地址、提交、还地址；Windows 上栈按需往下提交 |

唯一的互相引用是偷任务带来的：`worker` 偷活时要经线程池找到别的 `worker`。

### 线程数

平时开「进程能用的核数」根工作线程：Linux 上是亲和性允许的核数，再和容器的 CPU 配额（`/sys/fs/cgroup` 下的 `cpu.max`，或 v1 的两个文件）比，取小的；配额向上取整，不到 2 个核按 2 个算，和 Go 1.25 一样。macOS 和 Windows 用 `std::thread::hardware_concurrency()`。没有配置项。

### 队列、取活和叫醒

照路线图 4.1。实现时定下的几处：

- 本地队列和全局队列是同一种 `run_queue`：一串协程（`coroutine_list`，用控制块里的 `next` 串起来）加一把自旋锁，不限长。偷的时候锁上对方拿走一半（向上取整，最多 128 根），放开，再锁上自己放进去。
- 从全局队列取的时候一次取一批：每根活着的线程分一份再多拿一根，最多 128 根，多的放进自己的本地队列，Go 的 `globrunqget` 也这么取。每 61 次先看一眼全局队列时只取一根。
- 让出的协程排到本地队列末尾，不叫醒别的线程：这根线程接着就会取。其他线程都闲着时，监控连着两次看到「有活没人干」就叫醒一根来偷，所以一群一直让出的协程最多晚 2 ms 分到别的线程上。
- 闲着的线程各睡在自己的条件变量上，叫醒时取最后睡下的那根。
- 找活的线程找到了，而它是最后一根在找的，就再叫醒一根。

### 监控

在系统线程上，有工作线程忙时每 1 ms 看一遍，都闲着时一直睡；工作线程从闲着变成忙时，由它自己叫醒监控：

- 一根线程这一个间隔里一根协程都没跑完，把它「下一根」格子里的协程挪进全局队列；
- 有线程在同一根协程里待了 10 ms 以上、还有活排着、又没有闲着的线程，就补一根。补的线程总数不超过 256；卡住的线程恢复以后，多出来的线程闲下来就退出，但不少于平时的根数；
- 有活没人干、又没线程在找活，连着两次看到就叫醒一根。

C++ 分不出阻塞的系统调用和一直在算，两种都会补线程。所以 `fs::read_file` 这类会阻塞线程的调用不另做处理，路线图 4.4 留到这一步定的事就这么定了。

Windows 上系统线程的超时按系统节拍到期，默认约 15.6 ms，所以另用一个高精度定时器，经「等待完成包」接到完成端口上，到点时端口里多一个包（Go 也这么做）。定时器只在上一次的包取回来以后才重设，I/O 多的时候不用每取一批完成包都多三次系统调用。

### 定时器

- 定时器放在等它的协程的栈上，堆里只存它的时刻和指针：比较只读堆的数组，不去碰散在各协程栈上的定时器。堆是 4 叉的。
- 堆分成 16 份，每根线程固定往其中一份里放，各有一把自旋锁，工作线程之间不抢同一把锁。
- 系统线程每一轮先叫醒所有到点的定时器，再等 I/O，等到下一个定时器、下一次监控和 I/O 事件里最早的那个。这个循环在 `system_thread.cpp`，三个平台共用；等一次 I/O 的那一步（`io_poll`）由各平台的事件引擎实现。新放的定时器成了它那一份里最早的，就叫醒系统线程重新算。
- 系统线程叫醒的协程（到点的、等到 I/O 的）先攒成一批，这一轮处理完再一起排进全局队列，只拿一次锁、只看一次要不要叫醒工作线程。
- 精度：Linux 上 `epoll_wait` 的超时按毫秒向上取整，macOS 的 `kevent` 精确到纳秒，Windows 用监控那个高精度定时器。

### 栈

- 每根栈单独向系统要 1 MiB 地址，可用的部分提交，最底下 16 KiB 不提交，碰到就崩溃。
- 跑完的协程把栈还到这根工作线程手边（最多 16 根），手边满了还到全进程的空闲表。拿的时候先拿手边的，再拿空闲表里最后还回来的那根。
- 空闲表空了才向系统要新的，要的时候拿着空闲表的锁：很多线程同时进内核要地址，比在这把锁上排队还慢。
- 空闲表比 64 根多时，闲了 1 秒的那些整根还给系统，地址和页表一起还。这件事由系统线程上的一个定时器来做，一批最多 1 ms，批与批之间隔 10 ms，不让定时器和 I/O 晚太久。
- 和系统打交道的只有几个调用，在 `src/platform/`：`memory_*` 按页保留地址、提交、还地址，`thread_stack_*` 管 Windows 上栈按需往下提交和线程块里的栈界。栈池本身三个平台一份代码。

### 互斥量和条件变量

- 等的一方在自己的栈上放一条等待记录，排进对象的队列；叫醒的一方拿着对象的自旋锁把它摘下来，放了锁再叫醒。谁摘下来谁叫醒，所以排一次队恰好醒一次。等的时候不分配内存。
- 放锁时叫醒排在最前面的那根，它醒来和刚来的一起抢；它回来之前，再放锁也不叫第二根（Go 的 `mutexWoken`），放锁的多半马上又拿，叫多了是白醒。它抢输了就回到队首，下一次放锁直接把锁交给它，刚来的抢不到。作者定的，几种做法的对比见第 4 节。
- 限时等照路线图 4.4 定的做法，给这次等待配一个定时器：协程在栈上放一个定时器，到点时系统线程把它从队列里摘下来、记成到点、叫醒它。先被通知的话，它自己把定时器从堆里拿掉；已经拿不掉（系统线程正在跑它），就等它跑完再返回。普通线程用 `std::condition_variable` 的限时等，到点自己去队列里摘。
- 和 std 不一样的：可以拿着锁挂起，醒来换了线程再放；放一把没拿着的锁、拿没锁住的 `unique_lock` 去等，打印诊断后终止（std 是未定义行为）。和挂起一样，在 catch 块里要等（锁被人拿着、`wait`）时终止。
- 两个类型各 24 字节（`std::mutex` 在 Linux 上 40 字节、Windows 上 80 字节；`std::condition_variable` 48 和 72 字节）。构造函数是 constexpr，静态的对象不在 `main` 之前跑代码；析构函数是平凡的，销毁时还有人在等不查，和 std 一样是未定义行为。

栈池以前慢在两处：每根跑完立刻还给系统，以及很多线程同时进内核要地址。单独量后一处：Windows 上 20 根线程同时各要 500 根栈，CPU 450 到 875 ms，一根线程要 1 万根只要 16 到 31 ms，先拿一把锁再要是 109 到 125 ms；Linux 上 8 根线程同时要 156 到 212 ms，排队 100 到 116 ms，一根线程 26 到 29 ms。还一根栈 Linux 平均 2.8 到 3.9 µs，最长一次 1.7 ms；Windows 平均 2.5 到 2.7 µs，最长一次 0.15 ms。

调度器那五项也在栈池前后同场比过：起协程 8 根线程时 178 → 184 ns，1 根时 128 → 136 ns，两边都把函数按 64 字节对齐以后是 175 对 176 ns、137.5 对 137 ns，差别来自代码对齐；让出、来回传消息、一次叫醒 64 根没有变化，1000 根一起让出 11 → 8 ns。

serve 在压力下（每个请求一条新连接，4 个 ab 同时压，serve 限在 0-7 号核上，几个版本轮换先后各跑 3 轮）：

| | 一根工作线程（`b8bc921`） | 现在 | Go 写的同样的程序 |
| --- | --- | --- | --- |
| 每秒请求数 | 6.1 到 6.4 万 | 10.2 到 12.5 万 | 12.4 到 12.8 万 |
| p50 / p99（ab 只给整毫秒） | ≤2 / ≤3 ms | ≤1 / ≤2 ms | ≤1 / ≤2 ms |
| 每个请求的 CPU | 28 µs | 29 到 33 µs | 32 到 34 µs |
| 每个请求的 futex 调用（strace 数的，`43d5dec`） | 1.2 次 | 3.4 次 | — |

一根工作线程到多根，每个请求多出来的 CPU 是线程睡下和叫醒：epoll 和 close 两边一样多，accept4 改前多出来的是 EAGAIN 以后的重试。Go 写的同样的程序每个连接一根 goroutine，读到空行，回同一份响应，关连接；和它比在路线图第 2 节的护栏以内。

`cu::mutex`、`cu::condition_variable` 和 Go 的 `sync.Mutex`、`sync.Cond` 同场比（2026-10-22，5 轮中位数）：

| 项目 | v2（Linux，8 根） | Go（Linux） | v2（Windows，20 根） | Go（Windows） |
| --- | --- | --- | --- | --- |
| 拿放一把没人抢的锁 | 12.0 ns（0.12 s） | 11.3 ns（0.11 s） | 13.6 ns（0.14 s） | 10.8 ns（0.11 s） |
| 8 根协程各拿放 20 万次同一把锁，每次 | 12.5 ns（0.02 s） | 33 ns（0.15 s） | 11.8 ns（0.03 s） | 41 ns（0.39 s） |
| 两根协程用锁和条件变量轮流，每个来回 | 144 ns（0.03 s） | 273 ns（0.06 s） | 174 ns（0.05 s） | 430 ns（0.14 s） |
| 1 万根排在一把锁上，放开到全部拿过一次 | 3.2 ms（0.13 s） | 3.5 ms（0.04 s） | 3.9 ms（0.12 s） | 4.5 ms（0.12 s） |
| 1 万根等在条件变量上，`notify_all` 到全部结束 | 6.5 ms（0.14 s） | 3.7 ms（0.04 s） | 8.0 ms（0.14 s） | 2.5 ms（0.08 s） |
| 其中 `notify_all` 本身（各跑 3 遍） | 3.9 到 4.3 ms | 1.0 到 2.3 ms | 3.4 到 3.7 ms | 0.5 ms |
| 8 根协程抢 0.5 s、每次拿着锁算 1 µs，单次拿锁最久等了 | 16 ms（0.49 s） | 4.8 ms（0.65 s） | 21 ms（0.52 s） | 5.0 ms（0.50 s） |

1 万根那两项括号里的 CPU，大多是第一次起 1 万根协程要新栈，不是锁本身。只有 1 根工作线程时（Linux）：抢一把锁 11.8 ns，Go 12.8 ns；轮流 143 ns，Go 298 ns；1 万根排一把锁 3.2 ms，Go 2.5 ms；`notify_all` 1 万根 6.9 ms，Go 2.8 ms；最久等 59 ms，Go 51 ms。

放锁时怎么交给等的一方，四种做法同场比（Linux，8 根工作线程）：

| 做法 | 8 根协程抢一把锁，每次 | 单次拿锁最久等了 |
| --- | --- | --- |
| 叫醒的和刚来的一起抢，抢输一次，下次放锁直接交给它（现在的） | 12.5 ns | 16 ms |
| 照 Go：从排队算起等满 1 ms 还抢输，才直接交 | 12.1 ns | 16 ms |
| 从不直接交，一直一起抢 | 12.1 ns | 282 ms |
| 有人排着就直接交，先来先得 | 64 ns | 0.3 ms |

比 Go 慢的两处：

- `notify_all` 叫醒一大群：每叫醒一根约 0.35 µs，其中光沿着等待链走一遍就要 1.4 到 1.7 ms（只走不叫醒，量过）。等待记录在各自协程的栈上，相隔 1 MiB，走一步换一页；叫醒每根还有四次原子操作和一道屏障（格子交换、本地队列的锁、看要不要叫醒线程）。
- 一直不挂起的协程抢锁时，等锁的最久要等 16 ms：叫醒的那根进了放锁那根工作线程的格子，这根线程上的协程一直不挂起，格子又不让别的线程偷，要等监控 1 到 2 ms 挪走，排着的每一根都要等一次。Go 闲着的线程会去偷。这是路线图 4.1 定下的取舍，不只是锁的事。

## 5. 不做的事

| 不做 | 为什么 | 什么条件下重开 |
| --- | --- | --- |
| 无锁本地队列 | 见路线图第 7 节；这里量到锁在让出上占约 10 ns | 参考程序里本地队列的锁成了瓶颈时 |
| 分清阻塞和计算，只给阻塞的线程补线程 | 要看每根线程实际用了多少 CPU 时间，三个平台各一份代码；一直算的协程多时线程会多到 256 根，由系统分时 | 参考程序因为线程太多吃亏时 |
| 闲线程先空转一会儿再睡 | 见路线图第 7 节；serve 每个请求因此多 2 次 futex 调用、1 到 5 µs CPU | 有数据显示叫醒延迟或叫醒的 CPU 成了问题时 |
| 按 `/proc/self/cgroup` 找本进程所在的 cgroup | 容器里 `/sys/fs/cgroup` 就是容器自己那一层；宿主上 systemd 给服务设的 `CPUQuota=` 看不到 | 要在宿主上用 systemd 限核部署时 |
| Windows 上看进程亲和性和作业对象的 CPU 上限 | 没有这样部署的需要 | 要在受限的作业对象里跑时 |
| 控制块缓存：每根线程手边留一批控制块，别的线程释放时还回去 | 路线图 4.1 原来定了要做。实测 malloc 只占起协程的 25 到 30 ns：换成只分不还的分配（缓存能做到的上限），8 根线程时 177 ns 降到 152 ns，CPU 0.28 s 降到 0.24 s；比 Go 多出的 CPU 主要是几根线程抢着偷几乎不干活的协程，后来全局队列一次取一批，这部分 CPU 已经和 Go 一样。serve 每个请求约 30 µs，控制块分配占不到 0.1% | 起协程的开销在参考程序里量得出来时 |
| Linux 上用 `epoll_pwait2` 让定时器精确到纳秒 | 见上面第 4 节：定时器准一些，每睡一次多 0.1 µs CPU | 要亚毫秒的定时器时 |
| 栈一段段地要，空闲的先还内存、留着地址 | 见上面第 4 节 | 新要栈的系统调用在参考程序里量得出来时 |
| 留着的栈（空闲表里的 64 根、各线程手边的）把用过的页还掉 | 用过很深的栈留着时一直占着那些页；要多一个「还内存、留地址」的平台函数，三个平台各一份 | 参考程序里有递归很深的协程，留着的栈占的内存成了问题时 |
| 闲够了的栈一次全部还掉 | 一批最多 1 ms，Linux 上 1 万根要分 0.4 到 0.5 s 还完；这段时间里占着的内存是高峰时本来就占着的 | 高峰过后要内存回落得更快时 |
| `notify_all` 叫醒一大群时快一些：等待记录放进协程的控制块，一次叫醒一批、一次排进队列 | 见上面第 4 节：叫醒 1 万根时，`notify_all` 本身在 Linux 上是 Go 的 2 到 4 倍、Windows 上约 7 倍；serve 不用条件变量（作者定的先不做） | 参考程序里 `notify_all` 叫醒一大群成了瓶颈时 |
| 闲着的线程可以偷忙线程格子里的协程 | 一直不挂起的协程抢锁时，等锁的最久 16 ms，Go 4.8 ms；要改路线图 4.1 的决定（作者定的先不做） | 参考程序里等锁或者叫醒的延迟成了问题时 |
| 限时拿锁（`std::timed_mutex` 那样的 `try_lock_for`） | 没有调用方 | 有调用方时 |
| 销毁时还有人在等就终止（上一版这么做） | 要有析构函数；`std::mutex` 也不查 | 真出了销毁时还有人在等的 bug 时 |

## 6. 测了什么

- `tests/coroutine_test.cpp`：`std::thread` 的那些行为；`sleep_for` 睡够时长、睡到过去的时刻立刻返回、睡着时同一根线程上别的协程照跑、按时刻先后醒、普通线程上等于 `std::this_thread`。`tests/scheduler_test.cpp`：一直不让出的协程不挡别的协程；阻塞在系统调用里的协程不挡它刚起的那根（格子里的）；协程分到几根线程上；64 根协程各 300 次跨线程 join；4 根普通线程和协程互相等；1000 根协程一起睡到同一刻，一根都不早醒。`tests/fault/`：误用、栈溢出、在 catch 块里挂起。
- 反向验证过：去掉监控挪格子那一步，「不挡刚起的那根」失败；用 `taskset -c 0` 限在一个核上、去掉补线程，三条失败（不让出的那条 10 秒后放弃）。
- `tests/run_queue_test.cpp`：一串协程和就绪队列的先后次序；4 根线程放、4 根线程一根一根或者一批一批地取，每根协程恰好出来一次。`tests/park_test.cpp`：挂起和叫醒的握手，叫醒在挂起之前、途中、之后三种先后。
- `tests/stack_test.cpp`：一大群协程跑完以后，空闲表里多出来的栈 5 秒内还给系统（实际约 1.1 秒），再来一群照样能跑、照样还掉。反向验证过：让空闲的栈永远不还，这条失败。
- `tests/sync_test.cpp`：16 根协程和 2 根普通线程抢一把锁、拿着锁让出；拿着锁睡过去再放，等的那根不会提前拿到；`try_lock`；一直占着锁、从不挂起的协程挡不住等的那根；4 根协程放、3 根协程和 1 根普通线程取；`wait_for` 到点返回超时、回来时拿着锁，协程里和普通线程上各一遍；先被通知时定时器拿掉了（之后睡满 100 ms）；`wait_until` 用 `system_clock`；400 根协程各限时等 20 次、一根普通线程一直通知，每根都醒、只醒一次。`tests/fault/`：放没拿着的锁、拿没锁住的 `unique_lock` 去等。
- 反向验证过：去掉「抢输一次就直接交」，「挡不住等的那根」失败（10 秒后放弃；第一版测试拿着锁只算 20 µs，等的那根 41 ms 时碰巧抢到了，没抓到，改成算 5 ms）；到点不记成超时，`wait_for` 那条失败。
- 本机：Linux GCC debug / release、ASan + UBSan、Clang 14 的 TSan（多核 3 到 5 遍、单核 1 到 2 遍，0 条警告）；Windows MSVC debug / release、MSYS2 UCRT64 的 MinGW；GCC 4.8 和 macOS（照 SDK 抄的头文件桩）只做了类型检查。
- 没测：macOS 上的运行（只有 CI）；8 根以上工作线程；容器限核时的行为；补到很多线程时的内存。
