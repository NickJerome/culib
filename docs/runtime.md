# 协程运行时

`<culib/coroutine.h>` 是库的并发模型：`go()` 起协程，`wait_group` 等协程。会等待的调用（同步原语、`join` 式的等待、`sleep_for`）在协程里只挂起协程，在普通线程（包括 `main`）里阻塞那根线程。

```cpp
#include <culib/coroutine.h>

int main() {
    wavvix::wait_group group;          // 不用建运行时：第一次 go() 时自己起来
    group.go([](int count) {
        // 这里可以调用协程感知的 I/O、sleep_for、同步原语和 call_blocking。
        (void)count;
    }, 3);
    group.wait();                      // main 线程在这里等组里的协程结束
}
```

可运行的程序见 [`examples/coroutine.cpp`](../examples/coroutine.cpp)（最小用法）和 [`examples/runtime.cpp`](../examples/runtime.cpp)（工作线程、让出与睡眠、定时器、组里再加协程）。

## 运行时

运行时在第一次 `go()` 时启动，工作线程数取 [`os::cpu_count()`](../include/culib/os.h)：Linux 上按 CPU 亲和性和 cgroup 的 CPU 配额算，容器里不会报成宿主机的核数。环境变量 `WAVVIX_MAXPROCS` 可以改成 1 到 256 之间的任何数；给了别的值，第一次 `go()` 时打印诊断后终止。代码里没有设置线程数的接口。

运行时启动以后一直在，不析构，工作线程也不 join。**`main` 返回时进程直接退出，还没结束的协程不再运行**，和 Go 一样；要等就用 `wait_group`。退出时库自己的状态（运行时、日志输出表、flag 登记表）不析构，协程碰到它们是安全的；使用方自己的全局对象照常析构，还在跑的协程碰到它们是使用方的问题。

库不检测死锁：所有协程都挂起、谁也叫不醒谁时，等它们的 `wait_group::wait()` 会一直等下去。

## go 与 wait_group

`go(f, args...)` 起一根协程，在哪里都能调用：

- 参数按值保存，运行时移动给函数；传引用用 `std::ref`。新协程可能马上在别的工作线程上开始跑，所以传进去的引用和对象要活到协程结束。
- 没有句柄。要等它结束就把它放进 `wait_group`，要它的结果就让它送进 [`channel`](../include/culib/sync.h)。
- 函数里逃出的异常会 `std::terminate()`，相当于 Go 里没人 recover 的 panic。内存不够时打印诊断后终止。

`wait_group` 只有两个成员：`go(f, args...)` 往组里加一根协程，`wait()` 等组里的协程全部结束。

- `wait()` 返回时，组里协程的函数和它保存的参数都已经析构，协程写下的东西都看得见。
- 组里的协程可以接着往同一个组里加，`wait()` 连它们一起等。`wait()` 返回以后组可以再用。
- 可以有多个等待者，在协程里等和在普通线程里等都行。
- 组里还有协程没结束时析构，打印诊断后终止：那些协程结束时要回来通知这个组。

### 协程在哪根线程上跑

普通线程（包括 `main`）里起的协程排进全局等待队列，由空闲的工作线程取走；协程里起的协程先排在本线程上。全局等待队列先进先出；一直有活的工作线程每 61 轮也从全局队列取一根，排着的协程不用等那些一直让出的协程结束（Go 的调度器也用 61）。

协程**第一次运行后就绑在那根工作线程上**，不再换线程。所以要分清两种关系：

- **不同工作线程上的协程是并行的。** 共享的数据要加锁（[`wavvix::mutex`](../include/culib/sync.h) 跨线程可用，协程和普通线程之间也能用），或者用原子量。
- **同一根工作线程上的协程不会并行，也不会被抢占**，只在让出时切换。

协程里调用真正阻塞线程的函数（同步文件读写、`std::this_thread::sleep_for`、长时间持有 `std::mutex`、算个不停的循环）会连带卡住同一根工作线程上的所有协程。阻塞调用交给 `call_blocking`，长循环里适时 `yield()`。

### 内存

`go()` 分配一次：控制块和可调用对象在同一块里，经全局的 `operator new`。**栈在协程第一次运行时才分配**，向 [`wavvix::mem`](mem.md) 要，协程结束时还回去。所以排在队列里还没开始的协程不占栈，起一大批再慢慢跑不会一下子吃掉 `数量 × 栈大小` 的内存。分配器不分线程地复用释放的内存，空出来约一秒后、在分配器下一次取锁时还给系统，栈不另设缓存。

栈固定为 240 KiB 可用，分配器按 64 KiB 的整数倍给出，实际占 256 KiB 地址空间。用到的页才占物理内存；但 Windows 和严格 overcommit（`vm.overcommit_memory=2`）的 Linux 按整块记提交量，同时在跑的协程数要计入提交预算。

## yield 与 sleep_for

`yield()` 在协程里让出，排到本线程就绪队列的末尾；在协程外等同 `std::this_thread::yield()`。`sleep_for(d)` 在协程里只挂起这根协程，在协程外睡当前线程；零或负时长立即返回，要让出一次请用 `yield()`。

同一根工作线程上醒来的次序按时限，不按挂起的先后：工作线程忙的时候几个时限会在同一轮到期，它们仍按时限的先后排回就绪队列。不同工作线程上的协程各自醒来，Windows 默认的定时器精度约 15.6 ms，相差不到这么多的时限分不出先后。

## call_blocking

没法协作式让出的调用（`getaddrinfo`、第三方库的同步接口、普通文件读写）用 `call_blocking(f, args...)` 放到后台线程上，等待期间只挂起调用它的协程：

```cpp
std::string text = wavvix::call_blocking(read_config, path);
```

- 返回 `f` 的返回值；`f` 抛出的异常在调用处重新抛出。参数和直接调用一样传：左值按引用、右值照样移动，不拷贝——调用期间它们都活在等待协程的栈上，所以也没有每次调用的堆分配。
- 后台线程整个进程共用，第一次用到时才建，最多 64 根；同时进行的调用超过这个数就排队。
- 不在协程里时直接在当前线程调用。
- 没有超时也不能取消：`f` 不返回，等它的协程就一直挂着。

完整程序见 [`examples/call_blocking.cpp`](../examples/call_blocking.cpp)。

## 套接字

套接字第一次读写时绑到当时所在的工作线程，之后只能在那根线程上读写；在别的工作线程上读写打印诊断后终止。要在另一根协程里用同一个套接字，在第一次读写它的那根协程里用 `go()` 起那根协程：协程里起的协程排在本线程上。还没读写过的套接字（例如刚 `accept` 出来的连接）可以交给任何一根协程。连接、收发只能在协程里调用。详见[网络](net.md)。

## 误用与诊断

运行时的误用都打印一行诊断后终止，release 构建同样检查。每一条都由 [`tests/fault/runtime_faults.cpp`](../tests/fault/runtime_faults.cpp) 在子进程里核对过诊断文字。

| 误用 | 诊断里的关键句 |
| --- | --- |
| `WAVVIX_MAXPROCS` 不是 1 到 256 之间的整数 | WAVVIX_MAXPROCS 必须是 1 到 256 之间的整数 |
| 内存不够，建不起协程 | 内存不足，建不起协程 |
| 第一次运行时要不到栈（内存不够；debug 构建超过约 3 万根，见[栈溢出](#栈溢出)） | 栈内存不够，跑不起协程 |
| 套接字换了工作线程读写 | 不能换线程用 |
| `wait_group` 析构时组里还有协程 | 组里还有协程没结束 |
| `channel` 容量为 0；往关闭了的 channel send；重复关闭 | 容量至少为 1；已经关闭，不能再 send；重复关闭 |

## 栈溢出

协程栈大小固定。release 构建不设保护页：栈用超了不会报错，而是悄悄写坏相邻的内存，表现为别的协程卡住、崩溃或数据被改。不设保护页是为了让协程数量不受限制：保护页在 Linux 上每根栈要多占映射，默认上限会把并发协程卡在约 3 万根，而容器里改不了这个上限。原因和测量见[实现说明](implementation-notes.md#协程栈)。

debug 构建在每根栈的最低一页设保护页，溢出当场崩溃，调试器里能看到越界那一刻的调用栈。代价是 Linux 默认设置下 debug 构建最多约 3 万根同时在跑的协程。怀疑 release 程序里有栈溢出时（卡死或崩溃发生在无关的协程里），用 debug 构建重现。

普通代码用不了多少栈：库自己的协程最深用 4.1 KiB，格式化、异常、排序、DNS 解析最多 11.5 KiB，默认栈有 20 倍余量。会用超的只有递归深度随输入增长的代码，这些地方要自己限制深度：

- 解析嵌套数据（JSON、XML、表达式）时限制嵌套层数，或者改成循环加显式的栈。Go 的 `encoding/json` 也把嵌套限制在 1 万层。
- 用 `unique_ptr` 串起来的链表和树，析构时一层层递归，长链要写成循环释放。
- 不对外部输入用 `std::regex`。GCC 15 及以前的 libstdc++ 每匹配一个字符约用 0.7 KiB 栈，几百个字符就能用完默认栈；回溯式匹配遇到特定输入还要花指数级的时间。

确实需要深栈的代码放到 `std::thread` 里跑：普通线程的栈通常是 1 到 8 MiB。

## 和 Photon 的对照

PhotonLibOS 用 `photon::thread_create` 起协程、`thread_join` 等它，`photon_std::thread` 是 `std::thread` 风格的持有型句柄。culib 改成了 Go 的形状：没有句柄，`go()` 起了就不管，要等就用 `wait_group`。另外：

- Photon 的协程默认不迁移，迁移要显式调 `thread_migrate` 或在 vCPU 和协程上都打开工作窃取；culib 现在也不迁移，协程第一次运行后固定在一根工作线程上。
- Photon 的 WorkPool 用无锁环分发任务，环有容量上限；culib 的全局等待队列是互斥锁加侵入式链表，没有上限。实测环只在「起得密、每根活很短」时快（空协程 241 对 399 ns，1 µs 的活 489 对 615 ns），10 µs 以上的活和 TCP 长短连接持平，见[实现说明](implementation-notes.md#试过的全局队列和栈)。

## 只支持 64 位

协程的换栈汇编只有 x86_64 和 arm64 两种，栈来自只支持 64 位的分配器。32 位目标在编译期报错。

## 测试怎么分

`culib_test` 在 `main` 里把 `WAVVIX_MAXPROCS` 设成 4，不随机器的核数变。断言执行次序的测试在 [`runtime_order_test`](../tests/order/) 里，那个程序只开一根工作线程：所有协程排在同一根线程上，只在挂起和让出时切换，次序是确定的。
