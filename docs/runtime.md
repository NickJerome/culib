# 运行时

- 日期：2026-10-21
- 代码：`include/cu/coroutine.h`，`src/runtime/`，`src/platform/cpu_count*`

## 1. 做什么

协程和跑协程的线程：

- `cu::coroutine` 起协程、等它跑完，行为照 `std::thread`（路线图 4.2）。
- 几根工作线程跑协程，协程可以换线程（路线图 4.1）。
- 一根系统线程等 I/O 事件，顺带看着工作线程（监控）。
- 协程栈：每根 1 MiB，保护页一直开着。

## 2. 接口

| 分类 | 签名 | 说明 |
| --- | --- | --- |
| 起和等 | `coroutine(F&& f, Args&&... args)` | 参数按值拷进协程，构造完就开始排队跑 |
| | `void join()` / `void detach()` / `bool joinable() const` | 和 `std::thread` 一样 |
| | `id get_id() const` / `void swap(coroutine&)` | `id` 能比较、做哈希键、用 `<<` 输出 |
| 当前协程 | `this_coroutine::get_id()` | 不在协程里返回空 id |
| | `this_coroutine::yield()` | 排到本线程本地队列的末尾；不在协程里等于 `std::this_thread::yield()` |

`sleep_for` 和 `sleep_until` 要等定时器那一步。

用的时候要知道的三件事，都写在头文件里：

- 协程挂起以后可能在另一根线程上接着跑，`thread_local` 变量和 `std::this_thread::get_id()` 不要跨挂起点用。
- 协程里可以调会阻塞线程的函数，也可以一直算：排在后面的协程会被别的线程接走，都忙时运行时补一根线程。
- 不能在 catch 块里挂起，真的要等时打印诊断后终止。

## 3. 取舍

### 线程数

平时开「进程能用的核数」根工作线程：Linux 上是亲和性允许的核数，再和容器的 CPU 配额（`/sys/fs/cgroup` 下的 `cpu.max`，或 v1 的两个文件）比，取小的；配额向上取整，不到 2 个核按 2 个算，和 Go 1.25 一样。macOS 和 Windows 用 `std::thread::hardware_concurrency()`。没有配置项。

### 队列、取活和叫醒

照路线图 4.1。实现时定下的几处：

- 本地队列是 256 格的环，放、取、偷都在这根线程的自旋锁里。偷的时候锁上对方拿走一半（向上取整，最多 128 根），放开，再锁上自己放进去。
- 让出的协程排到本地队列末尾，不叫醒别的线程：这根线程接着就会取。其他线程都闲着时，监控连着两次看到「有活没人干」就叫醒一根来偷，所以一群一直让出的协程最多晚 2 ms 分到别的线程上。
- 闲着的线程各睡在自己的条件变量上，叫醒时取最后睡下的那根。
- 找活的线程找到了，而它是最后一根在找的，就再叫醒一根。

### 监控

在系统线程上，有工作线程忙时每 1 ms 看一遍，都闲着时一直睡，有线程忙起来再叫醒它：

- 一根线程这一个间隔里一根协程都没跑完，把它「下一根」格子里的协程挪进全局队列；
- 有线程在同一根协程里待了 10 ms 以上、还有活排着、又没有闲着的线程，就补一根。补的线程总数不超过 256；卡住的线程恢复以后，多出来的线程闲下来就退出，但不少于平时的根数；
- 有活没人干、又没线程在找活，连着两次看到就叫醒一根。

C++ 分不出阻塞的系统调用和一直在算，两种都会补线程。所以 `fs::read_file` 这类会阻塞线程的调用不另做处理，路线图 4.4 留到这一步定的事就这么定了。

Windows 上系统线程的超时按系统节拍到期，默认约 15.6 ms，所以另用一个高精度定时器，经「等待完成包」接到完成端口上，到点时端口里多一个包（Go 也这么做）。定时器只在上一次的包取回来以后才重设，I/O 多的时候不用每取一批完成包都多三次系统调用。

### 栈

全局缓存留 64 根，每根工作线程手边再留 16 根：跑完的协程把栈还到手边，下一根先从手边拿。

### catch 块

挂起之前查一次 `std::current_exception()`，在 catch 块里就终止，见路线图 4.2。

## 4. 测量

都是 2026-10-21 在 WSL2 上量的（i7-12700，Ubuntu 22.04，GCC 11.4 `-O2`，库是 xmake 的 release 构建）。8 根工作线程是用 `taskset -c 0-7` 限的，也就是 4 个大核加上它们的超线程。各项和路线图 4.1 原型那次同样的写法，Go 是 1.24.5；每项 5 轮，轮换先后，取中位数，括号里是整个程序用掉的 CPU 秒数。

| 项目（8 根工作线程） | v2 | Go |
| --- | --- | --- |
| 起一根空协程再等它跑完 | 185 ns（0.30 s） | 164 ns（0.10 s） |
| 让出 | 29 ns（0.03 s） | 118 ns（0.17 s） |
| 两根协程经 channel 来回传消息 | 97 ns（0.02 s） | 243 ns（0.06 s） |
| 一次叫醒 64 根，各算 2 µs | 65 µs（2.12 s） | 72 µs（2.22 s） |
| 1000 根协程一起让出 | 24 ns（0.08 s） | 173 ns（1.12 s） |

几处取舍的依据：

| 问题 | 量到的 | 怎么定的 |
| --- | --- | --- |
| 本地队列用锁 | 只有 1 根工作线程时，同一份代码去掉锁，让出从 32 ns 降到 22 ns | 照 4.1 留着锁：比 Go 快 4 倍，参考程序里还没看到它成为瓶颈 |
| 全局栈缓存一把锁 | 8 根线程起协程 365 ns（只有 1 根时 141 ns），手边留 16 根栈以后 185 ns | 手边留栈 |
| 监控每 1 ms 一查 | 一根协程卡在系统调用里 5 秒，Linux 上监控用掉 57 ms CPU，Windows 上 65 ms，约单核的 1%；都闲着时 5 秒用 0.2 ms | 照 4.1 |
| 卡住的线程格子里的协程 | 8 根时约 1.5 ms 后在别的线程上跑起来（20 次里最长 2.2 ms）；只有 1 根时约 11 ms（判定卡住 10 ms，再补一根线程） | 照 4.1 |
| Windows 上等 1 ms | 直接设超时等了 15.5 ms，高精度定时器加等待完成包 1.5 ms，高精度定时器配 APC 不触发 | 等待完成包 |
| catch 块检查 | 每次挂起 GCC 2.4 ns，MSVC 16 ns | 查 |

serve 在压力下（每个请求一条新连接，4 个 ab 同时压，serve 限在 0-7 号核上，两个版本各 4 轮、轮换先后）：

| | 一根工作线程（`b8bc921`） | 8 根 |
| --- | --- | --- |
| 每秒请求数 | 6.7 万 | 11.5 到 13.2 万 |
| p50 / p99（ab 只给整毫秒） | ≤2 / ≤2 ms | ≤1 / ≤2 ms |
| 每个请求的 CPU | 26 µs | 27 到 31 µs |
| 每个请求的 futex 调用（strace 数的） | 1.2 次 | 3.4 次 |

多出来的 CPU 是线程睡下和叫醒：epoll 和 close 两边一样多，accept4 改前多出来的是 EAGAIN 以后的重试。

## 5. 不做的事

| 不做 | 为什么 | 什么条件下重开 |
| --- | --- | --- |
| 无锁本地队列 | 见路线图第 7 节；这里量到锁在让出上占约 10 ns | 参考程序里本地队列的锁成了瓶颈时 |
| 分清阻塞和计算，只给阻塞的线程补线程 | 要看每根线程实际用了多少 CPU 时间，三个平台各一份代码；一直算的协程多时线程会多到 256 根，由系统分时 | 参考程序因为线程太多吃亏时 |
| 闲线程先空转一会儿再睡 | 见路线图第 7 节；serve 每个请求因此多 2 次 futex 调用、1 到 5 µs CPU | 有数据显示叫醒延迟或叫醒的 CPU 成了问题时 |
| 按 `/proc/self/cgroup` 找本进程所在的 cgroup | 容器里 `/sys/fs/cgroup` 就是容器自己那一层；宿主上 systemd 给服务设的 `CPUQuota=` 看不到 | 要在宿主上用 systemd 限核部署时 |
| Windows 上看进程亲和性和作业对象的 CPU 上限 | 没有这样部署的需要 | 要在受限的作业对象里跑时 |
| 控制块缓存 | 下一个提交做：起协程的 CPU 还是 Go 的 3 倍 | — |

## 6. 测了什么

- `tests/coroutine_test.cpp`：`std::thread` 的那些行为。`tests/scheduler_test.cpp`：一直不让出的协程不挡别的协程；阻塞在系统调用里的协程不挡它刚起的那根（格子里的）；协程分到几根线程上；64 根协程各 300 次跨线程 join；4 根普通线程和协程互相等。`tests/fault/`：误用、栈溢出、在 catch 块里挂起。
- 反向验证过：去掉监控挪格子那一步，「不挡刚起的那根」失败；用 `taskset -c 0` 限在一个核上、去掉补线程，三条失败（不让出的那条 10 秒后放弃）。
- 本机：Linux GCC debug / release、ASan + UBSan、Clang 14 的 TSan（多核 5 遍、单核 2 遍，0 条警告）；Windows MSVC debug / release、MSYS2 UCRT64 的 MinGW；GCC 4.8 和 macOS（照 SDK 抄的头文件桩）只做了类型检查。
- 没测：macOS 上的运行（只有 CI）；8 根以上工作线程；容器限核时的行为；补到很多线程时的内存。
