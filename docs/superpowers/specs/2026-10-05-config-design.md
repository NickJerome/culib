# config：三个待定项的答案，以及示例抓出来的两处

- 日期：2026-10-05
- 状态：**已实现**。路线图第二程第 11 项。
- 前置：[预期接口](2026-10-03-module-interfaces.md) 第 11 节给了接口和**三个「要定的事」**。

## 1. 三个待定项

预期接口第 11 节末尾写着：

> **要定的事**：到底是 ini 还是 toml 子集（toml 更现代但语法多；ini 简单但没有标准）；数组怎么表示（`key[0]`、还是逗号分隔）；是否支持环境变量替换 `${HOME}`。

### 1.1 ini，不是 toml

**toml 要回答的问题比 ini 多一个量级**：数组、内联表、表数组、多行字符串、转义规则、日期时间、各种数字写法（下划线分隔、十六进制、`inf`/`nan`）。每一条都是设计面，而服务配置一条都用不上。

ini 的子集反而**没有设计自由度**：注释、段、键等于值，就这三样。「ini 没有标准」这个缺点在这里是优点——我们只需要定自己认哪些，而需要认的恰好是所有 ini 都认的那部分。

### 1.2 数组：不做

`key[0] = a` 和 `key = a, b, c` 两种写法各有一堆跟进问题（下标要不要连续？逗号能不能转义？空元素算不算一个？），而**三个目标场景里没有消费者**。

**什么条件下做**：出现真实的「一个键要对应多个值」的配置项。那时倾向逗号分隔加 `strings::split`，因为它不需要新语法。

### 1.3 `${HOME}` 替换：不做

**没有消费者，而且它让配置文件的含义取决于环境**——同一个文件在两台机器上是两个意思，排查问题时要先问「你那边 HOME 是什么」。真要这么做的地方，用命令行传进来更明白。

**什么条件下做**：出现「同一份配置要分发到环境不同的机器」的真实需求。

## 2. 接口上改了两处

| 预期接口 | 实际 | 为什么 |
| --- | --- | --- |
| `std::string get_string(key, fallback)` 等直接返回值 | `result<std::string>` / `result<long long>` / … | 见下。**这是本模块最要紧的一条决定** |
| 只有 `get_int64` / `get_bool` | 加了 `get_double` | 超时秒数、比例这类配置项是常事，而 `lexical_cast` 本来就支持 |

### 2.1 「不存在」和「写错了」是两件事

```cpp
settings.get_int64("port", 8080)
```

| 情形 | 返回 |
| --- | --- |
| 没写 `port` | `ok(8080)`——**键不存在不是错误** |
| `port = 9000` | `ok(9000)` |
| `port = 80 80` | **error**，消息里带键名和原始文本 |

直接返回值的写法做不到第三行：它只能悄悄用默认值。而**`port = 80 80` 静默变成 8080 是那种要查一下午的事**——服务起来了、端口不对、配置文件看着没问题。

代价是调用点多一次 `is_ok()`。认了：开发约定里「可能失败的操作一律返回 `result`」，而这件事确实可能失败。

## 3. 示例抓出来的两处

开发约定里写着「示例没法作弊，它必须按用法写，所以比单元测试更容易发现接口问题」。这一期又中了两次，**两次都是示例先红的**。

### 3.1 行尾注释被吃进值里

第一版的解析只把**整行以 `#` 开头**当注释，于是示例里的

```ini
name = culib               # 等号两边的空白会去掉
```

值变成了 `culib               # 等号两边的空白会去掉`。更要紧的是 `port = 8080 # 端口` 会解析不出整数——而带行尾注释的配置文件到处都是。

**定的规则：前面有空白的 `#` 或 `;` 开始注释。**

```ini
port = 8080        # 端口       → "8080"
url  = http://x/#fragment       → "http://x/#fragment"    （# 前面没空白）
note = "a # b"                  → "a # b"                 （引号里的不算）
```

不在任何 `#` 上都切，是因为 URL 的片段和密码里带 `#` 是常事。要求有空白隔开既符合直觉又好记，真要写以 `#` 开头的值就用引号。

**单元测试当时是绿的**，因为它测的值里都没有 `#`——那正是「照着实现写测试会把 bug 一起藏起来」。

### 3.2 引号的语义顺带改对了

原来的实现是「首尾都是引号就把它们去掉」，于是 `""inner""` 得到 `"inner"`。加了注释规则之后换成更标准的「**带引号的值到下一个引号结束**」，而这顺带暴露了一个该报错的情形：

```ini
x = "a" junk
```

闭引号后面那个 `junk` 原来会被静默丢掉。**和 2.1 是同一条原则**——写错了要报出来，所以现在它是错误（闭引号后面只允许空白或注释）。引号没闭上也是错误。

## 4. 其余几条决定

- **重复的键后面覆盖前面**，和别的 ini 解析器一样。报错也是一种选择，但「和大家一样」在这里更重要：配置文件的读者未必读过本库的文档。
- **语法错一定说第几行。** 配置的错是人改出来的，而人需要知道改哪一行。从文件读时**还会带上文件名**——底层只知道「第 7 行」，不知道是哪个文件的第 7 行（开发约定：跨层传播时在层边界上补上下文）。
- **按出现顺序存，查找是线性的。** 配置文件是几十个键的量级；线性扫比一个 map 简单，而且 `keys()` 要的那个顺序天然就有了。**什么条件下换**：出现几千个键的配置文件。
- **嵌套用 `section.key` 扁平键**，不做任意深度的树。这样就不需要 `variant` 那种递归值类型（而 `variant` 已经评估过不做）。

## 5. `apply_to_flags()`：命令行优先

让配置文件和命令行**共用一套定义**，不用把每个设置写两遍。

两条规则：

- **命令行优先。** 已经在命令行上给过的键跳过，不让配置文件盖掉它。
- **flag 里没定义的键不算错。** 配置文件通常比命令行多（日志路径那些不走命令行），所以那些只是跳过。真正该报的是「定义了但值不对」。

实现时发现 `flag` 缺一块：它只有按**存储地址**问的 `was_given(const void*)`，而配置文件手里只有名字。所以给 `flag` 加了一个 `was_given(string_view)` 重载——**和 `log` 逼出 `fs::output_file`、IOCP 逼出 `io_engine_adopt` 是同一回事**：一个模块落地时发现下层缺一块。

**第一版漏了「命令行优先」这一条**：文档里写着，实现里没检查，配置文件会盖掉命令行给的值。写测试时才发现，而那条测试现在钉着它。

## 6. 实现验证

| 平台 / 工具链 | 结果 |
| --- | --- |
| Linux x86_64，GCC 14.2 / clang 19，debug / release | **272 个测试通过**，零警告 |
| MinGW-w64 x86_64 + wine | 269 个通过，零警告 |
| MinGW-w64 i686 | 编译链接通过 |
| ASan + UBSan，`detect_leaks=1` | 新增 21 条干净 |

21 条。值得点名的四条：

- `strips_a_trailing_comment_but_not_a_hash_inside_a_value`：3.1 那个 bug 的回归测试，连 `url = http://x/#fragment` 一起钉住。
- `treats_a_malformed_value_as_an_error_not_a_default`：2.1 那条原则，断言错误消息里带键名和原始文本。
- `says_which_line_is_wrong`：三种语法错各验一次行号。
- `leaves_alone_what_the_command_line_already_set`：第 5 节那个漏掉的规则。

`apply_to_flags` 那几条测试要先跑一次 `flag::parse`——`flag` 有个「`parse()` 之前读取选项的值就 abort」的门禁（那是它的时序陷阱）。

## 7. 没做什么

- **数组**、**`${VAR}` 替换**：见 1.2 / 1.3。
- **写回文件**：`config` 是只读的。改配置文件的程序要自己拼文本，而那会引出「注释保不保留」「顺序保不保留」一串问题，没有消费者。
- **热加载**：路线图写着「和第三程的 `fs::watcher` 配起来就是热加载」，所以等 `fs::watcher`。组合两者交给调用方，不做进 API。
- **多文件 include**：没有消费者。
