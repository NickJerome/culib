# 路线图

- 日期：2026-10-03
- 状态：生效中。这里是模块顺序的权威位置，取代 `2026-10-02-stopwatch-and-test-slimming-design.md` 第 6 节。

## 1. 这个库是给什么用的

**解决作者常见的开发用途。** 这一句是所有取舍的依据——判断「这个该不该做」时先问它在下面三个场景里有没有真实位置。

| 场景 | 说明 | 紧迫度 |
| --- | --- | --- |
| **小工具 CLI** | 临时切图这类一次性工具：参数、批量处理文件、进度输出 | 近期，最小可用门槛最低 |
| **多平台服务器程序** | 长期运行的进程：配置、日志、并发、网络、优雅退出 | 近期 |
| **easytier 式精简核心** | P2P mesh / NAT 穿透 / 虚拟网卡 | 远期，单个特定项目 |

两条边界：

- **culib 只做脚手架，不碰需要第三方库的领域。** 切图工具的图像解码（libpng / libjpeg）、easytier 核心的加密，都不在 culib 里。这些**先不做，真用到了再决定是自己写还是引入**——不预先为它们设计接口。
- **彩色终端、文本表格这类"给人眼看"的东西只对 CLI 场景有意义。** 服务器的输出去的是日志文件。

## 2. 按场景拆出来的真实需求

| 需求 | CLI | 服务器 | easytier 核心 |
| --- | --- | --- | --- |
| 命令行参数 | **核心** | 有用 | 有用 |
| 文件系统 | **核心**（批量处理要遍历目录） | 需要（配置、日志、pid） | 需要 |
| 字符串 | 需要（路径、文件名） | 需要 | 需要 |
| 日志 | 弱 | **核心** | **核心** |
| 并发 | 不需要 | **核心** | **核心** |
| 网络 | 不需要 | **核心** | **全部的核心** |
| 协程 | 不需要 | 需要（让异步 IO 代码可读） | **核心** |
| 字节缓冲与字节序 | 不需要 | 需要 | **核心** |
| 信号与优雅退出 | 弱 | **必须** | **必须** |
| 配置文件 | 不需要 | 需要 | 需要 |
| 时间（时间戳、超时） | 弱 | 需要 | 需要 |
| 彩色终端 | 有用 | 无用 | 无用 |
| 文本表格 | 几乎无用 | 无用 | 无用 |

三个结论：

1. **三个场景里有两个最需要网络，而原路线图里没有网络模块。** 这是最大的缺口。
2. **`log` 和 `thread` 在两个场景里是核心，原路线把它们排在第 9、10 位。** 最严重的顺序错配。
3. **`table` 在三个场景里都没有消费者，删掉。** 不是降级——服务器和 easytier 核心用不上，CLI 顶多列个结果，几行手写循环就够。

## 4. 关键决定

### 4.1 string_view：第一个做，而且不能别名到 std::string_view

**为什么第一个做**：第一程后面四个模块全都以字符串为输入——`lexical_cast` 整个模块的工作就是转字符串，`flag` 要在 `--port=8080` 上切 `=` 再转尾巴，`strings` 和 `fs` 全是字符串和路径。签名一旦定成 `const std::string&`，`fs::read_file("config.json")` 这种调用每次都要分配一次，而之后改成视图是对所有调用方的 API 破坏。约 150 行的前置工作，换掉一次全模块的签名返工。

它还把开发约定里一条空头承诺变成真的：`CLAUDE.md` 的「少分配、少拷贝」写着「参数优先传引用或**字符串视图**」，而这个库里目前并没有字符串视图。

**必须用自己的类型，不要在 C++17 下别名到 `std::string_view`。** 很多库（包括 abseil）会这么写：

```cpp
#if __cplusplus >= 201703L
using string_view = std::string_view;    // culib 不能这么做
#endif
```

culib 不行，因为它自己按 C++11 编译，而 README 允许使用方用更高的标准——CI 的 `consumed-as-dependency` 这一格就是 culib C++11 + 使用方 C++17。如果 `wavvix::string_view` 在两边是不同的类型，任何以它为参数的公共函数都会签名不匹配、链接失败。所以：

- 始终用 culib 自己的 `string_view`，类型身份与语言标准无关。
- 再加一个条件编译的转换构造函数，让 C++17 使用方能把 `std::string_view` 传进来。这是纯增量，不改类型身份和内存布局。

**范围**：`data()` / `size()` / 下标与迭代、常用查找与比较、到 `std::string` 的显式转换。`split` 之类属于 `strings`，不放在这里。

**对现有代码没有影响**，纯增量：`error` 的消息是它自己拥有的，`make_error(error_kind, std::string)` 按值取、允许移动，这是对的，不改。

### 4.2 协程为什么必须排在 net 之前

有了协程，net 的 API 形态就定了：

```cpp
auto n = sock.read(buf);   // 看起来是阻塞的，实际不可读时让出，可读时被调度回来
```

这是 libco 和 Go 的做法，比回调式事件循环**更简单**。但这意味着：**先做一个回调式的 net，协程来了之后那套 API 全废，net 要写第二遍。** 所以协程在前，或至少同时设计。

### 4.3 协程已定的两条

- **一次做全 6 个 (平台, 架构) 目标**，对齐 README 的平台矩阵。理由：协程是全有或全无的——程序一旦用了协程，发到某个平台就必须有那个平台的汇编，没有"部分可用"。
- **写 CFI / unwind 信息**，让 gdb 能在协程栈上回溯、异常能安全穿栈。场景 1 和 3 都是长期运行的进程，崩在协程里看不到调用栈是不可接受的。~~代价是工作量约翻倍。~~ **「翻倍」这个估计是错的，实测推翻了**：回溯和异常在协程栈内部靠编译器给普通函数生成的 CFI 就能工作，我们要写的只有 trampoline 上三行（48 字节 `.eh_frame`，覆盖 3 个字节代码），而且加不加行为一样。见 [coroutine 设计](2026-10-04-coroutine-design.md) 3.4。

### 4.4 协程的成本在哪（不是那 20 条指令）

上下文切换本身，x86_64 SysV 约 20 条指令（保存 rbx / rbp / r12-r15 / rsp / rip + MXCSR）。真正的成本：

**ABI 矩阵**，每个目标一套汇编：

| 目标 | 汇编器 | 麻烦 |
| --- | --- | --- |
| Linux / macOS x86_64 | GAS `.S` | 基准，最简单 |
| Linux / macOS arm64 | GAS `.S` | x19-x28、d8-d15；macOS 上还有指针认证与 W^X |
| MinGW x64 | GAS `.S` | 要存 xmm6-15（Win64 把它们算 callee-saved） |
| MSVC x64 | **MASM `.asm`** | **MSVC x64 不支持内联汇编**，必须独立 `.asm` 走 ml64；还要存 TIB 里的 StackBase / StackLimit / DeallocationStack |
| MSVC x86 | MASM | 32 位另一套 |

**其余四项，每一项都能单独坑很久：**

- **CFI / unwind**：见 4.3，已决定要做。
- **ASan 注解**：手写栈不告知 ASan 会满屏假报错。需要 `__sanitizer_start_switch_fiber` / `finish_switch_fiber` 配对。开发约定里有 ASan 验证这一条，所以这是必须项。
- **TLS 与异常状态**：TLS 是按线程而非按协程的，协程在线程间迁移时 TLS 会在脚下变；异常状态 `__cxa_eh_globals` 也在 TLS 里。
- **栈分配**：建议 `mmap` + 保护页（`mprotect`）/ `VirtualAlloc` + `PAGE_GUARD`，让栈溢出变成 SIGSEGV 而不是静默踩内存。不要用 malloc 的裸栈。

### 4.5 fs::watcher 和 net 是同一条依赖

**曾把 `fs::watcher` 排在第二程，理由是「只依赖 `fs`、用阻塞 `wait` 让调用方驱动，协程来了不用改第二遍」。那条理由是错的**，读 libuv 的头文件之后改掉。

协程调度器要能等待 watcher，而三个平台给出的可等待对象不一样：Linux 的 `inotify` 给一个 fd（直接进 epoll）、Windows 的 `ReadDirectoryChangesW` 给 overlapped I/O（进 IOCP），而 **macOS 的 `FSEvents` 给的是 CFRunLoop source，不是 fd，塞不进 kqueue**。libuv 的做法是在专门线程上跑 CFRunLoop，再用 async handle 唤醒 loop 线程——它在 macOS 上为文件监听开了一个隐藏线程。

两个后果：

- 「不用后台线程」在 macOS 上是假的。
- **「协程来了不用写第二遍」只在 watcher 本身能被调度器唤醒时成立**，而那需要调度器先存在。先做一个用 `poll()` 自己阻塞的版本，协程来了之后在协程里调它会阻塞整个线程，照样要写第二遍。

还有第三个后果，是协程第三次让某个设计变简单：**「内核通知 + 保底轮询」的组合不需要新 API**。没有协程时没法同时等两个东西（轮流 `wait` 要么忙等、要么互相拖延迟）；有协程之后两个等待循环各跑在自己的协程里，六行代码搞定，所以不用给 `watcher` 加 `set_rescan_interval`、也不用第三个 hybrid 类型。详见预期接口 5.1。

这和 4.2 里 `net` 的情况一模一样，所以结论也一样：**排在 `coroutine` 之后。** 代价是服务器的配置热加载要等到第三程。

### 4.6 协程挡在 thread 和 log 前面，不只是 net

4.2 的论证是：**先做回调式的 `net`，协程来了那套 API 全废，要写第二遍**，所以协程排在 `net` 前面。

**同一条论证对 `thread` 和 `log` 成立，原路线图没承认。** 具体的坑：

> 协程调用一个会阻塞的线程池 API（阻塞版的 `try_pop`、写满了的异步日志队列），**会把整根承载线程卡住，连带卡死那根线程上所有其他协程**。

这不是风格问题，是**接口形状取决于协程存不存在**：有协程时，这类 API 要么不能阻塞、要么得知道怎么让出。等写完再改就是 4.2 说的「写第二遍」。

所以 `coroutine` 从第 11 位提到第 8 位，排在 `thread` 之前。代价是把体量最大、风险最高的模块提前，但「协程必须做」这件事已经没有分歧（见 4.3），早做意味着建在它上面的东西第一次就建对。

不受影响的：`os`、`time`、配置文件都不碰并发，顺序不动。`thread` 里的读写锁（C++11 没有 `shared_mutex`）也和协程无关，真需要时可以单独先做。

**这条是作者问「那这里不应该还有加上汇编的协程吗」时发现的**——原路线图把 4.2 的原则只应用到了 `net` 一处，没有推广到所有「会阻塞的并发接口」。

## 5. 平台验证

协程要做全 6 个 (平台, 架构) 目标，所以平台覆盖直接决定那一程能不能开工。

**汇编写错的后果不是编译失败，而是静默的栈损坏**——少存一个 callee-saved 寄存器，程序可能跑上万次才崩一次，且崩的位置与原因无关。这类缺陷读代码发现不了，只能靠在真实平台上跑。

### 5.1 CI 用标准写法，不在 YAML 里凑

`.github/workflows/build.yml` 就是普通的三平台矩阵，没有任何条件开关：

```yaml
runs-on: ${{ matrix.target.os }}
target:
  - { name: linux-gcc,    os: ubuntu-latest,  toolchain: gcc }
  - { name: linux-clang,  os: ubuntu-latest,  toolchain: clang }
  - { name: macos-clang,  os: macos-latest,   toolchain: clang }
  - { name: windows-msvc, os: windows-latest, toolchain: msvc }
```

所有跨平台 C++ 库（fmt、spdlog、Catch2、nlohmann/json、abseil、asio、xmake 自己）都是这个写法。它们不需要开关，因为跑在 GitHub 的托管 runner 上。

**「没有 Windows / macOS runner」是基础设施问题，不是 workflow 的问题，不要在 YAML 里解。** 曾经试过三种 YAML 侧的办法，都不该用：

- `if: vars.HAS_WINDOWS_RUNNER` ——配置在仓库外（Gitea 界面），不进 git、看不见。
- `if: github.event_name == 'workflow_dispatch'` ——加好 runner 还要改 YAML，而且两个平台绑在一起。
- 拆成两个 workflow，一个只能手动触发 ——同样是为基础设施缺口写代码。

### 5.2 自建 Gitea 怎么拿到三平台 runner

主仓库在 `git.wangjerome.com` 上，Gitea 的自建 act_runner 一般只有 Linux。标准做法是**用 Gitea 的 Push Mirror 镜像到一个 GitHub 仓库，只借它的 runner 跑 CI**：

1. GitHub 上建一个仓库（可以是私有的；私有仓库每月有免费的 Actions 额度，公开仓库无限）。
2. GitHub 生成一个有 `repo` 权限的 Personal Access Token。
3. Gitea 仓库 → 设置 → 仓库 → 镜像设置 → 添加推送镜像，填 GitHub 仓库地址和那个 token。
4. 之后每次 push 到 Gitea 会自动同步到 GitHub，在那边触发这个 workflow。

本地 git 用法完全不变，仍然只对 Gitea 一个远端 push。

如果以后更愿意全在自建上跑：Windows 的 act_runner 可以装成服务，macOS 自建比较麻烦。但不管走哪条路，**workflow 文件保持上面那个标准写法不动**。
