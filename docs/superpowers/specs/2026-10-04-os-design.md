# os 设计

- 日期：2026-10-04
- 状态：已实现
- 取代 [预期接口](2026-10-03-module-interfaces.md) 第 7 节。第二程第 6 项（`optional` 已先落地）。

## 1. 这个模块是做什么的

**核心只有一件事：让长期运行的进程能干净地停下来。** 路线图的需求表里 `信号与优雅退出` 对「多平台服务器」和「easytier 核心」两个场景都标着**必须**，是整个模块里唯一一个这种级别的。其余几项（环境变量、进程与机器信息）是顺带的，因为它们同样是「一件事三个平台 API 名字不同」。

实测差别（`examples/os.cpp`，循环写记录时发 SIGINT）：

```
默认行为：  record 0166:                     ← 停在一半，坏数据
装了处理器：record 651083: payload-complete  ← 写完当前记录
            [干净退出，共 651084 条]
```

**和 `coroutine` 不是一类活**，所以不合并：`os` 包装已有的系统调用、把平台差异收敛掉；`coroutine` 是平台根本没提供这件事，要自己写寄存器保存/恢复的汇编。体量也不是一个量级（见路线图 4.4、4.6）。

## 2. 接口

```cpp
namespace wavvix { namespace os {

optional<std::string> getenv(string_view name);        // 「没设置」不是失败
result<void> setenv(string_view name, string_view value);
result<void> unsetenv(string_view name);               // 幂等

result<std::string> executable_path();                 // 已解析符号链接的绝对路径
result<std::string> hostname();
long process_id() noexcept;
unsigned cpu_count() noexcept;                         // 至少 1

result<void> install_stop_handler();                   // 必须显式调用，幂等
bool stop_requested() noexcept;                        // 单向，不复位
void request_stop() noexcept;                          // 自己翻标志

}}
```

## 3. 关键决定

### 3.1 只提供一个标志，不提供「在信号里跑的回调」

预期接口原本有 `void on_signal(signal which, void (*handler)())`。**去掉了。**

信号处理函数里几乎什么都不能调：`printf`、`fclose`、`malloc`、加锁全不是 async-signal-safe 的——信号可能正好打在 `malloc` 持锁的时候，此时再 `malloc` 就是死锁。POSIX 只允许调 `signal-safety(7)` 里那张很短的白名单。

**一个收 `void(*)()` 的接口没法被安全使用**，给出来就是发一把枪：使用者会在里面写日志、关文件、释放资源，而那些全是未定义行为。按「难以误用」，这个接口不该存在。

库内的处理函数只做一件事：

```cpp
void raise_stop_flag(int) { detail::stop_flag = 1; }
```

真要自定义处理，自己调 `std::signal`，后果自负。

### 3.2 标志用 volatile sig_atomic_t，不用 std::atomic<bool>

`signal-safety(7)` 明确保证的是「对 `volatile sig_atomic_t` 的赋值」在处理函数里安全。`std::atomic` 的无锁性是实现定义的，而且标准没有把它列进 async-signal-safe 的清单。单向翻一个标志不需要更强的保证。

### 3.3 install_stop_handler 必须显式调用

修改进程级的信号处置是**调用方的决定**，库不在背后替它做——一个链接了 culib 的程序不该因为链接而改变自己对 SIGINT 的反应。这也符合「不在 `main` 之前执行任何代码」。

两边都做成幂等：POSIX 的 `sigaction` 天然覆盖；Windows 的 `SetConsoleCtrlHandler` **重复注册同一个函数会注册两次**（两次都会被调），所以先摘掉再装。

### 3.4 不设 SA_RESTART

**想要**阻塞的系统调用被 `EINTR` 打断：否则一个卡在 `read` 上的主循环收到信号也不会醒过来，`stop_requested()` 永远没机会被检查。代价是调用方要处理 `EINTR`，写进了 `os_posix.cpp` 的注释。

### 3.5 SIGHUP 保持默认

按惯例 SIGHUP 是「重载配置」而不是「停止」（nginx、apache 都这样），而热加载要等第三程的 `fs::watcher`。接它反而会让「收到 SIGHUP 就停」这个不符合惯例的行为被固化。

实测验证：发 SIGHUP 时进程退出码 129（128 + SIGHUP），说明没被接管。

### 3.6 砍掉动态库加载

预期接口原本有 `class library`（`open` / `symbol` / RAII 关闭）。**去掉了**：三个目标场景里没有插件架构，而它是本模块平台差异最大的部分（符号修饰、`RTLD_*` 标志、Windows 的 DLL 搜索路径与 `SetDefaultDllDirectories`）。按「一个模块在三个场景里都找不到消费者，就不该做」。真要做插件时再加。

**重开条件**：出现需要运行期加载代码的场景（插件、可选后端）。那时要连带决定「符号怎么导出」，那是比 `dlopen` 本身更大的设计问题。

### 3.7 不做崩溃调用栈

要 `dbghelp`（Windows，还得分发 PDB 才有符号）或 `backtrace`（glibc 扩展，musl 没有）。跨平台一致性在整个库里最差，而 **core dump 加 gdb 能解决同样的问题**。按「不碰需要第三方库的领域」的精神。

### 3.8 cpu_count 只修 hardware_concurrency 的一个毛病

`std::thread::hardware_concurrency()` 在 C++11 就有，所以这是个薄包装，唯一的作用是把「不知道时返回 0」改成至少 1——**0 对线程池没有意义**，而 `thread_pool` 否则就得自己写 `std::max(1u, ...)`。

**已知局限写进了头文件**：Linux 上它数的是在线 CPU 数而不是 cgroup 配额，所以容器里会多报。真要按配额开线程得读 `/sys/fs/cgroup`，那是 `thread` 模块该定的事，不在这里猜。

### 3.9 getenv 返回 optional，而空字符串是合法的值

「没设置」是正常结果不是失败，所以是 `optional`（见 [optional 设计](2026-10-04-optional-design.md) 第 1 节）。

**设置成空字符串和没设置是两回事**，两个平台都支持，测试里钉住了。这一点在 Windows 上差点写错，见 4.3。

## 4. 实现验证

环境 Linux / GCC 14.2 与 clang 19，`-Wall -Wextra -Wpedantic -Werror`，零警告；Windows 侧 MinGW-w64 + wine。

### 4.1 构建与测试

148 个测试通过（新增 6 个）：环境变量的读写删 + 覆盖 + 空值 + 非 ASCII 值 + 幂等删除、两种非法名字及其消息、`executable_path` 是绝对路径且那个文件真实存在且名字里有 `culib_test`、`hostname` 非空且不含空白、`process_id` 大于 0 且稳定、`cpu_count` 至少 1 且稳定、以及「没人叫停时 `stop_requested()` 是 false，而且装处理器本身不翻标志、重复装安全」。

**停止标志故意不在单元测试里测**：它按设计是单向的，调 `request_stop()` 会污染后面所有测试。那条路径用独立进程发真信号验证（见 4.2），那也比单元测试更接近真实用法。

### 4.2 真信号

`examples/os.cpp` 跑一个「写记录」的循环，外部发信号：

| 信号 | 退出码 | 行为 |
| --- | --- | --- |
| SIGINT | 0 | 写完当前记录，最后一行是 `[干净退出，共 651084 条]` |
| SIGTERM | 0 | 同上 |
| SIGHUP | **129** | 没被接管，走默认终止——符合 3.5 的设计 |

对照：不装处理器时文件停在 `record 0166: `，即一条记录写了一半。

**Windows 的控制台事件没有验证过**：wine 下没法可靠地投递 `CTRL_C_EVENT`（`kill -INT` 不会被翻译成控制台事件）。`console_handler` 的代码编译通过、逻辑按 MSDN 写，但那条路径一次都没执行过。**这是本模块最大的未验证面。**

### 4.3 MinGW + wine 抓到的第二个真 bug

`getenv` 在 Windows 上把「值为空字符串」当成了「没设置」。原因是 `GetEnvironmentVariableW` 两次调用的返回值含义不同：

| 调用方式 | 返回 | 值为空时 |
| --- | --- | --- |
| `(name, 0, 0)` | 需要的大小，**含**结尾 `'\0'` | **1** |
| `(name, buf, n)` | 存进去的字符数，**不含** `'\0'` | **0** |

第一版拿第二次的 0 判断「没设置」。正确的判别在第一次：返回 0 才是不存在，返回 1 就是「存在且为空」。用一个绕开 culib 的裸 `SetEnvironmentVariableW` / `GetEnvironmentVariableW` 程序确认了这个行为，才动手改。

**Linux 上 `std::getenv` 没有这个歧义**（空值返回指向 `""` 的指针，不存在返回 `NULL`），所以本机永远测不出来。这是 MinGW + wine 这套机制抓到的第二个真 bug，第一个是 `fs_win.cpp` 漏了 include。

### 4.4 没覆盖

- **MSVC 和 macOS 要等 CI。** macOS 的 `executable_path` 走 `_NSGetExecutablePath` + `realpath`，是和 Linux 完全不同的一条分支，**从未被任何机器编译过**（MinGW 不编译它，本机是 Linux）。
- **Windows 的控制台事件路径从未执行**，见 4.2。
- `hostname` 和 `executable_path` 的「缓冲区不够要重试」分支都没触发过：本机的主机名和路径都很短。那些循环是按文档写的，没有实测。
- 环境变量在**多线程**下读写没有保护。POSIX 的 `setenv` 不是线程安全的（和并发的 `getenv` 一起用是数据竞争）。目前的用法是「启动时读一次」，没问题；真要在运行期改环境变量就得加锁，到那时再说。头文件里**还没写这一条**，是个欠账。
