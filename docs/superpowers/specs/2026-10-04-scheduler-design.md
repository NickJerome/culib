# 调度器与 I/O 引擎：定位和那个决定全局的岔路

- 日期：2026-10-04
- 状态：**第一、二期已实现**（vCPU + 调度器、栈池）。**第三期（事件引擎）已单独设计**，见 [事件引擎设计](2026-10-05-event-engine-design.md)。第四期起未动。
- 前置：[coroutine 设计](2026-10-04-coroutine-design.md)（原语已完成）、路线图 4.2 / 4.6。
- **本文改变了库的定位**，见第 1 节。

## 1. 定位变了：协程是并发模型，不是一个工具

原来的定位（coroutine 设计第 1 节）是「这一程只做原语，调度器跟着 `net` 一起设计」。**作者的判断是协程应当是一等公民、协程取代线程**，并且指了 PhotonLibOS 作为参照。读完之后同意，而且我原来那个定位有个具体的错：

**我做的 API 是「生成器」形状，不是「goroutine」形状。** 调用方自己 `resume()` 推着跑——那是把协程当一个偶尔用的工具。如果协程是并发模型，`resume()` 就该是调度器的私事，用户只写 `spawn(f)` 然后不管。

### 已定

- **vCPU 模型**：一根操作系统线程 = 一个 vCPU，上面跑一个调度器和一堆协程。协程绑在 vCPU 上（[coroutine 设计](2026-10-04-coroutine-design.md) 3.13 已经把这条做成运行期检查了），跨 vCPU 要显式搬。
- **四个 I/O 后端**：`io_uring`、`epoll`、`kqueue`、`IOCP`，一套抽象。
- `thread` 模块因此缩水：不再是「线程池 + 任务队列」，而是「起 N 个 vCPU」加「一个给真阻塞活用的池子」（Photon 的 `WorkPool` 就是干这个的——既不能让出、又必须做的活，比如调一个只有阻塞版的第三方函数）。
- 同步原语（`mutex` / `condition_variable` / `semaphore` / `rwlock`）挪到协程这一层，名字和 `std::` 对齐。

### 已完成的东西没有白做

换栈汇编（五个目标）、保护页、ASan 注解、线程绑定检查全是地基，一行不动。变的是上面那层的定位。

## 2. 那个决定全局的岔路：抽象是「就绪」还是「完成」

这是本文唯一真正要紧的决定，因为它决定了四个后端里哪三个要写模拟层。

两种形状：

| | 形状 | 调用方看到的 |
| --- | --- | --- |
| **就绪**（readiness） | 「等到 fd 可读」，然后调用方自己做系统调用 | `wait_readable(fd); n = recv(fd, buf, len);` |
| **完成**（completion） | 「帮我读，读完叫我」 | `n = read(fd, buf, len);`（协程挂起，醒来结果在手） |

### 四个后端天然是哪一种

| 后端 | 天然形状 | 另一种形状要付什么 |
| --- | --- | --- |
| `epoll` | 就绪 | 做完成：等可读之后自己调一次系统调用。**三行** |
| `kqueue` | 就绪 | 同上。**三行** |
| `io_uring` | 完成 | 做就绪：用 `IORING_OP_POLL_ADD` 当通知器。能做，但等于放弃它的主要好处 |
| `IOCP` | 完成 | 做就绪：**Windows 没有「告诉我这个套接字何时可读」这种操作**。实际的做法比这里原先估的更糟——参照实现走的是未公开的内核接口（`\Device\Afd` + 硬编码的 `IOCTL_AFD_POLL`），外加一个自管道和一套重提交状态机。**2026-10-05 读源码核实后改正**，原文猜的是「零长度 `WSARecv` 这类技巧」，账单见 [事件引擎设计](2026-10-05-event-engine-design.md) 第 2 节 |

**所以选完成形状。** 模拟的方向是容易的那一边：就绪 → 完成是三行，完成 → 就绪在 Windows 上是一摊。

### 读过的三个库，正好印证

| 库 | 抽象形状 | 证据 | 它为什么这么选 |
| --- | --- | --- | --- |
| **PhotonLibOS** | **就绪** | `MasterEventEngine::wait_for_fd(int fd, uint32_t interest, Timeout)`，io_uring 后端用 `POLL_ADD` 实现它 | **Linux 优先**。它的 Windows 支持是次要的，所以 IOCP 那一格的别扭不要紧 |
| **libuv** | **完成** | `uv_read_cb(stream, ssize_t nread, const uv_buf_t* buf)` —— 给的是「已经读了多少、在哪」。`uv_poll_t` 只是给外部 fd 用的副通道，不是核心 | 跨平台，Windows 一等公民 |
| **asio** | **完成** | `handler(error_code, bytes_transferred)` | 同上 |

**规律：认真做 Windows 的库是完成形状，Linux 优先的是就绪形状。**

culib 承诺三个平台对等（README 的平台矩阵），所以 Photon 那个选择的弱点正好落在 culib 不能弱的地方。**这是本文和参照库最大的一处不同，而理由是 culib 自己的约束，不是口味。**

### 额外的好处：和协程的调用点天然一致

有协程之后，用户写的是：

```cpp
const ssize_t n = sock.read(buf, sizeof buf);   // 看起来是阻塞的
```

**从调用方看，这本来就是完成形状。** 选完成形状的内部抽象，等于内外一致；选就绪形状就要在中间多一层把「等可读 + 系统调用」包成「read」，每个后端包一遍。

## 3. 零第三方依赖对 io_uring 的后果

`liburing` 是通常的用法，但它是第三方库，而「零第三方依赖」是硬约束。

io_uring 本身是三个系统调用（`io_uring_setup` / `io_uring_enter` / `io_uring_register`），`liburing` 只是个便利封装。自己写要 `mmap` 两个环、处理 SQ/CQ 的 head/tail 内存序——约两三百行，路数是公开且成熟的。

**代价要记清楚**：这是四个后端里最难写也最难验证的一个，而且 CI 的容器里 seccomp 常常把 io_uring 挡掉。所以：

- **`epoll` 是 Linux 上的基准后端，`io_uring` 是运行期探测到可用才启用的加速。** 不是「有 io_uring 就不要 epoll」——探测失败要能无声退回。
- 内核下限按 README 的 glibc 2.17 算的话，io_uring（5.1 起）在相当多目标机器上没有，所以退回路径是常态而不是例外。

## 4. 「零配置」这条约定要给例外

约定原文：

> **零配置、零管理**：包含头文件即可使用，无需 `init()` / `cleanup()`

带 I/O 引擎的调度器绕不开初始化：epoll/kqueue/IOCP 的句柄要有人建、有人关，vCPU 要有人起。

**例外的形状是「用到才起」**：

- 第一次 `spawn` 协程时，当前线程自动变成 vCPU，事件引擎自动建起来；进程退出时自动收。
- 要控制参数（几个 vCPU、强制某个后端、io_uring 的队列深度）的再显式调一次初始化。
- **不 spawn 协程就什么都不初始化**，所以 CLI 场景（三个目标场景之一）一分钱不付，「无启动开销」那条也保住。

这样约定的精神（「简单的事一行完成」「零启动开销」）还在，只是把「绝对没有 init」放宽成「不用时没有、要调时可以调」。

## 5. 怎么分期：这是全库最大的一块，不能一口做完

体量上这已经不是一个模块，而是四五个。一口写完再测是最糟的做法——`coroutine` 那次就看到了，**arm64 和 MASM 两份汇编是推上 CI 才第一次被验证的**，而那只是一个模块的一部分。

分期的判据是**每一期都能单独验证**：

| 期 | 内容 | 验证靠什么 |
| --- | --- | --- |
| 1 | **vCPU + 调度器**，只有 `spawn` / `yield` / `sleep`，没有 I/O | **已完成**，见第 7 节 |
| 2 | **栈池化**，改默认栈大小 | **池已完成**（第 8 节）；默认栈大小还没改，见 8.4 |
| 3 | **事件引擎抽象 + `epoll` / `kqueue` / `IOCP` 三个后端** | 一套测试跑三个后端，行为必须一致。**设计见 [事件引擎设计](2026-10-05-event-engine-design.md)**，那条判据在那边否掉了两个标准优化 |
| 4 | **`io_uring` 后端 + 运行期探测与退回** | 同一套测试在 io_uring 和 epoll 下结果相同；强制关掉 io_uring 也要过 |
| 5 | **协程感知的同步原语** | 多协程竞争、超时、唤醒公平性 |
| 6 | **`net`** | 真的收发 |

第 1 期之后就能回答「协程取代线程」这句话落地成什么样；第 3 期之后三平台对等才算兑现。

### 栈的两个数要改

| | 现在 | 要改成 | 理由 |
| --- | --- | --- | --- |
| 默认栈 | 128 KB | **更大**（Photon 是 8 MB） | 协程取代线程，就得能跑任意代码——深递归、假设自己在线程栈上的库函数。128 KB 会炸，而且是栈溢出那种炸法 |
| 创建开销 | 7 µs（三个系统调用） | 池化之后应到百纳秒级 | 一个请求一根协程时，7 µs 太慢 |

具体数字等第 2 期实测，不在这里拍。Photon 的栈池分「每 vCPU」和「全进程」两档，而且**默认不池化**——那是它的选择，我们要不要默认池化等量完再定。

## 6. 还没定的

- **具体接口**。按开发约定，接口要先列表格、配可运行用例过给作者，再写代码。本文不越过那一步。
- **协程感知的 `mutex` 等要不要像 Photon 那样提供 `std::` 替身命名空间**（`photon_std::`），让现有线程代码原样改。倾向不做：那是给「迁移存量代码」用的，而 culib 没有存量。
- **`resume()` 要不要从公共 API 拿掉**。Photon 不暴露它（只有 `thread_yield_to`）。倾向保留但降级：`spawn` 是主路，`resume` 留给明确要手动驱动的场合，文档写明两者不能混用同一根协程。
- **vCPU 之间要不要偷活**。协程绑定是现在的语义，显式 `migrate` 是 Photon 的做法。自动偷活要先解决 [coroutine 设计](2026-10-04-coroutine-design.md) 3.12 里那两条（`thread_local` 语义、`__cxa_eh_globals`），其中第一条库修不了。

## 7. 第一期的实现验证：vCPU + 调度器

`include/culib/scheduler.h` 四个入口加两个查询：

| 签名 | 说明 |
| --- | --- |
| `template <typename F> void spawn(F body, std::size_t stack_size = default_stack_size)` | 起一根，排进当前 vCPU。协程里也能调 |
| `void yield()` | 让出，排到队尾。只能在协程里 |
| `void sleep_for(std::chrono::nanoseconds)` | 协程里是挂起 + 定时器；**协程外是真睡线程** |
| `std::size_t run()` | 把当前线程变成 vCPU，跑到全部结束，返回跑完几根 |
| `std::size_t scheduled()` | 还剩几根（含在睡的） |

### 7.1 调度器只有一个要紧的结构

**跑一轮时把整个 ready 队列 `swap` 到局部变量再遍历。** 因为协程在跑的过程中会 `spawn`、会 `sleep`，那些都改动成员容器——直接遍历成员容器的话，一次 `push_back` 扩容就让迭代失效，而那种崩溃只在「刚好扩容」时出现，是最难复现的一类。

三个队列：`ready`（本轮/下一轮跑）、`sleeping`（等定时器）、`incoming`（正在跑的协程 spawn 出来的）。`incoming` 分开是同一个理由。

### 7.2 睡眠用单调时钟

`std::chrono::steady_clock`，不是 `time` 模块的 `timestamp`（那是墙上时钟）。墙上时钟会被改系统时间带着跳，「睡 10 毫秒」就可能变成睡一小时或者立刻醒。

### 7.3 「用到才起」兑现了

vCPU 在第一次 `spawn` 时才建。`scheduled()` 在没 spawn 过时直接读 `thread_local` 指针、看到 0 就返回 0，**一次分配都没有**。不用协程的程序（CLI 场景）一分钱不付。

每根线程一个 vCPU 对象，**故意泄漏到进程结束**——vCPU 的生命周期就是线程的生命周期，而「线程退出时精确回收」要 `pthread_key` / `FlsAlloc`，为一个指针不值当。ASan 开 `detect_leaks=1` 没报，因为 `thread_local` 指针还指着它。

### 7.4 实际输出

`examples/scheduler.cpp`：

```
1. spawn 完就不管，调度器负责推
   执行顺序 甲乙甲乙甲乙   跑完 2 根（轮转，不是一根跑到底）

2. 睡的是协程，不是线程
   一根睡了 30 ms，另一根在这段时间里转了 225002 轮
   总共花了 30.08 ms —— 线程没被睡住，只有那一根协程在等

3. 定时器按时间排序唤醒
   spawn 的顺序是 C A B，醒来的顺序是 ABC

4. 协程里还能再 spawn
   一根父协程起了 4 根子协程，总共跑完 5 根

5. vCPU 模型：一根线程一个调度器，想用多核就多调几次 run()
   3 个 vCPU 各跑 50 根，共 150 根，花了 11.04 ms
   每个 vCPU 有自己的运行队列，不加锁，协程也不会被偷到别的 vCPU
```

第 2 段那个 **22.5 万轮**是「睡的是协程不是线程」最直白的证据：那 30 毫秒里 vCPU 一直在干活。

### 7.5 测试

12 条：空跑、单根跑完、让出轮转（断言 `甲乙甲乙甲乙` 这个确切顺序）、嵌套 spawn、200 根不丢、**睡的那根不卡住别人**（断言对面转了 10 轮以上）、定时器按时间排序（spawn 顺序 C A B，断言醒来是 ABC）、**同一轮里多个定时器到期时仍按时间排序**（见 7.6）、协程外 sleep 真睡线程、`scheduled()` 计数、每根协程的栈互不干扰、跑完再跑返回 0。

### 7.6 「定时器按时间排序唤醒」原先只在 Linux 上碰巧成立

**2026-10-05 补：这是一个真 bug，不是 flaky 测试。** 第三期做完推 CI 时，`macos-clang` 两格和 `windows-msvc / release` 都挂在 7.4 第 3 段那条测试上，拿到的是 `"CAB"` 和 `"ACB"`。

原因在 `run()` 第 2 步：到期的睡眠任务当时是**按它们在 `sleeping` 容器里的次序**搬回 `ready` 的，而那个次序就是 spawn 次序。

- **Linux 上看不出来**：空闲路径正好睡到最早那个 deadline，所以三个 sleeper 各自单独一轮醒，一轮里只有一个到期，容器次序和时间次序没有区别。
- **macOS 和 Windows 上就不行**：定时器粒度更粗，一次睡眠 overshoot 到好几个一起到期，于是按 spawn 次序唤醒。

改法是**到期的那一批按 `wake_at` 排序再入队**，用 `stable_sort`：deadline 相同时按 spawn 次序醒，那是能预期也能测的，unstable 排序会让它变成「不保证」。

**原来那条测试查不出这个毛病**，因为它依赖平台的定时器粒度。新加的那条不依赖：让另一根协程**不让出**地占住 vCPU 直到所有 deadline 都过去，三个必定落在同一轮。它在 Linux 上复现出和 macOS CI 一模一样的 `"CAB"`，修完才绿。

**顺带一条教训**：`sleeping` 现在仍是无序 `vector`，每轮扫一遍找到期的、再排序。sleeper 很多时该换成按 `wake_at` 的最小堆（找最早的从 O(n) 变 O(1)，而且到期的天然有序，不用排）。**什么条件下换**：量出这一遍扫描在定时器密集的负载里占比显著。现在不换，因为每轮本来就要扫一遍。

## 8. 第二期的实现验证：栈池

### 8.1 为什么必须做

不池化时一根协程的栈要三个系统调用。实测：

| | 耗时 |
| --- | --- |
| `mmap` + `mprotect` + `munmap` | **5586 ns** |
| 池命中，什么都不做 | **0 ns** |

协程当并发模型用（一个请求一根）时，这个差别决定能不能用。

### 8.2 借了 mimalloc 两条，明确不要第三条

读了 mimalloc 的 `types.h`。它每页有三条空闲链表（`free` / `local_free` / `thread_free`），注释说得很清楚：`local_free` 让延迟回收变成确定性的节拍，`thread_free` 是**为了让常见路径不用原子操作**。

| mimalloc 的做法 | 我们 | 为什么 |
| --- | --- | --- |
| 线程本地堆，常见路径无锁无原子 | **照抄**。每线程一组桶 | 协程绑 vCPU，所以队列本来就不跨线程 |
| 空闲链表的节点放在空闲内存自己身上 | **照抄**。节点写在栈的低端（保护页上方） | 池本身不需要任何额外分配 |
| `thread_free`：别的线程释放的块要还给原主 | **不要** | **我们的块是栈，彼此可互换**——在哪根线程释放就进那根线程的池，没有归属问题。少一条原子链表 |

第三条是实质简化，而理由是我们的块比 mimalloc 的块弱一个约束。

### 8.3 回收时不把物理页还给系统

| 做法 | 耗时 |
| --- | --- |
| 什么都不做 | **0 ns** |
| `madvise(MADV_DONTNEED)` 整个栈 | 1587 ns |
| 只还深处那一半 | 280 ns |

**选 0 ns**：没被摸过的页本来就不占物理内存，只有真递归很深的协程才会留下常驻页。代价是内存高水位会留着，所以用**每线程缓存字节数上限**兜住（64 位 32 MB、32 位 8 MB），超了就真 `munmap`。

**按字节封顶而不是按个数**：否则 8 MB 的栈会凭个数把地址空间占光。

真遇到高水位有害的负载，再把「只还深处一半」那条 280 ns 的做法做成可选——现在不做，因为没有消费者。

### 8.4 分桶：向上取整到 2 的幂

桶的大小都是 2 的幂且不小于 4096，所以「按桶大小分配」之后再反查桶号一定得到同一个桶——**释放时不需要额外记住它是从哪个桶来的**。

多出来的是虚拟地址，没碰到的页不占物理内存，这也是每个分配器都在做的事。

**默认栈大小还没改**（现在 128 KB）。设计文档第 5 节说要加大（Photon 是 8 MB），但那个数要配合「池按字节封顶」一起定：8 MB 的栈在 32 MB 预算下只能缓存 4 根，池就基本没用了。所以这两个数要一起量，排在第三期之后。

### 8.5 效果

`examples/scheduler.cpp` 第 6 段，同一次运行里量冷热两条路：

```
6. spawn 的开销：冷和热差两个数量级
   冷（先攒两万根再跑）    6682 ns/根   池是空的，每根真分配一次栈
   热（spawn 一根跑一根）   111 ns/根   池命中，零系统调用
```

**60 倍**。服务器是第二种形状（一个请求一根协程，上一根结束时栈进池子）。

协程原语那边同样受益：`examples/coroutine.cpp` 的「创建加销毁一根」从约 7000 ns 降到 **38 ns**。

### 8.6 测试

三条，**都不靠计时**（计时在 CI 上会抖）：

- `reuses_stacks_from_the_pool`：两根协程里同一位置的局部变量**地址相同**，证明栈被复用了。确定性的。
- `rounds_stack_requests_into_buckets`：40 KB 和 50 KB 的请求复用同一块栈（同桶），4 MB 的请求用另一块。
- `keeps_pooled_stacks_usable_after_heavy_churn`：200 轮复用，每轮把 4 KB 栈空间写满再核对——池化最怕「上一根留下的东西把下一根搞坏」。

### 8.7 验证面

190 个测试在 GCC 14.2 和 clang 19 × debug/release 下通过，零警告；MinGW-w64 x64 + wine 同样 190 个通过；MinGW x86 编译链接通过（跑不了，wine 没 WOW64）。

ASan 开 `detect_leaks=1` 跑「300 轮 spawn + 8 KB 栈写满 + 协程栈上抛接异常 + sleep」干净——**栈池改了内存的生命周期，所以这一遍必须重跑**。
